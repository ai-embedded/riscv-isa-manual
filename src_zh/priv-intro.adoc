[[priv-intro]]

== 引言

本文档描述了 RISC-V 特权架构，涵盖了 RISC-V 系统中除非特权 ISA 之外的所有方面，包括特权指令以及运行操作系统和连接外部设备所需的附加功能。

[NOTE]
====
我们设计决策的评论格式与本段落相同，如果读者只对规范本身感兴趣，可以跳过。

***
我们简要指出，本文档中描述的整个特权级设计可以用完全不同的特权级设计替换，而无需更改非特权 ISA，甚至可能无需更改 ABI。特别是，此特权规范旨在运行现有流行的操作系统，因此体现了传统的基于级别的保护模型。替代特权规范可以体现其他更灵活的保护域模型。为了表达的简洁性，文本的编写方式就好像这是唯一可能的特权架构一样。
====

=== RISC-V 特权软件栈术语

本节描述了我们用于描述 RISC-V 各种可能的特权软件栈组件的术语。

<<privimps>> 展示了 RISC-V 架构可以支持的一些可能的软件栈。左侧显示了一个简单的系统，它仅支持在应用程序执行环境 (AEE) 上运行单个应用程序。应用程序被编码为使用特定的应用程序二进制接口 (ABI) 运行。ABI 包括支持的用户级 ISA 以及一组与 AEE 交互的 ABI 调用。ABI 向应用程序隐藏了 AEE 的细节，以便在实现 AEE 时提供更大的灵活性。相同的 ABI 可以在多个不同的主机操作系统上原生实现，或者可以在具有不同原生 ISA 的机器上运行的用户模式仿真环境支持。

[NOTE]
====
我们的图形约定使用带有白色文本的黑框表示抽象接口，以将其与实现接口的组件的具体实例区分开来。
====
[[privimps]]
.支持各种形式特权执行的不同实现栈。
image::png/privimps.png[]

中间的配置显示了一个传统的操作系统 (OS)，它可以支持多个应用程序的多程序执行。每个应用程序通过 ABI 与 OS 通信，OS 提供 AEE。就像应用程序通过 ABI 与 AEE 交互一样，RISC-V 操作系统通过 supervisor 二进制接口 (SBI) 与 supervisor 执行环境 (SEE) 交互。SBI 包括用户级和 supervisor 级 ISA 以及一组 SBI 函数调用。在所有 SEE 实现中使用单个 SBI 允许单个 OS 二进制映像在任何 SEE 上运行。SEE 可以是低端硬件平台中的简单引导加载程序和 BIOS 风格的 IO 系统，或者是高端服务器中由 hypervisor 提供的虚拟机，或者是架构仿真环境中主机操作系统之上的薄转换层。

[NOTE]
====
大多数 supervisor 级 ISA 定义没有将 SBI 与执行环境和/或硬件平台分离，这使得虚拟化和新硬件平台的启动复杂化。
====
最右侧的配置显示了一个虚拟机监视器配置，其中单个 hypervisor 支持多个多程序 OS。每个 OS 通过 SBI 与 hypervisor 通信，hypervisor 提供 SEE。hypervisor 使用 hypervisor 二进制接口 (HBI) 与 hypervisor 执行环境 (HEE) 通信，以将 hypervisor 与硬件平台的细节隔离开来。

[NOTE]
====
ABI、SBI 和 HBI 仍在开发中，但我们现在优先支持 Type-2 hypervisor，其中 SBI 由 S 模式 OS 递归提供。
====

RISC-V ISA 的硬件实现通常需要除特权 ISA 之外的附加功能来支持各种执行环境（AEE、SEE 或 HEE）。

=== 特权级别

在任何时候，RISC-V 硬件线程 (_hart_) 都以某种特权级别运行，该级别编码在一个或多个 CSR（控制和状态寄存器）中的模式中。目前定义了三个 RISC-V 特权级别，如 <<privlevels>> 所示。

特权级别用于在软件栈的不同组件之间提供保护，尝试执行当前特权模式不允许的操作将导致引发异常。这些异常通常会导致陷阱进入底层执行环境。

[NOTE]
====
在描述中，我们试图将编写代码的特权级别与运行代码的特权模式分开，尽管两者通常是紧密相关的。例如，supervisor 级操作系统可以在具有三个特权模式的系统上以 supervisor 模式运行，但也可以在具有两个或更多特权模式的系统上在经典虚拟机监视器下以用户模式运行。在这两种情况下，可以使用相同的 supervisor 级操作系统二进制代码，该代码根据 supervisor 级 SBI 编码，因此期望能够使用 supervisor 级特权指令和 CSR。当在用户模式下运行客户操作系统时，所有 supervisor 级操作都将被捕获并由在更高特权级别运行的 SEE 模拟。
====
机器级别具有最高特权，并且是 RISC-V 硬件平台唯一强制的特权级别。在机器模式 (M 模式) 下运行的代码通常是固有受信任的，因为它对机器实现具有低级访问权限。M 模式可用于管理 RISC-V 上的安全执行环境。用户模式 (U 模式) 和 supervisor 模式 (S 模式) 分别用于常规应用程序和操作系统使用。

每个特权级别都有一组核心特权 ISA 扩展，以及可选的扩展和变体。例如，机器模式支持内存保护的可选标准扩展。此外，supervisor 模式可以扩展以支持 Type-2 hypervisor 执行，如 <<hypervisor>> 中所述。

实现可以提供 1 到 3 种特权模式，以较低的实现成本换取较低的隔离度，如 <<privcombs>> 所示。

所有硬件实现都必须提供 M 模式，因为这是唯一可以无限制访问整个机器的模式。最简单的 RISC-V 实现可能只提供 M 模式，尽管这无法提供针对不正确或恶意应用程序代码的保护。

[NOTE]
====
可选 PMP 功能的锁定功能即使仅实现 M 模式，也可以提供一些有限的保护。
====
许多 RISC-V 实现还将至少支持用户模式 (U 模式)，以保护系统的其余部分免受应用程序代码的影响。可以添加 supervisor 模式 (S 模式) 以在 supervisor 级操作系统和 SEE 之间提供隔离。

hart 通常在 U 模式下运行应用程序代码，直到某个陷阱（例如，supervisor 调用或定时器中断）强制切换到陷阱处理程序，该处理程序通常在更特权的模式下运行。然后 hart 将执行陷阱处理程序，该处理程序最终将在 U 模式下恢复执行，从原始陷阱指令处或之后。增加特权级别的陷阱称为 _垂直_ 陷阱，而保持在相同特权级别的陷阱称为 _水平_ 陷阱。RISC-V 特权架构提供了灵活的陷阱路由到不同特权层。

[NOTE]
====
水平陷阱可以实现为垂直陷阱，将控制权返回到较低特权模式下的水平陷阱处理程序。
====

=== 调试模式

实现还可以包括调试模式，以支持片外调试和/或制造测试。调试模式 (D 模式) 可以被视为一个附加特权模式，具有比 M 模式更多的访问权限。单独的调试规范提案描述了 RISC-V hart 在调试模式下的操作。调试模式保留了一些仅在 D 模式下可访问的 CSR 地址，并且还可能保留平台上的物理地址空间的某些部分。
