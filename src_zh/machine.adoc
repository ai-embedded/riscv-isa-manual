[[machine]]
== 机器级 ISA，版本 1.13

本章描述了机器模式（M 模式）中可用的机器级操作，M 模式是 RISC-V hart 中最高的特权模式。M 模式用于对硬件平台进行低级访问，并且是复位时进入的第一个模式。M 模式还可以用于实现直接在硬件中实现过于困难或昂贵的功能。RISC-V 机器级 ISA 包含一个通用核心，该核心根据支持的其他特权级别和硬件实现的其他细节进行扩展。

=== 机器级 CSR

除了本节中描述的机器级 CSR 之外，M 模式代码还可以访问较低特权级别的所有 CSR。

[[misa]]
==== 机器 ISA (`misa`) 寄存器

`misa` CSR 是一个 *WARL* 读写寄存器，报告 hart 支持的 ISA。该寄存器在任何实现中都必须可读，但可以返回零值以指示 `misa` 寄存器未实现，这要求通过单独的非标准机制确定 CPU 功能。

.机器 ISA 寄存器 (misa)

MXL（机器 XLEN）字段编码原生基本整数 ISA 宽度，如 <<misabase>> 所示。MXL 字段是只读的。如果 `misa` 非零，MXL 字段指示 M 模式下的有效 XLEN，一个称为 _MXLEN_ 的常量。XLEN 从不大于 MXLEN，但在较低特权模式下 XLEN 可能小于 MXLEN。

[NOTE]
====
基本宽度可以通过对返回的 `misa` 值的符号进行分支，以及可能左移一位并对符号进行第二次分支来快速确定。这些检查可以在汇编代码中编写，而无需知道 hart 的寄存器宽度 (MXLEN)。基本宽度由 __MXLEN=2^MXL+4^__ 给出。

如果 `misa` 为零，也可以通过将立即数 2 放入寄存器，然后将寄存器左移 31 位来找到基本宽度。如果为零，则 hart 为 RV32，否则为 RV64。
====

Extensions 字段编码标准扩展的存在，每个字母一个位（位 0 编码扩展“A”的存在，位 1 编码扩展“B”的存在，直到位 25 编码“Z”）。“I”位将为 RV32I 和 RV64I 基本 ISA 设置，“E”位将为 RV32E 和 RV64E 设置。
Extensions 字段是一个 *WARL* 字段，可以包含可写位，其中实现允许修改支持的 ISA。复位时，Extensions 字段应包含支持的最大扩展集，如果“I”和“E”都可用，则应选择“I”而不是“E”。

当通过清除 `misa` 中的位来禁用标准扩展时，该扩展定义或修改的指令和 CSR 将恢复其定义或保留的行为，就像该扩展未实现一样。

[NOTE]
====
对于给定的 RISC-V 执行环境，指令、扩展或其他 RISC-V ISA 功能通常通过该环境中可观察到的执行行为来判断是否 _已实现_。例如，如果 F 扩展的指令按指定执行，则 F 扩展被认为已为执行环境实现。

根据 _已实现_ 的此定义，通过清除 `misa` 中的位来禁用扩展会导致该扩展在 M 模式下被视为 _未实现_。例如，设置 `misa`.F=0 会导致 F 扩展在 M 模式下未实现，因为 F 扩展的指令将不按非特权 ISA 的要求执行，而是可能引发非法指令异常。

严格根据可观察行为定义术语 _已实现_ 可能与同一词的其他常见理解冲突。特别是，尽管常见用法可能允许“已实现但已禁用”的组合，但在本文档中，这被认为是术语的矛盾，因为 _禁用_ 意味着执行不会按要求行为，以便该功能被视为 _已实现_。同样，此处“已实现且已启用”是冗余的；“已实现”就足够了。
====

如果存在任何非标准扩展，则“X”位将设置。

当“B”位为 1 时，实现支持 Zba、Zbb 和 Zbs 扩展提供的指令。当“B”位为 0 时，表示实现可能不支持一个或多个 Zba、Zbb 或 Zbs 扩展。

当“M”位为 1 时，实现支持 M 扩展定义的所有乘法和除法指令。当“M”位为 0 时，表示实现可能不支持这些指令。但是，如果支持 Zmmul 扩展，则无论“M”位的值如何，都支持其指定的乘法指令。

当“S”位为 1 时，实现支持 supervisor 模式。
当“S”位为 0 时，实现可能不支持 supervisor 模式。

当“U”位为 1 时，实现支持用户模式。
当“U”位为 0 时，实现可能不支持用户模式。

[NOTE]
====
`misa` CSR 向机器模式代码公开了 CPU 功能的基本目录。更广泛的信息可以在机器模式下通过探测其他机器寄存器和检查系统中其他 ROM 存储来获取，作为启动过程的一部分。

我们要求较低特权级别执行环境调用，而不是读取 CPU 寄存器来确定每个特权级别可用的功能。这使得虚拟化层可以更改在任何级别观察到的 ISA，并支持更丰富的命令接口，而不会给硬件设计带来负担。
====

“E”位是只读的。除非 `misa` 全为只读零，否则“E”位始终读取为“I”位的补码。如果执行环境同时支持 RV32E 和 RV32I，软件可以通过清除“I”位来选择 RV32E。

如果 ISA 功能 _x_ 依赖于 ISA 功能 _y_，则尝试启用功能 _x_ 但禁用功能 _y_ 会导致两个功能都被禁用。例如，设置“F”=0 和“D”=1 会导致“F”和“D”都被清除。
同样，设置“U”=0 和“S”=1 会导致“U”和“S”都被清除。

实现可以对两个或多个 `misa` 字段的集体设置施加额外约束，在这种情况下，它们作为一个 *WARL* 字段集体发挥作用。尝试写入不支持的组合会导致这些位设置为某个支持的组合。

写入 `misa` 可能会增加 IALIGN，例如，通过禁用“C”扩展。如果写入 `misa` 的指令增加了 IALIGN，并且后续指令的地址未对齐 IALIGN 位，则对 `misa` 的写入将被抑制，使 `misa` 保持不变。

当软件启用以前禁用的扩展时，除非该扩展另有规定，否则与该扩展唯一关联的所有状态都是未指定的。

注意：尽管 `misa` 中位 25-0 中的一个位设置为 1 意味着相应的功能已实现，但反之不一定成立：这些位中的一个位清除不一定意味着相应的功能未实现。这是因为，当某个功能未实现时，相应的操作码和 CSR 变为保留，不一定是非法。

==== 机器供应商 ID (`mvendorid`) 寄存器

`mvendorid` CSR 是一个 32 位只读寄存器，提供核心提供商的 JEDEC 制造商 ID。该寄存器在任何实现中都必须可读，但可以返回 0 值以指示该字段未实现或这是非商业实现。

//.供应商 ID 寄存器 (`mvendorid`)
//image::png/mvendorid.png[align="center"]

.供应商 ID 寄存器 (`mvendorid`)
include::images/bytefield/mvendorid.edn[]

JEDEC 制造商 ID 通常编码为一系列单字节延续代码 `0x7f`，以不等于 `0x7f` 的单字节 ID 终止，每个字节的最高有效位中有一个奇偶校验位。
`mvendorid` 在 Bank 字段中编码单字节延续代码的数量，并在 Offset 字段中编码最终字节，丢弃奇偶校验位。例如，JEDEC 制造商 ID `0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x8a`（十二个延续代码后跟 `0x8a`）将在 `mvendorid` CSR 中编码为 `0x60a`。

[NOTE]
====
在 JEDEC 的说法中，银行号比延续代码的数量大一；因此，`mvendorid` Bank 字段编码的值比 JEDEC 银行号小一。

***
以前，供应商 ID 是由 RISC-V International 分配的数字，但这与 JEDEC 维护制造商 ID 标准的工作重复。在撰写本文时，向 JEDEC 注册制造商 ID 的一次性费用为 500 美元。
====

==== 机器架构 ID (`marchid`) 寄存器

`marchid` CSR 是一个 MXLEN 位只读寄存器，编码 hart 的基本微架构。该寄存器在任何实现中都必须可读，但可以返回 0 值以指示该字段未实现。`mvendorid` 和 `marchid` 的组合应唯一标识所实现的 hart 微架构类型。

.机器架构 ID (`marchid`) 寄存器
include::images/bytefield/marchid.edn[]

开源项目架构 ID 由 RISC-V International 全局分配，具有非零架构 ID，最高有效位 (MSB) 为零。商业架构 ID 由每个商业供应商独立分配，但必须设置 MSB，并且其余 MXLEN-1 位不能包含零。

[NOTE]
====
目的是让架构 ID 代表与开发相关的项目微架构，而不是特定的组织。开源设计的商业制造应（并且可能被许可要求）保留原始架构 ID。这将有助于减少碎片化和工具支持成本，并提供归属。开源架构 ID 由 RISC-V International 管理，并且只应分配给已发布、正常运行的开源项目。商业架构 ID 可以由任何注册供应商独立管理，但要求其 ID 与开源架构 ID（MSB 设置）不重叠，以防止供应商希望同时使用闭源和开源微架构时发生冲突。

以下 Implementation 字段中采用的约定可用于区分同一架构设计的不同分支，包括按组织区分。`misa` 寄存器也有助于区分设计的不同变体。
====

==== 机器实现 ID (`mimpid`) 寄存器

`mimpid` CSR 提供处理器实现版本的唯一编码。该寄存器在任何实现中都必须可读，但可以返回 0 值以指示该字段未实现。Implementation 值应反映 RISC-V 处理器本身的设计，而不是任何周围系统。

==== Hart ID (`mhartid`) 寄存器

`mhartid` CSR 是一个 MXLEN 位只读寄存器，包含运行代码的硬件线程的整数 ID。该寄存器在任何实现中都必须可读。Hart ID 在多处理器系统中可能不一定连续编号，但至少一个 hart 必须具有 ID 为零的 hart。Hart ID 在执行环境中必须是唯一的。

.Hart ID (`mhartid`) 寄存器
include::images/bytefield/mhartid.edn[]

[NOTE]
====
在某些情况下，我们必须确保只有一个 hart 运行某些代码（例如，复位时），因此要求一个 hart 具有已知的 hart ID 为零。

为了提高效率，系统实现者应旨在减小系统中使用的最大 hart ID 的大小。
====

[[privstack]]
===== `mstatus` 寄存器中的特权和全局中断使能栈

全局中断使能位 MIE 和 SIE 分别用于 M 模式和 S 模式。这些位主要用于保证当前特权模式下中断处理程序的原子性。

[NOTE]
====
全局 __x__IE 位位于 `mstatus` 的低位，允许它们通过单个 CSR 指令原子地设置或清除。
====

当 hart 在特权模式 _x_ 中执行时，当 __x__IE=1 时全局启用中断，当 __x__IE=0 时全局禁用中断。对于较低特权模式 __w__<__x__ 的中断，无论较低特权模式的任何全局 __w__IE 位设置如何，始终全局禁用。对于较高特权模式 __y__>__x__ 的中断，无论较高特权模式的全局 __y__IE 位设置如何，始终全局启用。较高特权级别代码可以使用单独的每个中断使能位来禁用选定的较高特权模式中断，然后将控制权交给较低特权模式。
如果未实现 supervisor 模式，则 SIE 和 SPIE 为只读 0。

[NOTE]
====
较高特权模式 _y_ 可以在将控制权交给较低特权模式之前禁用其所有中断，但这将是不寻常的，因为它只会留下同步陷阱、不可屏蔽中断或复位作为重新获得 hart 控制权的方式。
====

为了支持嵌套陷阱，每个可以响应中断的特权模式 _x_ 都有一个两级中断使能位和特权模式栈。__x__PIE 保存陷阱之前活动的中断使能位的值，__x__PP 保存先前的特权模式。__x__PP 字段只能保存特权模式直到 _x_，因此 MPP 宽两比特，SPP 宽一比特。当从特权模式 _y_ 陷入特权模式 _x_ 时，__x__PIE 设置为 __x__IE 的值；__x__IE 设置为 0；__x__PP 设置为 _y_。

[NOTE]
====
对于较低特权模式，任何陷阱（同步或异步）通常都在较高特权模式下发生，并且在进入时禁用中断。高级陷阱处理程序将处理陷阱并使用堆栈信息返回，或者，如果未立即返回到中断上下文，则在重新启用中断之前保存特权堆栈，因此每个堆栈只需要一个条目。
====

MRET 或 SRET 指令分别用于从 M 模式或 S 模式的陷阱返回。执行 __x__RET 指令时，假设 __x__PP 保存值 _y_，__x__IE 设置为 __x__PIE；特权模式更改为 _y_；__x__PIE 设置为 1；__x__PP 设置为最低特权支持模式（如果实现了 U 模式则为 U，否则为 M）。如果 __y__≠M，__x__RET 还会设置 MPRV=0。

[NOTE]
====
在 __x__RET 上将 __x__PP 设置为最低特权支持模式有助于识别两级特权模式堆栈管理中的软件错误。
====

[NOTE]
====
陷阱处理程序必须设计为在处理陷阱的关键状态信息（处理和从陷阱恢复所需）的阶段既不启用中断也不引发异常。在此陷阱处理关键阶段发生的异常或中断可能导致陷阱覆盖此类关键状态。这可能导致恢复初始陷阱所需的数据丢失。此外，如果处理陷阱所需的代码路径中发生异常，则这种情况可能导致无限循环的陷阱。为防止这种情况，陷阱处理程序必须精心设计，以识别并安全地管理其操作流程中的异常。
====

__x__PP 字段是 *WARL* 字段，只能保存特权模式 _x_ 和任何低于 _x_ 的已实现特权模式。如果未实现特权模式 _x_，则 __x__PP 必须为只读 0。

[NOTE]
====
M 模式软件可以通过将特权模式写入 MPP 然后读回它来确定是否实现了特权模式。

如果机器只提供 U 和 M 模式，则只需要一个硬件存储位来表示 MPP 中的 00 或 11。
====

[[machine-double-trap]]
===== `mstatus` 寄存器中的双重陷阱控制

双重陷阱通常发生在陷阱处理操作的敏感阶段——当陷阱处理程序（负责管理这些事件的组件）处于不可重入状态时发生异常或中断。这种不可重入通常发生在陷阱处理的早期阶段，此时陷阱处理程序尚未保存处理和从陷阱恢复所需的必要状态。在此阶段发生陷阱可能导致关键状态信息被覆盖，从而导致恢复初始陷阱所需的数据丢失。此后，导致此关键错误条件的陷阱称为 _意外陷阱_。陷阱处理程序设计为在此处理阶段既不启用中断也不引发异常。然而，管理可能不可预测发生的硬件错误异常，对陷阱处理程序实现提出了重大挑战，因为存在双重陷阱的潜在风险。

MDT（机器禁用陷阱）位是 Smdbltrp 扩展引入的 WARL 字段。复位时，`MDT` 字段设置为 1。当 `MDT` 位通过显式 CSR 写入设置为 1 时，`MIE`（机器中断使能）位清除为 0。对于 RV64，无论同一写入是否写入 `MIE` 位，此清除都会发生。`MIE` 位只能通过显式 CSR 写入设置为 1，如果 `MDT` 位已为 0，或者对于 RV64，正在通过同一写入设置为 0（对于 RV32，`MDT` 位在 `mstatush` 中，`MIE` 位在 `mstatus` 寄存器中）。

当陷阱将进入 M 模式时，如果 `MDT` 位当前为 0，则将其设置为 1，并且陷阱按预期传递。但是，如果 `MDT` 已设置为 1，则这是一个 _意外陷阱_。当 Smrnmi 扩展实现时，由 RNMI 引起的陷阱不被视为 _意外陷阱_，无论 `MDT` 位的状态如何。由 RNMI 引起的陷阱不会设置 `MDT` 位。然而，当在 M 模式下执行且 `mnstatus.NMIE` 设置为 0 时发生的陷阱是 _意外陷阱_。

发生 _意外陷阱_ 时，处理如下：

* 当 Smrnmi 扩展实现且 `mnstatus.NMIE` 为 1 时，hart 陷阱到 RNMI 处理程序。为了传递此陷阱，`mnepc` 和 `mncause` 寄存器分别写入 _意外陷阱_ 将写入 `mepc` 和 `mcause` 寄存器的值。`mnstatus` 寄存器中的特权模式信息字段被写入以指示 M 模式，并且其 `NMIE` 字段设置为 0。

[NOTE]
====
此规范的结果是，在发生双重陷阱时，RNMI 处理程序未提供陷阱在 `mtval` 和 `mtval2` 寄存器中报告的信息。如果需要，RNMI 处理程序可以通过解码 `mnepc` 中地址处的指令并检查其源寄存器内容来获取此信息。
====

* 当 Smrnmi 扩展未实现，或者 Smrnmi 扩展实现且 `mnstatus.NMIE` 为 0 时，hart 进入关键错误状态，不更新任何架构状态，包括 `pc`。此状态涉及停止执行，禁用所有中断（包括 NMI），并向平台断言 `critical-error` 信号。

[NOTE]
====
当 hart 断言 `critical-error` 信号时，平台执行的操作是平台特定的。可能的行动范围包括重新启动受影响的 hart 或重新启动整个平台等。
====

`MRET` 和 `SRET` 指令在 M 模式下执行时，将 `MDT` 位设置为 0。如果新特权模式是 U、VS 或 VU，则 `sstatus.SDT` 也设置为 0。此外，如果是 VU，则 `vsstatus.SDT` 也设置为 0。

`MNRET` 指令由 Smrnmi 扩展提供，如果新特权模式不是 M，则将 `MDT` 位设置为 0。如果是 U、VS 或 VU，则 `sstatus.SDT` 也设置为 0。此外，如果是 VU，则 `vsstatus.SDT` 也设置为 0。

[[xlen-control]]
===== `mstatus` 寄存器中的基本 ISA 控制

对于 RV64 hart，SXL 和 UXL 字段是 *WARL* 字段，分别控制 S 模式和 U 模式的 XLEN 值。这些字段的编码与 `misa` 的 MXL 字段相同，如 <<misabase>> 所示。S 模式和 U 模式下的有效 XLEN 分别称为 _SXLEN_ 和 _UXLEN_。

当 MXLEN=32 时，SXL 和 UXL 字段不存在，SXLEN=32 和 UXLEN=32。

当 MXLEN=64 时，如果不支持 S 模式，则 SXL 为只读零。否则，它是一个 *WARL* 字段，编码 SXLEN 的当前值。特别是，实现可以使 SXL 成为一个只读字段，其值始终确保 SXLEN=MXLEN。

当 MXLEN=64 时，如果不支持 U 模式，则 UXL 为只读零。否则，它是一个 *WARL* 字段，编码 UXLEN 的当前值。特别是，实现可以使 UXL 成为一个只读字段，其值始终确保 UXLEN=MXLEN 或 UXLEN=SXLEN。

如果实现了 S 模式，则 UXL 字段可能采用的合法值集不包括那些会导致 UXLEN 大于 SXLEN 的值。

无论何时，任何模式下的 XLEN 设置为小于最宽支持 XLEN 的值时，所有操作都必须忽略高于配置 XLEN 的源操作数寄存器位，并且必须符号扩展结果以填充目标寄存器中整个最宽支持 XLEN。同样，高于 XLEN 的 `pc` 位被忽略，并且当写入 `pc` 时，它会符号扩展以填充最宽支持 XLEN。

[NOTE]
====
我们要求操作始终用定义的值填充整个底层硬件寄存器，以避免实现定义的行为。

为了降低硬件复杂性，架构不施加任何检查，要求较低特权模式的 XLEN 设置小于或等于下一个较高特权模式。实际上，此类设置几乎总是软件错误，但即使在这种情况下，机器操作也是明确定义的。
====

一些 HINT 指令编码为整数计算指令，它们用其当前值覆盖其目标寄存器，例如 `c.addi x8, 0`。
当此类 HINT 在 XLEN < MXLEN 且目标寄存器的 MXLEN..XLEN 位不全等于位 XLEN-1 时执行时，目标寄存器的 MXLEN..XLEN 位是保持不变还是被 XLEN-1 位的副本覆盖是实现定义的。

注意：此定义允许实现省略某些 HINT 的寄存器回写，同时允许它们以与其他整数计算指令相同的方式执行其他 HINT。
实现选择仅对 XLEN 设置大于当前 XLEN 的特权模式可见；对当前特权模式不可见。

===== `mstatus` 寄存器中的内存特权

MPRV（修改特权）位修改 _有效特权模式_，即加载和存储执行的特权级别。当 MPRV=0 时，加载和存储行为正常，使用当前特权模式的转换和保护机制。当 MPRV=1 时，加载和存储内存地址被转换和保护，并应用字节序，就像当前特权模式设置为 MPP 一样。指令地址转换和保护不受 MPRV 设置的影响。如果不支持 U 模式，MPRV 为只读 0。

更改特权模式为低于 M 模式的 MRET 或 SRET 指令也会设置 MPRV=0。

MXR（使可执行可读）位修改加载访问虚拟内存的特权。当 MXR=0 时，只有标记为可读（<<sv32pte>> 中 R=1）的页面加载才会成功。当 MXR=1 时，标记为可读或可执行（R=1 或 X=1）的页面加载都会成功。当未启用基于页的虚拟内存时，MXR 无效。如果不支持 S 模式，MXR 为只读 0。

[NOTE]
====
MPRV 和 MXR 机制旨在提高 M 模式例程的效率，这些例程模拟缺失的硬件功能，例如未对齐的加载和存储。MPRV 消除了在软件中执行地址转换的需要。MXR 允许从标记为只执行的页面加载指令字。

当前特权模式和 MPP 指定的特权模式可能具有不同的 XLEN 设置。当 MPRV=1 时，加载和存储内存地址被视为当前 XLEN 设置为 MPP 的 XLEN，遵循 <<xlen-control>> 中的规则。
====
SUM（允许 Supervisor 用户内存访问）位修改 S 模式加载和存储访问虚拟内存的特权。当 SUM=0 时，S 模式内存访问 U 模式可访问的页面（<<sv32pte>> 中 U=1）将导致故障。当 SUM=1 时，允许这些访问。当未启用基于页的虚拟内存时，SUM 无效。请注意，虽然 SUM 在非 S 模式执行时通常被忽略，但当 MPRV=1 且 MPP=S 时，它 _是_ 有效的。如果不支持 S 模式或 `satp`.MODE 为只读 0，则 SUM 为只读 0。

MXR 和 SUM 机制仅影响页表条目中编码的权限的解释。特别是，它们对是否因 PMA 或 PMP 引发访问故障异常没有影响。

===== `mstatus` 和 `mstatush` 寄存器中的字节序控制

`mstatus` 和 `mstatush` 中的 MBE、SBE 和 UBE 位是 *WARL* 字段，控制除指令获取之外的内存访问的字节序。指令获取始终是小端序。

MBE 控制从 M 模式进行的非指令获取内存访问（假设 `mstatus`.MPRV=0）是小端序 (MBE=0) 还是大端序 (MBE=1)。

如果不支持 S 模式，SBE 为只读 0。否则，SBE 控制从 S 模式进行的显式加载和存储内存访问是小端序 (SBE=0) 还是大端序 (SBE=1)。

如果不支持 U 模式，UBE 为只读 0。否则，UBE 控制从 U 模式进行的显式加载和存储内存访问是小端序 (UBE=0) 还是大端序 (UBE=1)。

对于对 supervisor 级内存管理数据结构（例如页表）的 _隐式_ 访问，字节序始终由 SBE 控制。由于更改 SBE 会改变实现对这些数据结构的解释，如果任何此类数据结构在更改 SBE 后仍在使用，M 模式软件必须在更改 SBE 后执行一个 `SFENCE.VMA` 指令，其中 _rs1_=`x0` 且 _rs2_=`x0`。

[NOTE]
====
只有在特殊情况下，给定内存管理数据结构才会被解释为小端和大端。实际上，SBE 只会在世界切换时在运行时更改，在这种情况下，旧的和新的内存管理数据结构都不会以不同的字节序重新解释。在这种情况下，除了世界切换通常需要之外，不需要额外的 `SFENCE.VMA`。

---

卷 I 将 hart 的地址空间定义为连续地址处 2^XLEN^ 字节的循环序列。地址和字节位置之间的对应关系是固定的，不受任何字节序模式的影响。相反，适用的字节序模式决定了内存字节和多字节数量（半字、字等）之间的映射顺序。

---

标准 RISC-V ABI 预计将是纯小端或纯大端，不兼容混合字节序。
尽管如此，字节序控制的定义允许例如一个字节序的操作系统执行相反字节序的用户模式程序。还考虑了非标准用法，即软件根据需要翻转内存访问的字节序。

***

RISC-V 指令统一为小端，以将指令编码与当前字节序设置解耦，从而有利于硬件和软件。否则，例如，RISC-V 汇编器或反汇编器将始终需要知道预期的活动字节序，尽管字节序模式可能在执行期间动态更改。相比之下，通过为指令提供固定字节序，有时精心编写的软件即使在二进制形式下也可以是字节序无关的，就像位置无关代码一样。

选择指令仅为小端确实会带来一些后果，对于编码或解码机器指令的 RISC-V 软件而言。在大端模式下，此类软件必须考虑显式加载和存储的字节序与指令的字节序相反的事实，例如在加载后和存储前交换字节顺序。
====

[[virt-control]]
===== `mstatus` 寄存器中的虚拟化支持

TVM（陷阱虚拟内存）位是一个 *WARL* 字段，支持拦截 supervisor 虚拟内存管理操作。当 TVM=1 时，在 S 模式下执行时尝试读取或写入 `satp` CSR 或执行 `SFENCE.VMA` 或 `SINVAL.VMA` 指令将引发非法指令异常。当 TVM=0 时，这些操作在 S 模式下允许。当不支持 S 模式时，TVM 为只读 0。

[NOTE]
====
TVM 机制通过允许客户操作系统在 S 模式下执行而不是在 U 模式下进行经典虚拟化来提高虚拟化效率。这种方法消除了捕获大多数 S 模式 CSR 访问的需要。

捕获 `satp` 访问以及 `SFENCE.VMA` 和 `SINVAL.VMA` 指令提供了延迟填充影子页表所需的钩子。
====

TW（超时等待）位是一个 *WARL* 字段，支持拦截 WFI 指令（参见 <<wfi>>）。当 TW=0 时，WFI 指令可以在较低特权模式下执行，除非因其他原因被阻止。当 TW=1 时，如果在任何较低特权模式下执行 WFI，并且它未在实现定义的有界时间限制内完成，则 WFI 指令会导致非法指令异常。当 TW=1 时，即使在执行指令时存在全局禁用的中断，实现也可以使 WFI 始终在较低特权模式下引发非法指令异常。当没有低于 M 的特权模式时，TW 为只读 0。

[NOTE]
====
捕获 WFI 指令可以触发世界切换到另一个客户操作系统，而不是浪费地在当前客户机中空闲。
====

如果实现了 S 模式，则在 U 模式下执行 WFI 会导致非法指令异常，除非它在实现定义的有界时间限制内完成。本规范的未来修订版可能会添加一个功能，允许 S 模式选择性地允许在 U 模式下执行 WFI。此功能仅在 TW=0 时激活。

TSR（陷阱 SRET）位是一个 *WARL* 字段，支持拦截 supervisor 异常返回指令 SRET。当 TSR=1 时，在 S 模式下执行时尝试执行 SRET 将引发非法指令异常。当 TSR=0 时，此操作在 S 模式下允许。当不支持 S 模式时，TSR 为只读 0。

[NOTE]
====
捕获 SRET 对于在未提供管理程序扩展的实现上模拟管理程序扩展（参见 <<hypervisor>>）是必要的。
====

===== `mstatus` 寄存器中的扩展上下文状态

支持实质性扩展是 RISC-V 的主要目标之一，因此我们定义了一个标准接口，允许未更改的特权模式代码（特别是 supervisor 级操作系统）支持任意用户模式状态扩展。

[NOTE]
====
迄今为止，V 扩展是唯一一个定义了浮点 CSR 和数据寄存器之外的附加状态的标准扩展。
====

FS[1:0] 和 VS[1:0] *WARL* 字段以及 XS[1:0] 只读字段用于通过设置和跟踪浮点单元和任何其他用户模式扩展的当前状态来降低上下文保存和恢复的成本。FS 字段编码浮点单元状态的状态，包括浮点寄存器 `f0`–`f31` 和 CSR `fcsr`、`frm` 和 `fflags`。VS 字段编码向量扩展状态的状态，包括向量寄存器 `v0`–`v31` 和 CSR `vcsr`、`vxrm`、`vxsat`、`vstart`、`vl`、`vtype` 和 `vlenb`。XS 字段编码附加用户模式扩展和相关状态的状态。上下文切换例程可以检查这些字段，以快速确定是否需要保存或恢复状态。如果需要保存或恢复，通常需要额外的指令和 CSR 来实现和优化该过程。

[NOTE]
====
设计预期大多数上下文切换不需要在浮点单元或其他扩展中保存/恢复状态，因此通过 SD 位提供了快速检查。
====

FS、VS 和 XS 字段使用相同的状态编码，如 <<fsxsencoding>> 所示，有四种可能的状态值：关闭、初始、干净和脏。

如果实现了 F 扩展，则 FS 字段不得为只读零。

如果未实现 F 扩展和 S 模式，则 FS 为只读零。如果实现了 S 模式但未实现 F 扩展，则 FS 可以选择为只读零。

[NOTE]
====
允许具有 S 模式但没有 F 扩展的实现，但不要求，使 FS 字段为只读零。一些此类实现将选择 _不_ 使 FS 字段为只读零，以便通过 M 模式的不可见陷阱来模拟 S 模式和 U 模式的 F 扩展。
====

如果实现了 `v` 寄存器，则 VS 字段不得为只读零。

如果未实现 `v` 寄存器和 S 模式，则 VS 为只读零。如果实现了 S 模式但未实现 `v` 寄存器，则 VS 可以选择为只读零。

在没有需要新状态的附加用户扩展的 hart 中，XS 字段为只读零。每个具有状态的附加扩展都提供一个 CSR 字段，该字段编码与 XS 状态等效的状态。XS 字段表示所有扩展状态的摘要，如 <<fsxsencoding>> 所示。

[NOTE]
====
XS 字段有效地报告了所有用户扩展状态字段的最大状态值，尽管单个扩展可以使用与 XS 不同的编码。
====

SD 位是只读位，当 FS、VS 或 XS 字段指示存在需要将扩展用户上下文保存到内存的脏状态时，该位被设置（即 `SD=(FS==0b11 OR XS==0b11 OR VS==0b11)`）。这允许特权代码快速确定何时除了整数寄存器集和 `pc` 之外不需要额外的上下文保存。

当扩展的状态设置为关闭时，任何尝试读取或写入相应状态的指令都将导致非法指令异常。当状态为初始时，相应状态应具有初始常量值。当状态为干净时，相应状态可能与初始值不同，但与上下文交换时存储的最后一个值匹配。当状态为脏时，相应状态可能自上次上下文保存以来已被修改。

在上下文保存期间，负责的特权代码只需在状态为脏时写入相应的状态，然后可以将扩展的状态重置为干净。在上下文恢复期间，只有当状态为干净时（恢复时永远不应为脏）才需要从内存加载上下文。如果状态为初始，则在上下文恢复时必须将上下文设置为初始常量值，以避免安全漏洞，但这可以在不访问内存的情况下完成。例如，浮点寄存器都可以初始化为立即数 0。

FS 和 XS 字段在保存上下文之前由特权代码读取。FS 字段在恢复用户上下文时由特权代码直接设置，而 XS 字段通过写入单个扩展的状态寄存器间接设置。状态字段也将在指令执行期间更新，无论特权模式如何。

用户模式 ISA 的扩展通常包括附加的用户模式状态，并且此状态可能比基本整数寄存器大得多。扩展可能仅用于某些应用程序，或者可能仅在单个应用程序的短时间内需要。为了提高性能，用户模式扩展可以定义附加指令，以允许用户模式软件将单元返回到初始状态，甚至关闭单元。

例如，协处理器可能需要在使用前进行配置，并在使用后“取消配置”。未配置状态将表示为上下文保存的初始状态。如果同一应用程序在取消配置和下次配置之间保持运行（这将状态设置为脏），则无需在取消配置指令处实际重新初始化状态，因为所有状态都对用户进程是本地的，即初始状态可能只导致协处理器状态在上下文恢复时初始化为常量值，而不是在每次取消配置时。

执行用户模式指令以禁用单元并将其置于关闭状态将导致非法指令异常，如果任何后续指令在重新打开单元之前尝试使用该单元。打开单元的用户模式指令还必须确保单元的状态已正确初始化，因为该单元可能在此期间已被其他上下文使用。

更改 FS 的设置对浮点寄存器状态的内容没有影响。特别是，设置 FS=关闭不会破坏状态，设置 FS=初始也不会清除内容。同样，VS 的设置对向量寄存器状态的内容没有影响。然而，其他扩展可能在设置为关闭时不会保留状态。

实现可以选择不精确地跟踪浮点寄存器状态的脏性，即使未修改也报告状态为脏。在某些实现上，一些不改变浮点状态的指令可能导致状态从初始或干净转换为脏。在其他实现上，可能根本不跟踪脏性，在这种情况下，有效的 FS 状态是关闭和脏，并且尝试将 FS 设置为初始或干净会导致其设置为脏。

[NOTE]
====
FS 的此定义不禁止由于错误推测而将 FS 设置为脏。某些平台可能会选择禁止推测性写入 FS 以关闭潜在的侧信道。
====

如果指令显式或隐式写入浮点寄存器或 `fcsr` 但不改变其内容，并且 FS=初始或 FS=干净，则 FS 是否转换为脏是实现定义的。

实现可以选择以类似的不精确方式跟踪向量寄存器状态的脏性，包括当软件尝试将 VS 设置为初始或 VS=干净时，可能将 VS 设置为脏。当 VS=初始或 VS=干净时，写入向量寄存器或向量 CSR 但不改变其内容的指令是否导致 VS 转换为脏是实现定义的。

标准特权指令用于初始化、保存和恢复扩展状态，通过将状态视为不透明对象，使特权代码免受附加扩展状态的细节影响。

[NOTE]
====
许多协处理器扩展仅在有限的上下文中使用，允许软件在完成后安全地取消配置甚至禁用单元。这减少了大型有状态协处理器的上下文切换开销。

我们将浮点状态与其他扩展状态分开，因为当存在浮点单元时，浮点寄存器是标准调用约定的一部分，因此用户模式软件无法知道何时可以安全地禁用浮点单元。
====

XS 字段提供了所有附加扩展状态的摘要，但可以在扩展中维护额外的微架构位，以进一步减少上下文保存和恢复开销。

SD 位是只读的，当 FS、VS 或 XS 位编码脏状态时（即 `SD=(FS==0b11 OR XS==0b11 OR VS==0b11)`），该位被设置。这允许特权代码快速确定何时除了整数寄存器集和 `pc` 之外不需要额外的上下文保存。

浮点单元状态始终使用标准指令（F、D 和/或 Q）进行初始化、保存和恢复，并且特权代码必须了解 FLEN 以确定为每个 `f` 寄存器保留的适当空间。

机器和 Supervisor 模式共享 FS、VS 和 XS 位的单个副本。Supervisor 级软件通常直接使用 FS、VS 和 XS 位来记录相对于 Supervisor 级保存上下文的状态。机器级软件在保存和恢复其相应版本的上下文中的扩展状态时必须更加保守。

[NOTE]
====
在任何合理的使用情况下，用户和 supervisor 级别之间的上下文切换次数应远远超过到其他特权级别的上下文切换次数。请注意，协处理器不应要求保存和恢复其上下文以服务异步中断，除非中断导致用户级上下文交换。
====

* 1 - `LP_EXPECTED` - 预期有着陆垫指令。

`mtvec` 寄存器是一个 MXLEN 位 *WARL* 读/写寄存器，它保存陷阱向量配置，由向量基地址 (BASE) 和向量模式 (MODE) 组成。

`mtvec` 寄存器必须始终实现，但可以包含只读值。如果 `mtvec` 可写，则寄存器可能包含的值集可能因实现而异。BASE 字段中的值必须始终对齐到 4 字节边界，并且 MODE 设置可能对 BASE 字段中的值施加额外的对齐约束。

==== 机器陷阱委托 (`medeleg` 和 `mideleg`) 寄存器

默认情况下，任何特权级别的所有陷阱都在机器模式下处理，尽管机器模式处理程序可以使用 MRET 指令（<<otherpriv>>）将陷阱重定向回适当的级别。为了提高性能，实现可以提供 `medeleg` 和 `mideleg` 中的单个读/写位，以指示某些异常和中断应直接由较低特权级别处理。机器异常委托寄存器 (`medeleg`) 是一个 64 位读/写寄存器。
机器中断委托 (`mideleg`) 寄存器是一个 MXLEN 位读/写寄存器。

在具有 S 模式的 hart 中，`medeleg` 和 `mideleg` 寄存器必须存在，并且在 `medeleg` 或 `mideleg` 中设置一个位将委托相应的陷阱（当在 S 模式或 U 模式下发生时）到 S 模式陷阱处理程序。在没有 S 模式的 hart 中，`medeleg` 和 `mideleg` 寄存器不应存在。

[NOTE]
====
在 1.9.1 及更早版本中，这些寄存器存在，但在 M 模式下（或没有 N hart 的 M/U）硬连线为零。没有理由要求它们在这些情况下返回零，因为 `misa` 寄存器指示它们是否存在。
====

当陷阱委托给 S 模式时，`scause` 寄存器写入陷阱原因；`sepc` 寄存器写入发生陷阱的指令的虚拟地址；`stval` 寄存器写入异常特定数据；`mstatus` 的 SPP 字段写入陷阱时活动的特权模式；`mstatus` 的 SPIE 字段写入陷阱时 SIE 字段的值；`mstatus` 的 SIE 字段清除。`mcause`、`mepc` 和 `mtval` 寄存器以及 `mstatus` 的 MPP 和 MPIE 字段不写入。

实现可以选择子集可委托的陷阱，通过将 1 写入每个位位置，然后读回 `medeleg` 或 `mideleg` 的值来查看哪些位位置为 1，从而找到支持的可委托位。

实现不得将 `medeleg` 的任何位设置为只读 1，即任何可委托的同步陷阱都必须支持不被委托。同样，实现不得将 `mideleg` 中对应于机器级中断的任何位固定为只读 1（但可以对较低级别中断这样做）。

[NOTE]
====
1.11 及更早版本禁止 `mideleg` 的任何位为只读 1。平台标准可以随时添加此类限制。
====

陷阱永远不会从特权更高的模式转换为特权更低的模式。例如，如果 M 模式已将非法指令异常委托给 S 模式，并且 M 模式软件随后执行非法指令，则陷阱在 M 模式下发生，而不是委托给 S 模式。相比之下，陷阱可以水平发生。使用相同的示例，如果 M 模式已将非法指令异常委托给 S 模式，并且 S 模式软件随后执行非法指令，则陷阱在 S 模式下发生。

委托中断导致中断在委托者特权级别被屏蔽。例如，如果通过设置 `mideleg`[5] 将 supervisor 定时器中断 (STI) 委托给 S 模式，则在 M 模式下执行时将不会发生 STI。相比之下，如果 `mideleg`[5] 清除，则 STI 可以在任何模式下发生，并且无论当前模式如何，都将控制权转移到 M 模式。

.机器异常委托 (`medeleg`) 寄存器。
include::images/bytefield/medeleg.edn[]

`medeleg` 为 <<mcauses>> 中显示的每个同步异常分配了一个位位置，位位置的索引等于 `mcause` 寄存器中返回的值（即，设置位 8 允许用户模式环境调用委托给较低特权陷阱处理程序）。

当 XLEN=32 时，`medelegh` 是一个 32 位读/写寄存器，它与 `medeleg` 的 63:32 位别名。
当 XLEN=64 时，`medelegh` 寄存器不存在。

include::images/bytefield/mideleg.edn[]

`mideleg` 保存单个中断的陷阱委托位，位的布局与 `mip` 寄存器中的布局匹配（即，STIP 中断委托控制位于位 5）。

对于在较低特权模式下不会发生的异常，相应的 `medeleg` 位应为只读零。特别是，`medeleg`[11] 为只读零。

`medeleg`[16] 为只读零，因为双重陷阱不可委托。

==== 机器中断 (`mip` 和 `mie`) 寄存器

`mip` 寄存器是一个 MXLEN 位读/写寄存器，包含待处理中断的信息，而 `mie` 是相应的 MXLEN 位读/写寄存器，包含中断使能位。
中断原因号 _i_（如 CSR `mcause`，<<mcause>> 中报告）对应于 `mip` 和 `mie` 中的位 _i_。位 15:0 仅分配给标准中断原因，而位 16 及以上指定用于平台使用。

注意：指定用于平台的中断可以根据平台的判断指定用于自定义用途。

.机器中断待处理 (`mip`) 寄存器。
include::images/bytefield/mideleg.edn[]

.机器中断使能 (`mie`) 寄存器
include::images/bytefield/mideleg.edn[]

当中断 _i_ 满足以下所有条件时，它将陷阱到 M 模式（导致特权模式更改为 M 模式）：(a) 当前特权模式是 M 且 `mstatus` 寄存器中的 MIE 位已设置，或者当前特权模式的特权低于 M 模式；(b) `mip` 和 `mie` 中位 _i_ 都已设置；(c) 如果寄存器 `mideleg` 存在，则 `mideleg` 中位 _i_ 未设置。

这些中断陷阱发生的条件必须在中断变为或停止待处理在 `mip` 中时，以及在执行 __x__RET 指令或显式写入这些中断陷阱条件明确依赖的 CSR（包括 `mip`、`mie`、`mstatus` 和 `mideleg`）之后立即评估。

M 模式的中断优先于任何较低特权模式的中断。

`mip` 寄存器中的每个单独位可以是可写或只读。当 `mip` 中位 _i_ 可写时，可以通过将此位写入 0 来清除待处理中断 _i_。如果中断 _i_ 可以变为待处理，但 `mip` 中位 _i_ 是只读的，则实现必须提供其他机制来清除待处理中断。

如果相应的中断可以变为待处理，则 `mie` 中的位必须是可写的。`mie` 中不可写的位必须是只读零。

[NOTE]
====
机器级中断寄存器处理少数根中断源，这些中断源为了简单起见被分配了固定的服务优先级，而单独的外部中断控制器可以对更大范围的中断实现更复杂的优先级方案，然后将这些中断多路复用到机器级中断源中。

---

不可屏蔽中断不会通过 `mip` 寄存器可见，因为当执行 NMI 陷阱处理程序时，其存在是隐式已知的。
====

`mip`.MEIP 和 `mie`.MEIE 位是机器级外部中断的中断待处理和中断使能位。MEIP 在 `mip` 中是只读的，由平台特定的中断控制器设置和清除。

`mip`.MTIP 和 `mie`.MTIE 位是机器定时器中断的中断待处理和中断使能位。MTIP 在 `mip` 寄存器中是只读的，通过写入内存映射的机器模式定时器比较寄存器来清除。

`mip`.MSIP 和 `mie`.MSIE 位是机器级软件中断的中断待处理和中断使能位。MSIP 在 `mip` 中是只读的，通过访问内存映射的控制寄存器写入，远程 hart 使用这些寄存器提供机器级处理器间中断。hart 可以使用相同的内存映射控制寄存器写入自己的 MSIP 位。如果系统只有一个 hart，或者如果平台标准支持通过外部中断 (MEI) 传递机器级处理器间中断，则 `mip`.MSIP 和 `mie`.MSIE 都可以是只读零。

如果未实现 supervisor 模式，则 `mip` 的 SEIP、STIP 和 SSIP 位以及 `mie` 的 SEIE、STIE 和 SSIE 位为只读零。

如果实现了 supervisor 模式，则 `mip`.SEIP 和 `mie`.SEIE 位是 supervisor 级外部中断的中断待处理和中断使能位。SEIP 在 `mip` 中是可写的，M 模式软件可以写入它以指示 S 模式有外部中断待处理。此外，平台级中断控制器可以生成 supervisor 级外部中断。supervisor 级外部中断根据软件可写 SEIP 位和来自外部中断控制器的信号的逻辑或而变为待处理。当使用 CSR 指令读取 `mip` 时，返回到 `rd` 目标寄存器中的 SEIP 位的值是软件可写位和来自中断控制器的中断信号的逻辑或，但来自中断控制器的信号不用于计算写入 SEIP 的值。只有软件可写 SEIP 位参与 CSRRS 或 CSRRC 指令的读-改-写序列。

[NOTE]
====
例如，如果我们将软件可写 SEIP 位命名为 `B`，将来自外部中断控制器的信号命名为 `E`，那么如果执行 `csrrs t0, mip, t1`，则 `t0[9]` 写入 `B || E`，然后 `B` 写入 `B || t1[9]`。如果执行 `csrrw t0, mip, t1`，则 `t0[9]` 写入 `B || E`，并且 `B` 简单地写入 `t1[9]`。在这两种情况下，`B` 都不依赖于 `E`。

SEIP 字段的行为旨在允许更高特权层干净地模拟外部中断，而不会丢失任何真正的外部中断。因此，CSR 指令的行为与常规 CSR 访问略有不同。
====

如果实现了 supervisor 模式，则 `mip`.STIP 和 `mie`.STIE 位是 supervisor 级定时器中断的中断待处理和中断使能位。STIP 在 `mip` 中是可写的，M 模式软件可以写入它以将定时器中断传递给 S 模式。

如果实现了 supervisor 模式，则 `mip`.SSIP 和 `mie`.SSIE 位是 supervisor 级软件中断的中断待处理和中断使能位。SSIP 在 `mip` 中是可写的，也可以由平台特定的中断控制器设置为 1。

如果实现了 Sscofpmf 扩展，则 `mip`.LCOFIP 和 `mie`.LCOFIE 位是本地计数器溢出中断的中断待处理和中断使能位。
LCOFIP 在 `mip` 中是读写的，反映了由于任何 `mhpmevent__n__`.OF 位设置而导致的本地计数器溢出中断请求的发生。
如果未实现 Sscofpmf 扩展，则 `mip`.LCOFIP 和 `mie`.LCOFIE 为只读零。

同时针对 M 模式的多个中断按以下递减优先级顺序处理：MEI、MSI、MTI、SEI、SSI、STI、LCOFI。

[NOTE]
====
机器级中断固定优先级排序规则是根据以下理由制定的。

为了支持抢占，较高特权模式的中断必须在较低特权模式的中断之前得到服务。

位 16 及以上的平台特定机器级中断源具有平台特定的优先级，但通常选择具有最高服务优先级以支持非常快速的本地向量中断。

外部中断在内部（定时器/软件）中断之前处理，因为外部中断通常由可能需要低中断服务时间的设备生成。

软件中断在内部定时器中断之前处理，因为内部定时器中断通常用于时间片，其中时间精度不那么重要，而软件中断用于处理器间消息传递。当需要高精度计时时，可以避免软件中断，或者高精度定时器中断可以通过不同的中断路径路由。软件中断位于 `mip` 的最低四位，因为这些位通常由软件写入，并且此位置允许使用带有五位立即数的单个 CSR 指令。
====

`mip` 和 `mie` 寄存器的受限视图在 supervisor 级别显示为 `sip` 和 `sie` 寄存器。如果通过设置 `mideleg` 寄存器中的位将中断委托给 S 模式，则该中断在 `sip` 寄存器中可见，并且可以使用 `sie` 寄存器进行屏蔽。
否则，`sip` 和 `sie` 中相应的位为只读零。

==== 硬件性能监视器

M 模式包括一个基本的硬件性能监视功能。`mcycle` CSR 计数 hart 运行的处理器核心执行的时钟周期数。`minstret` CSR 计数 hart 已执行的指令数。`mcycle` 和 `minstret` 寄存器在所有 RV32 和 RV64 hart 上都具有 64 位精度。

计数器寄存器在 hart 复位后具有任意值，并且可以写入给定值。任何 CSR 写入在写入指令完成之后生效。`mcycle` CSR 可以在同一核心上的 hart 之间共享，在这种情况下，对 `mcycle` 的写入将对这些 hart 可见。平台应提供一种机制来指示哪些 hart 共享 `mcycle` CSR。

硬件性能监视器包括 29 个额外的 64 位事件计数器，`mhpmcounter3`-`mhpmcounter31`。事件选择器 CSR `mhpmevent3`-`mhpmevent31` 是 64 位 *WARL* 寄存器，控制哪个事件导致相应的计数器递增。这些事件的含义由平台定义，但事件 0 定义为“无事件”。所有计数器都应实现，但合法的实现是使计数器及其相应的事件选择器为只读 0。

.硬件性能监视器计数器。
include::images/bytefield/hpmevents.edn[]

`mhpmcounters` 是 *WARL* 寄存器，在 RV32 和 RV64 上支持高达 64 位的精度。

当 XLEN=32 时，读取 `mcycle`、`minstret`、`mhpmcounter__n__` 和 `mhpmevent__n__` CSR 返回相应寄存器的 31-0 位，写入仅更改 31-0 位；读取 `mcycleh`、`minstreth`、`mhpmcounter__n__h` 和 `mhpmevent__n__h` CSR 返回相应寄存器的 63-32 位，写入仅更改 63-32 位。
`mhpmevent__n__h` CSR 仅在实现 Sscofpmf 扩展时提供。

[[mcounteren]]
==== 机器计数器使能 (`mcounteren`) 寄存器

计数器使能 `mcounteren` 寄存器是一个 32 位寄存器，控制硬件性能监视计数器对下一个较低特权模式的可用性。

.计数器使能 (`mcounteren`) 寄存器。
include::images/bytefield/counteren.edn[]

此寄存器中的设置仅控制可访问性。读取或写入此寄存器的行为不影响底层计数器，即使不可访问，计数器也会继续递增。

当 `mcounteren` 寄存器中的 CY、TM、IR 或 HPM__n__ 位清除时，在 S 模式或 U 模式下执行时尝试读取 `cycle`、`time`、`instret` 或 `hpmcountern` 寄存器将导致非法指令异常。当这些位中的一个设置时，允许在下一个已实现的特权模式（如果已实现 S 模式，否则为 U 模式）中访问相应的寄存器。

[NOTE]
====
计数器使能位以最少的硬件支持两种常见用例。对于不需要高性能定时器和计数器的 hart，机器模式软件可以捕获访问并在软件中实现所有功能。对于需要高性能定时器和计数器但不需要混淆底层硬件计数器的 hart，计数器可以直接暴露给较低特权模式。
====

`cycle`、`instret` 和 `hpmcountern` CSR 分别是 `mcycle`、`minstret` 和 `mhpmcounter n` 的只读影子。`time` CSR 是内存映射 `mtime` 寄存器的只读影子。
类似地，当 XLEN=32 时，`cycleh`、`instreth` 和 `hpmcounternh` CSR 分别是 `mcycleh`、`minstreth` 和 `mhpmcounternh` 的只读影子。当 XLEN=32 时，`timeh` CSR 是内存映射 `mtime` 寄存器高 32 位的只读影子，而 `time` 仅影子 `mtime` 的低 32 位。

[NOTE]
====
实现可以将 `time` 和 `timeh` CSR 的读取转换为对内存映射 `mtime` 寄存器的加载，或者在 M 模式软件中为较低特权模式模拟此功能。
====

在具有 U 模式的 hart 中，`mcounteren` 必须实现，但所有字段都是 *WARL* 并且可以是只读零，表示当在较低特权模式下执行时，读取相应的计数器将导致非法指令异常。在没有 U 模式的 hart 中，`mcounteren` 寄存器不应存在。

==== 机器计数器禁用 (`mcountinhibit`) 寄存器

.计数器禁用 `mcountinhibit` 寄存器
include::images/bytefield/counterinh.edn[]

计数器禁用 `mcountinhibit` 寄存器是一个 32 位 *WARL* 寄存器，控制哪些硬件性能监视计数器递增。此寄存器中的设置仅控制计数器是否递增；它们的可访问性不受此寄存器设置的影响。

当 `mcountinhibit` 寄存器中的 CY、IR 或 HPM__n__ 位清除时，`mcycle`、`minstret` 或 `mhpmcountern` 寄存器照常递增。
当 CY、IR 或 HPM_n_ 位设置时，相应的计数器不递增。

`mcycle` CSR 可以在同一核心上的 hart 之间共享，在这种情况下，`mcountinhibit.CY` 字段也将在这些 hart 之间共享，因此对 `mcountinhibit.CY` 的写入将对这些 hart 可见。

如果未实现 `mcountinhibit` 寄存器，则实现的行为就像该寄存器设置为零一样。

[NOTE]
====
当不需要 `mcycle` 和 `minstret` 计数器时，有条件地禁用它们以减少能耗是可取的。提供单个 CSR 来禁用所有计数器也允许原子地采样计数器。

因为 `mtime` 计数器可以在多个核心之间共享，所以不能使用 `mcountinhibit` 机制禁用它。
====

==== 机器暂存 (`mscratch`) 寄存器

`mscratch` 寄存器是一个 MXLEN 位读/写寄存器，专用于机器模式。通常，它用于保存指向机器模式 hart 局部上下文空间的指针，并在进入 M 模式陷阱处理程序时与用户寄存器交换。

.机器模式暂存寄存器。
include::images/bytefield/mscratch.edn[]

[NOTE]
====
MIPS ISA 分配了两个用户寄存器 (`k0`/`k1`) 供操作系统使用。尽管 MIPS 方案提供了快速简单的实现，但它也减少了可用用户寄存器，并且不适用于更高级别的特权或嵌套陷阱。它还可能要求在返回用户级别之前清除两个寄存器，以避免潜在的安全漏洞并提供确定性调试行为。

RISC-V 用户 ISA 旨在支持许多可能的特权系统环境，因此我们不想在用户级 ISA 中感染任何与操作系统相关的功能。RISC-V CSR 交换指令可以快速保存/恢复值到 `mscratch` 寄存器。与 MIPS 设计不同，操作系统可以依赖在用户上下文运行时在 `mscratch` 寄存器中保存值。
====

==== 机器异常程序计数器 (`mepc`) 寄存器

`mepc` 是一个 MXLEN 位读/写寄存器，格式如 <<mepcreg>> 所示。`mepc` 的低位 (`mepc[0]`) 始终为零。在仅支持 IALIGN=32 的实现上，低两位 (`mepc[1:0]`) 始终为零。

如果实现允许 IALIGN 为 16 或 32（例如通过更改 CSR `misa`），则无论何时 IALIGN=32，`mepc[1]` 位在读取时都会被屏蔽，使其显示为 0。这种屏蔽也发生在 MRET 指令的隐式读取中。尽管被屏蔽，但当 IALIGN=32 时，`mepc[1]` 仍然可写。

`mepc` 是一个 *WARL* 寄存器，必须能够保存所有有效的虚拟地址。它不需要能够保存所有可能的无效地址。在写入 `mepc` 之前，实现可以将无效地址转换为 `mepc` 能够保存的其他无效地址。

[NOTE]
====
当未启用地址转换时，虚拟地址和物理地址相等。因此，`mepc` 必须能够表示的地址集包括可用作有效 `pc` 或有效地址的物理地址集。
====

当陷阱进入 M 模式时，`mepc` 写入被中断或遇到异常的指令的虚拟地址。否则，`mepc` 从不被实现写入，尽管它可以由软件显式写入。

==== 机器原因 (`mcause`) 寄存器

`mcause` 寄存器是一个 MXLEN 位读写寄存器，格式如 <<mcausereg>> 所示。当陷阱进入 M 模式时，`mcause` 写入一个代码，指示导致陷阱的事件。否则，`mcause` 从不被实现写入，尽管它可以由软件显式写入。

`mcause` 寄存器中的 Interrupt 位在陷阱由中断引起时设置。Exception Code 字段包含一个代码，标识上次异常或中断。<<mcauses>> 列出了可能的机器级异常代码。Exception Code 是一个 *WLRL* 字段，因此只保证保存支持的异常代码。

[[mcausereg]]
.机器原因 (`mcause`) 寄存器。
include::images/bytefield/mcausereg.edn[]

请注意，加载和加载-预留指令生成加载异常，而存储、存储-条件和 AMO 指令生成存储/AMO 异常。

[NOTE]
====
中断可以通过对 `mcause` 寄存器值的符号进行单个分支来与其它陷阱分离。左移可以移除中断位并缩放异常代码以索引到陷阱向量表中。

[NOTE]
====
软件检查异常是一种同步异常，当违反 ISA 扩展定义的检查和断言时触发，这些检查和断言旨在保护软件资产的完整性，包括例如控制流和内存访问约束。当引发此异常时，`__x__tval` 寄存器设置为 0 或由规定引发异常的扩展定义的有意义值。此异常的优先级相对于其他同步异常，取决于此异常的原因，并由规定引发异常的扩展定义。

硬件错误异常是一种同步异常，当指令显式或隐式访问损坏或不可纠正的数据时触发。在此上下文中，“数据”涵盖 RISC-V hart 中使用的所有类型信息。发生硬件错误异常时，`__x__epc` 寄存器设置为尝试访问损坏数据的指令的地址，而 `__x__tval` 寄存器设置为 0 或尝试访问损坏数据的指令获取、加载或存储的虚拟地址。硬件错误异常的优先级是实现定义的，但任何给定事件通常预计在发现硬件错误的总体优先级顺序中的点处被识别。
====

==== 机器陷阱值 (`mtval`) 寄存器

`mtval` 寄存器是一个 MXLEN 位读写寄存器，格式如 <<mtvalreg>> 所示。当陷阱进入 M 模式时，`mtval` 设置为零或写入异常特定信息，以帮助软件处理陷阱。否则，`mtval` 从不被实现写入，尽管它可以由软件显式写入。硬件平台将指定哪些异常必须有意义地设置 `mtval`，哪些可以无条件地将其设置为零，以及哪些可以根据导致异常的底层事件表现出任一行为。
如果硬件平台指定没有异常将 `mtval` 设置为非零值，则 `mtval` 为只读零。

当指令获取、加载或存储发生断点、地址未对齐、访问故障或页故障异常时，如果 `mtval` 写入非零值，则 `mtval` 将包含故障虚拟地址。

当启用基于页的虚拟内存时，`mtval` 写入故障虚拟地址，即使是物理内存访问故障异常。这种设计降低了大多数实现的路径成本，特别是那些具有硬件页表遍历器的实现。

[[mtvalreg]]
.机器陷阱值 (`mtval`) 寄存器。
include::images/bytefield/mtvalreg.edn[]


如果当错位的加载或存储导致访问故障或页故障异常时 `mtval` 写入非零值，则 `mtval` 将包含导致故障的访问部分的虚拟地址。

如果当指令访问故障或页故障异常发生在具有可变长度指令的 hart 上时 `mtval` 写入非零值，则 `mtval` 将包含导致故障的指令部分的虚拟地址，而 `mepc` 将指向指令的开始。

`mtval` 寄存器也可以选择用于在非法指令异常时返回故障指令位（`mepc` 指向内存中的故障指令）。如果当非法指令异常发生时 `mtval` 写入非零值，则 `mtval` 将包含以下最短的：

* 实际故障指令

* 故障指令的前 ILEN 位

* 故障指令的前 MXLEN 位

在非法指令异常时加载到 `mtval` 中的值是右对齐的，所有未使用的高位都清零。

[NOTE]
====
在 `mtval` 中捕获故障指令减少了指令仿真的开销，如果指令未对齐，可能避免几次部分指令加载，以及当使用加载将指令获取到数据寄存器中时可能的数据缓存未命中或缓慢的非缓存访问。如果另一个代理正在操作指令内存，如在动态翻译系统中可能发生的情况，还存在原子性问题。

要求是在触发陷阱之前将整个指令（或至少前 MXLEN 位）获取到 `mtval` 中。这不应该约束实现，通常在尝试解码指令之前会获取整个指令，并避免复杂化软件处理程序。

`mtval` 中的零值表示该功能不受支持，或获取了非法的零指令。可以使用从 `mepc` 指向的指令内存的加载来区分这两种情况（或者，可以询问系统配置信息以在运行时之前安装适当的陷阱处理）。
====

在由软件检查异常引起的陷阱中，`mtval` 寄存器保存异常的原因。定义了以下编码：

* 0 - 未提供信息。
* 2 - 着陆垫故障。由 Zicfilp 扩展定义（<<priv-forward>>）。
* 3 - 影子栈故障。由 Zicfiss 扩展定义（<<priv-backward>>）。

对于其他陷阱，`mtval` 设置为零，但未来标准可能重新定义其他陷阱的 `mtval` 设置。

如果 `mtval` 不是只读零，它是一个 *WARL* 寄存器，必须能够保存所有有效虚拟地址和零值。它不需要能够保存所有可能的无效地址。在写入 `mtval` 之前，实现可以将无效地址转换为 `mtval` 能够保存的其他无效地址。如果实现了返回故障指令位的功能，`mtval` 还必须能够保存所有小于 2^__N__^ 的值，其中 _N_ 是 MXLEN 和 ILEN 中的较小者。

==== 机器配置指针 (`mconfigptr`) 寄存器

`mconfigptr` 寄存器是一个 MXLEN 位只读 CSR，格式如 <<mconfigptrreg>> 所示，它保存配置数据结构的物理地址。软件可以遍历此数据结构以发现有关 hart、平台及其配置的信息。

[[mconfigptrreg]]

=== 机器保护和翻译

本节描述 RISC-V 机器模式中的内存保护和翻译设施。

==== 物理内存保护 (PMP)

PMP（物理内存保护）提供按地址范围的读、写和执行权限，以保护机器模式软件。PMP 检查适用于机器模式下的所有内存访问，当前实现的所有有效虚拟地址转换模式（包括裸模式）以及所有特权模式下的所有内存访问。

[NOTE]
====
PMP 是可选的。在没有 PMP 的机器上，物理内存地址只受平台内存映射的约束。
====

PMP 违反被报告为访问异常。在机器模式下，PMP 违反被报告为机器模式访问异常。在较低特权模式下（当前为 S 或 U），访问违反可能导致机器模式访问异常或较低特权模式的访问异常，这取决于实现选择。为了帮助调试，实现应该在可能的情况下将 PMP 违反报告给适当的特权模式。

PMP 状态通过机器模式 CSR 进行控制：最多 16 个 PMP 地址寄存器 `pmpaddr0`–`pmpaddr15`，以及最多 64 个 PMP 配置寄存器 `pmpcfg0`、`pmpcfg2`、...、`pmpcfg14`。在 RV32 中，每个 `pmpcfg_i_` 寄存器保存四个 PMP 条目的配置信息，因此 `pmpcfg0` 保存 `pmp0cfg`–`pmp3cfg` 的配置信息。

PMP 检查适用于有效特权模式为 S 或 U 的所有访问，包括 S 和 U 模式中的指令获取和数据访问，以及当 `mstatus` 中的 MPRV 位设置且 `mstatus` 中的 MPP 字段包含 S 或 U 时 M 模式中的数据访问。PMP 检查还适用于虚拟地址转换的页表访问，其有效特权模式为 S。

[NOTE]
====
这个实现还在开发中，完整的 PMP 功能描述将在未来版本中提供。目前的机器级保护机制为系统软件提供了基本的内存访问控制能力。
====
