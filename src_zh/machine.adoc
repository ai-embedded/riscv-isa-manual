[[machine]]
== 机器级 ISA，版本 1.13

本章描述了在机器模式（M-mode）下可用的机器级操作，M-mode 是 RISC-V hart 中的最高特权模式。M-mode 用于对硬件平台的低级访问，是复位时进入的第一个模式。M-mode 也可以用来实现那些直接在硬件中实现过于困难或昂贵的特性。RISC-V 机器级 ISA 包含一个公共核心，该核心根据支持的其他特权级别和硬件实现的其他细节进行扩展。

=== 机器级 CSR

除了本节描述的机器级 CSR 外，M-mode 代码还可以访问较低特权级别的所有 CSR。

[[misa]]
==== 机器 ISA (`misa`) 寄存器

`misa` CSR 是一个 *WARL* 读写寄存器，报告 hart 支持的 ISA。该寄存器在任何实现中都必须是可读的，但可以返回零值以表示 `misa` 寄存器未实现，这要求通过单独的非标准机制来确定 CPU 能力。

.机器 ISA 寄存器 (misa)
include::images/bytefield/misareg.edn[]

MXL（机器 XLEN）字段编码本机基础整数 ISA 宽度，如 <<misabase>> 所示。MXL 字段是只读的。如果 `misa` 非零，MXL 字段指示 M-mode 中的有效 XLEN，这是一个称为 _MXLEN_ 的常数。XLEN 永远不会大于 MXLEN，但在较低特权模式下 XLEN 可能小于 MXLEN。

[NOTE]
====
可以使用对返回的 `misa` 值符号的分支快速确定基础宽度，可能还需要左移一位和第二个符号分支。这些检查可以用汇编代码编写，而无需知道 hart 的寄存器宽度（MXLEN）。基础宽度由 __MXLEN=2^MXL+4^__ 给出。

如果 `misa` 为零，也可以找到基础宽度，方法是将立即数 2 放入寄存器，然后将寄存器左移 31 位。如果为零，hart 是 RV32，否则是 RV64。
====

扩展字段编码标准扩展的存在，字母表的每个字母用一个位表示（位 0 编码扩展 "A" 的存在，位 1 编码扩展 "B" 的存在，直到位 25 编码 "Z"）。对于 RV32I 和 RV64I 基础 ISA，"I" 位将被设置，对于 RV32E 和 RV64E，"E" 位将被设置。扩展字段是一个 *WARL* 字段，可以包含可写位，其中实现允许修改支持的 ISA。在复位时，扩展字段应包含支持扩展的最大集合，如果两者都可用，应选择 "I" 而不是 "E"。

当通过清除 `misa` 中的位禁用标准扩展时，扩展定义或修改的指令和 CSR 将恢复到它们定义的或保留的行为，就好像该扩展未实现一样。

[NOTE]
====
对于给定的 RISC-V 执行环境，RISC-V ISA 的指令、扩展或其他特性通常通过该环境中的可观察执行行为来判断是否已 _实现_。例如，当且仅当 RISC-V 非特权 ISA 为 F 定义的指令按规定执行时，才称 F 扩展为执行环境实现。

使用 _实现_ 的这个定义，通过清除 `misa` 中的位禁用扩展会导致该扩展在 M-mode 中被视为 _未实现_。例如，设置 `misa`.F=0 会导致 F 扩展在 M-mode 中未实现，因为 F 扩展的指令不会按照非特权 ISA 的要求执行，而可能引发非法指令异常。

严格基于可观察行为定义术语 _实现_ 可能与该词的其他常见理解相冲突。特别是，虽然常见用法可能允许 "已实现但已禁用" 的组合，但在本文档中这被认为是术语矛盾，因为 _禁用_ 意味着执行不会按照特性被认为 _已实现_ 所需的方式表现。同样，"已实现且已启用" 在这里是冗余的；"已实现" 就足够了。
====

如果有任何非标准扩展，"X" 位将被设置。

当 "B" 位为 1 时，实现支持 Zba、Zbb 和 Zbs 扩展提供的指令。当 "B" 位为 0 时，表示实现可能不支持 Zba、Zbb 或 Zbs 扩展中的一个或多个。

当 "M" 位为 1 时，实现支持 M 扩展定义的所有乘法和除法指令。当 "M" 位为 0 时，表示实现可能不支持这些指令。但是，如果支持 Zmmul 扩展，则无论 "M" 位的值如何，都支持它指定的乘法指令。

当 "S" 位为 1 时，实现支持管理员模式。当 "S" 位为 0 时，实现可能不支持管理员模式。

当 "U" 位为 1 时，实现支持用户模式。当 "U" 位为 0 时，实现可能不支持用户模式。

[NOTE]
====
`misa` CSR 向机器模式代码公开了 CPU 特性的基本目录。可以在机器模式下通过探测其他机器寄存器并检查系统中的其他 ROM 存储作为引导过程的一部分来获得更广泛的信息。

我们要求较低特权级别执行环境调用而不是读取 CPU 寄存器来确定每个特权级别的可用特性。这使虚拟化层能够改变在任何级别观察到的 ISA，并支持更丰富的命令接口，而不会给硬件设计带来负担。
====

"E" 位是只读的。除非 `misa` 全部为只读零，"E" 位总是读作 "I" 位的补码。如果执行环境同时支持 RV32E 和 RV32I，软件可以通过清除 "I" 位来选择 RV32E。

如果 ISA 特性 _x_ 依赖于 ISA 特性 _y_，则尝试启用特性 _x_ 但禁用特性 _y_ 会导致两个特性都被禁用。例如，设置 "F"=0 和 "D"=1 会导致 "F" 和 "D" 都被清除。类似地，设置 "U"=0 和 "S"=1 会导致 "U" 和 "S" 都被清除。

实现可能对两个或多个 `misa` 字段的集体设置施加额外约束，在这种情况下，它们集体作为单个 *WARL* 字段运行。尝试写入不支持的组合会导致这些位被设置为某个支持的组合。

写入 `misa` 可能会增加 IALIGN，例如通过禁用 "C" 扩展。如果写入 `misa` 的指令会增加 IALIGN，并且后续指令的地址不是 IALIGN 位对齐的，则对 `misa` 的写入被抑制，`misa` 保持不变。

当软件启用先前禁用的扩展时，与该扩展唯一关联的所有状态都是未指定的，除非该扩展另有规定。

注意：虽然 `misa` 中位 25--0 之一被设置为 1 意味着相应的特性已实现，但反之不一定成立：这些位之一被清除并不一定意味着相应的特性未实现。这源于这样一个事实：当特性未实现时，相应的操作码和 CSR 变为保留的，不一定是非法的。

==== 机器供应商 ID (`mvendorid`) 寄存器

`mvendorid` CSR 是一个 32 位只读寄存器，提供核心提供商的 JEDEC 制造商 ID。该寄存器在任何实现中都必须是可读的，但可以返回值 0 以表示该字段未实现或这是非商业实现。

.供应商 ID 寄存器 (`mvendorid`)
include::images/bytefield/mvendorid.edn[]

JEDEC 制造商 ID 通常编码为一系列单字节继续码 `0x7f`，由不等于 `0x7f` 的单字节 ID 终止，每个字节的最高有效位中有奇偶校验位。`mvendorid` 在 Bank 字段中编码单字节继续码的数量，在 Offset 字段中编码最后的字节，丢弃奇偶校验位。例如，JEDEC 制造商 ID `0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x7f 0x8a`（十二个继续码后跟 `0x8a`）在 `mvendorid` CSR 中将被编码为 `0x60a`。

[NOTE]
====
在 JEDEC 的说法中，银行号比继续码数量大一；因此，`mvendorid` Bank 字段编码的值比 JEDEC 银行号小一。

***
以前，供应商 ID 是由 RISC-V International 分配的数字，但这重复了 JEDEC 在维护制造商 ID 标准方面的工作。在撰写本文时，向 JEDEC 注册制造商 ID 的一次性费用为 500 美元。
====

==== 机器架构 ID (`marchid`) 寄存器

`marchid` CSR 是一个 MXLEN 位只读寄存器，编码 hart 的基础微架构。该寄存器在任何实现中都必须是可读的，但可以返回值 0 以表示该字段未实现。`mvendorid` 和 `marchid` 的组合应该唯一标识所实现的 hart 微架构类型。

.机器架构 ID (`marchid`) 寄存器
include::images/bytefield/marchid.edn[]

开源项目架构 ID 由 RISC-V International 全局分配，具有非零架构 ID 且最高有效位 (MSB) 为零。商业架构 ID 由每个商业供应商独立分配，但必须设置 MSB 并且不能在剩余的 MXLEN-1 位中包含零。

[NOTE]
====
目的是让架构 ID 代表与开发发生的项目相关的微架构，而不是特定的组织。开源设计的商业制造应该（并且可能被许可证要求）保留原始架构 ID。这将有助于减少碎片化和工具支持成本，并提供归属。开源架构 ID 由 RISC-V International 管理，应该只分配给已发布的、功能性的开源项目。商业架构 ID 可以由任何注册供应商独立管理，但要求具有与开源架构 ID 不相交的 ID（设置 MSB）以防止供应商希望同时使用闭源和开源微架构时的冲突。

以下实现字段中采用的约定可用于分离同一架构设计的分支，包括按组织分离。`misa` 寄存器也有助于区分设计的不同变体。
====

==== 机器实现 ID (`mimpid`) 寄存器

`mimpid` CSR 提供处理器实现版本的唯一编码。该寄存器在任何实现中都必须是可读的，但可以返回值 0 以表示该字段未实现。实现值应反映 RISC-V 处理器本身的设计，而不是任何周围系统。

.机器实现 ID (`mimpid`) 寄存器

==== Hart ID (`mhartid`) 寄存器

`mhartid` CSR 是一个 MXLEN 位只读寄存器，包含运行代码的硬件线程的整数 ID。该寄存器在任何实现中都必须是可读的。Hart ID 在多处理器系统中可能不一定连续编号，但至少一个 hart 必须具有 hart ID 零。Hart ID 在执行环境中必须是唯一的。

.Hart ID (`mhartid`) 寄存器
include::images/bytefield/mhartid.edn[]

[NOTE]
====
在某些情况下，我们必须确保恰好一个 hart 运行某些代码（例如，在复位时），因此要求一个 hart 具有已知的 hart ID 零。

为了提高效率，系统实现者应该旨在减少系统中使用的最大 hart ID 的大小。
====

[[privstack]]
===== `mstatus` 寄存器中的特权和全局中断使能栈

为 M-mode 和 S-mode 分别提供全局中断使能位 MIE 和 SIE。这些位主要用于保证在当前特权模式下相对于中断处理程序的原子性。

[NOTE]
====
全局 __x__IE 位位于 `mstatus` 的低位，允许用单个 CSR 指令原子地设置或清除它们。
====

当 hart 在特权模式 _x_ 中执行时，当 __x__IE=1 时中断全局启用，当 __x__IE=0 时全局禁用。对于较低特权模式的中断，__w__<__x__，无论较低特权模式的任何全局 __w__IE 位的设置如何，都总是全局禁用。对于较高特权模式的中断，__y__>__x__，无论较高特权模式的全局 __y__IE 位的设置如何，都总是全局启用。较高特权级别的代码可以使用单独的每中断使能位在将控制转让给较低特权模式之前禁用选定的较高特权模式中断。如果未实现管理员模式，则 SIE 和 SPIE 为只读 0。

[NOTE]
====
较高特权模式 _y_ 可以在将控制转让给较低特权模式之前禁用其所有中断，但这将是不寻常的，因为它将只留下同步陷阱、不可屏蔽中断或复位作为重新获得 hart 控制的手段。
====

为了支持嵌套陷阱，每个可以响应中断的特权模式 _x_ 都有一个两级的中断使能位和特权模式栈。__x__PIE 保存陷阱前活动的中断使能位的值，__x__PP 保存先前的特权模式。__x__PP 字段只能保存到 _x_ 的特权模式，因此 MPP 宽度为两位，SPP 宽度为一位。当从特权模式 _y_ 进入特权模式 _x_ 时发生陷阱，__x__PIE 设置为 __x__IE 的值；__x__IE 设置为 0；__x__PP 设置为 _y_。

[NOTE]
====
对于较低特权模式，任何陷阱（同步或异步）通常在较高特权模式下处理，进入时禁用中断。较高级别的陷阱处理程序将服务陷阱并使用堆栈信息返回，或者，如果不立即返回到中断的上下文，将在重新启用中断之前保存特权栈，因此每个栈只需要一个条目。
====

MRET 或 SRET 指令分别用于从 M-mode 或 S-mode 中的陷阱返回。当执行 __x__RET 指令时，假设 __x__PP 保存值 _y_，__x__IE 设置为 __x__PIE；特权模式更改为 _y_；__x__PIE 设置为 1；__x__PP 设置为最低特权支持模式（如果实现了 U-mode 则为 U，否则为 M）。如果 __y__&#8800;M，__x__RET 也设置 MPRV=0。

[NOTE]
====
在 __x__RET 时将 __x__PP 设置为最低特权支持模式有助于识别两级特权模式栈管理中的软件错误。
====

[NOTE]
====
陷阱处理程序必须设计为在处理阶段既不启用中断也不引起异常，在该阶段陷阱处理程序保存处理和从陷阱恢复所需的关键状态信息。在陷阱处理的这个关键阶段中的异常或中断可能导致可以覆盖这种关键状态的陷阱。这可能导致丢失从初始陷阱恢复所需的数据。此外，如果在处理陷阱所需的代码路径中发生异常，那么这种情况可能导致陷阱的无限循环。为防止这种情况，陷阱处理程序必须精心设计以识别和安全地管理其操作流程中的异常。
====

__x__PP 字段是 *WARL* 字段，只能保存特权模式 _x_ 和任何实现的低于 _x_ 的特权模式。如果未实现特权模式 _x_，则 __x__PP 必须为只读 0。

[NOTE]
====
M-mode 软件可以通过将该模式写入 MPP 然后读回来确定是否实现了特权模式。

如果机器只提供 U 和 M 模式，则只需要一个硬件存储位来表示 MPP 中的 00 或 11。
====

[[machine-double-trap]]
===== `mstatus` 寄存器中的双重陷阱控制

双重陷阱通常在陷阱处理操作的敏感阶段出现——当陷阱处理程序（负责管理这些事件的组件）处于不可重入状态时发生异常或中断。这种不可重入性通常发生在陷阱处理的早期阶段，其中陷阱处理程序尚未保存处理和从陷阱恢复所需的必要状态。在此阶段发生的陷阱可能导致关键状态信息的覆盖，从而导致从初始陷阱恢复所需数据的丢失。引起此关键错误条件的陷阱此后被称为 _意外陷阱_。陷阱处理程序设计为在此处理阶段既不启用中断也不引起异常。然而，管理可能不可预测地发生的硬件错误异常，由于双重陷阱的潜在风险，在陷阱处理程序实现中带来重大挑战。

M-mode-禁用-陷阱（`MDT`）位是由 Smdbltrp 扩展引入的 WARL 字段。复位时，`MDT` 字段设置为 1。当通过显式 CSR 写入将 `MDT` 位设置为 1 时，`MIE`（机器中断使能）位被清除为 0。对于 RV64，无论同一写入对 `MIE` 位写入任何值，都会发生此清除。只有当 `MDT` 位已经为 0 或对于 RV64，同一写入将其设置为 0 时（对于 RV32，`MDT` 位在 `mstatush` 中，`MIE` 位在 `mstatus` 寄存器中），`MIE` 位才能通过显式 CSR 写入设置为 1。

当要进入 M-mode 的陷阱时，如果 `MDT` 位当前为 0，则将其设置为 1，并按预期传递陷阱。但是，如果 `MDT` 已经设置为 1，那么这是一个 _意外陷阱_。当实现 Smrnmi 扩展时，RNMI 引起的陷阱不被视为 _意外陷阱_，无论 `MDT` 位的状态如何。RNMI 引起的陷阱不设置 `MDT` 位。但是，当在 M-mode 中执行且 `mnstatus.NMIE` 设置为 0 时发生的陷阱是 _意外陷阱_。

在发生 _意外陷阱_ 的情况下，处理如下：

* 当实现 Smrnmi 扩展且 `mnstatus.NMIE` 为 1 时，hart 陷阱到 RNMI 处理程序。为了传递此陷阱，`mnepc` 和 `mncause` 寄存器写入 _意外陷阱_ 将分别写入 `mepc` 和 `mcause` 寄存器的值。`mnstatus` 寄存器中的特权模式信息字段写入以指示 M-mode，其 `NMIE` 字段设置为 0。

[NOTE]
====
该规范的结果是，在发生双重陷阱时，RNMI 处理程序不提供陷阱在 `mtval` 和 `mtval2` 寄存器中报告的信息。如果需要，RNMI 处理程序可以通过解码 `mnepc` 中地址处的指令并检查其源寄存器内容来获得此信息。
====

* 当未实现 Smrnmi 扩展时，或如果实现 Smrnmi 扩展且 `mnstatus.NMIE` 为 0，hart 进入关键错误状态而不更新任何架构状态，包括 `pc`。此状态涉及停止执行、禁用所有中断（包括 NMI）并向平台断言 `critical-error` 信号。

[NOTE]
====
当 hart 断言 `critical-error` 信号时平台执行的操作是平台特定的。可能的操作范围包括重启受影响的 hart 或重启整个平台等。
====

`MRET` 和 `SRET` 指令在 M-mode 中执行时，将 `MDT` 位设置为 0。如果新特权模式是 U、VS 或 VU，则 `sstatus.SDT` 也设置为 0。此外，如果是 VU，则 `vsstatus.SDT` 也设置为 0。

由 Smrnmi 扩展提供的 `MNRET` 指令，如果新特权模式不是 M，则将 `MDT` 位设置为 0。如果是 U、VS 或 VU，则 `sstatus.SDT` 也设置为 0。此外，如果是 VU，则 `vsstatus.SDT` 也设置为 0。

[[xlen-control]]
===== `mstatus` 寄存器中的基本 ISA 控制

对于 RV64 hart，SXL 和 UXL 字段是 *WARL* 字段，分别控制 S-mode 和 U-mode 的 XLEN 值。这些字段的编码与 `misa` 的 MXL 字段相同，如 <<misabase>> 所示。S-mode 和 U-mode 中的有效 XLEN 分别称为 _SXLEN_ 和 _UXLEN_。

当 MXLEN=32 时，SXL 和 UXL 字段不存在，SXLEN=32 和 UXLEN=32。

当 MXLEN=64 时，如果不支持 S-mode，则 SXL 为只读零。否则，它是编码当前 SXLEN 值的 *WARL* 字段。特别是，实现可能使 SXL 为只读字段，其值始终确保 SXLEN=MXLEN。

当 MXLEN=64 时，如果不支持 U-mode，则 UXL 为只读零。否则，它是编码当前 UXLEN 值的 *WARL* 字段。特别是，实现可能使 UXL 为只读字段，其值始终确保 UXLEN=MXLEN 或 UXLEN=SXLEN。

如果实现 S-mode，UXL 字段可能假设的合法值集合排除那些会导致 UXLEN 大于 SXLEN 的值。

每当任何模式中的 XLEN 设置为小于最宽支持的 XLEN 的值时，所有操作必须忽略配置 XLEN 以上的源操作数寄存器位，并且必须符号扩展结果以填充目标寄存器中的整个最宽支持的 XLEN。类似地，XLEN 以上的 `pc` 位被忽略，当写入 `pc` 时，它被符号扩展以填充最宽支持的 XLEN。

[NOTE]
====
我们要求操作始终用定义的值填充整个底层硬件寄存器，以避免实现定义的行为。

为了减少硬件复杂性，架构不强制检查较低特权模式的 XLEN 设置小于或等于下一个较高特权模式。在实践中，这种设置几乎总是软件错误，但即使在这种情况下机器操作也是明确定义的。
====

一些 HINT 指令被编码为用当前值覆盖其目标寄存器的整数计算指令，例如 `c.addi x8, 0`。当使用 XLEN < MXLEN 执行这样的 HINT 且目标寄存器的位 MXLEN..XLEN 不全等于位 XLEN-1 时，目标寄存器的位 MXLEN..XLEN 是否保持不变或用位 XLEN-1 的副本覆盖是实现定义的。

注意：该定义允许实现为某些 HINT 省略寄存器写回，同时允许它们以与其他整数计算指令相同的方式执行其他 HINT。实现选择仅由具有大于当前 XLEN 的 XLEN 设置的特权模式可观察；对当前特权模式不可见。

===== `mstatus` 寄存器中的内存特权

MPRV（修改特权）位修改 _有效特权模式_，即执行加载和存储的特权级别。当 MPRV=0 时，加载和存储表现正常，使用当前特权模式的转换和保护机制。当 MPRV=1 时，加载和存储内存地址被转换和保护，并应用字节序，就好像当前特权模式设置为 MPP。指令地址转换和保护不受 MPRV 设置的影响。如果不支持 U-mode，MPRV 为只读 0。

将特权模式更改为小于 M 的模式的 MRET 或 SRET 指令也设置 MPRV=0。

MXR（使可执行可读）位修改加载访问虚拟内存的特权。当 MXR=0 时，只有来自标记为可读（<<sv32pte>> 中 R=1）页面的加载会成功。当 MXR=1 时，来自标记为可读或可执行（R=1 或 X=1）页面的加载会成功。当基于页面的虚拟内存不生效时，MXR 无效。如果不支持 S-mode，MXR 为只读 0。

[NOTE]
====
MPRV 和 MXR 机制的设想是为了提高模拟缺失硬件特性的 M-mode 例程的效率，例如未对齐的加载和存储。MPRV 避免了在软件中执行地址转换的需要。MXR 允许从标记为仅执行的页面加载指令字。

当前特权模式和 MPP 指定的特权模式可能具有不同的 XLEN 设置。当 MPRV=1 时，加载和存储内存地址被视为当前 XLEN 设置为 MPP 的 XLEN，遵循 <<xlen-control>> 中的规则。
====

SUM（允许管理员用户内存访问）位修改 S-mode 加载和存储访问虚拟内存的特权。当 SUM=0 时，S-mode 对 U-mode 可访问页面（<<sv32pte>> 中 U=1）的内存访问将发生故障。当 SUM=1 时，允许这些访问。当基于页面的虚拟内存不生效时，SUM 无效。注意，虽然 SUM 在不在 S-mode 中执行时通常被忽略，但当 MPRV=1 且 MPP=S 时它 _是_ 生效的。如果不支持 S-mode 或 `satp`.MODE 为只读 0，SUM 为只读 0。

MXR 和 SUM 机制只影响页表条目中编码的权限的解释。特别是，它们对由于 PMA 或 PMP 而引发访问故障异常没有影响。

===== `mstatus` 和 `mstatush` 寄存器中的字节序控制

`mstatus` 和 `mstatush` 中的 MBE、SBE 和 UBE 位是 *WARL* 字段，控制除指令获取之外的内存访问的字节序。指令获取始终是小端的。

MBE 控制从 M-mode 进行的非指令获取内存访问（假设 `mstatus`.MPRV=0）是小端（MBE=0）还是大端（MBE=1）。

如果不支持 S-mode，SBE 为只读 0。否则，SBE 控制从 S-mode 进行的显式加载和存储内存访问是小端（SBE=0）还是大端（SBE=1）。

如果不支持 U-mode，UBE 为只读 0。否则，UBE 控制从 U-mode 进行的显式加载和存储内存访问是小端（UBE=0）还是大端（UBE=1）。

对于对管理员级内存管理数据结构（如页表）的 _隐式_ 访问，字节序总是由 SBE 控制。由于更改 SBE 会改变实现对这些数据结构的解释，如果任何这样的数据结构在 SBE 更改后仍在使用，M-mode 软件必须在更改 SBE 后执行 SFENCE.VMA 指令，其中 _rs1_=`x0` 和 _rs2_=`x0`。

[NOTE]
====
只有在人为的场景中，给定的内存管理数据结构才会被解释为小端和大端。在实践中，SBE 只会在世界切换时在运行时更改，在这种情况下，旧的和新的内存管理数据结构都不会以不同的字节序重新解释。在这种情况下，除了世界切换通常需要的之外，不需要额外的 SFENCE.VMA。
====

如果支持 S-mode，实现可能使 SBE 为 MBE 的只读副本。如果支持 U-mode，实现可能使 UBE 为 MBE 或 SBE 的只读副本。

[NOTE]
====
如果字段 MBE、SBE 和 UBE 都为只读 0，则实现仅支持小端内存访问。如果 MBE 为只读 1 且 SBE 和 UBE 在支持 S-mode 和 U-mode 时各自为只读 1，则实现仅支持大端内存访问（除了指令获取）。

'''

卷 I 将 hart 的地址空间定义为连续地址处 2^XLEN^ 字节的循环序列。地址和字节位置之间的对应关系是固定的，不受任何字节序模式的影响。相反，适用的字节序模式确定内存字节和多字节数量（半字、字等）之间映射的顺序。

---

标准 RISC-V ABI 预期纯粹是仅小端或仅大端，不容纳混合字节序。尽管如此，字节序控制已定义为允许，例如，一种字节序的操作系统执行相反字节序的用户模式程序。还考虑了软件根据需要翻转内存访问字节序的非标准用法的可能性。

***

RISC-V 指令统一为小端，将指令编码与当前字节序设置解耦，这有利于硬件和软件。否则，例如，RISC-V 汇编器或反汇编器总是需要知道预期的活动字节序，尽管字节序模式可能在执行期间动态改变。相比之下，通过给指令固定的字节序，有时可能使精心编写的软件即使以二进制形式也与字节序无关，很像位置无关代码。

选择指令仅为小端确实对编码或解码机器指令的 RISC-V 软件有后果。在大端模式下，这样的软件必须考虑显式加载和存储的字节序与指令相反的事实，例如通过在加载后和存储前交换字节顺序。
====

[[virt-control]]
===== `mstatus` 寄存器中的虚拟化支持

TVM（陷阱虚拟内存）位是支持拦截管理员虚拟内存管理操作的 *WARL* 字段。当 TVM=1 时，在 S-mode 中执行时尝试读取或写入 `satp` CSR 或执行 SFENCE.VMA 或 SINVAL.VMA 指令将引发非法指令异常。当 TVM=0 时，在 S-mode 中允许这些操作。当不支持 S-mode 时，TVM 为只读 0。

[NOTE]
====
TVM 机制通过允许客户操作系统在 S-mode 中执行，而不是在 U-mode 中经典地虚拟化它们，提高了虚拟化效率。这种方法避免了陷阱访问大多数 S-mode CSR 的需要。

陷阱 `satp` 访问以及 SFENCE.VMA 和 SINVAL.VMA 指令提供了延迟填充影子页表所需的钩子。
====

TW（超时等待）位是支持拦截 WFI 指令（见 <<wfi>>）的 *WARL* 字段。当 TW=0 时，WFI 指令可以在较低特权模式下执行，当没有因为其他原因阻止时。当 TW=1 时，如果 WFI 在任何较低特权模式下执行，并且它没有在实现特定的有界时间限制内完成，WFI 指令引起非法指令异常。当 TW=1 时，实现可能让 WFI 在较低特权模式下总是引发非法指令异常，即使在执行指令时有待处理的全局禁用中断。当没有小于 M 的模式时，TW 为只读 0。

[NOTE]
====
陷阱 WFI 指令可以触发世界切换到另一个客户操作系统，而不是在当前客户中浪费地空闲。
====

当实现 S-mode 时，在 U-mode 中执行 WFI 引起非法指令异常，除非它在实现特定的有界时间限制内完成。本规范的未来修订可能添加允许 S-mode 选择性地允许 U-mode 中的 WFI 的特性。这样的特性只有在 TW=0 时才活跃。

TSR（陷阱 SRET）位是支持拦截管理员异常返回指令 SRET 的 *WARL* 字段。当 TSR=1 时，在 S-mode 中执行时尝试执行 SRET 将引发非法指令异常。当 TSR=0 时，在 S-mode 中允许此操作。当不支持 S-mode 时，TSR 为只读 0。

[NOTE]
====
陷阱 SRET 对于在不提供管理程序扩展（见 <<hypervisor>>）的实现上模拟它是必要的。
====

===== `mstatus` 寄存器中的扩展上下文状态

支持大量扩展是 RISC-V 的主要目标之一，因此我们定义了一个标准接口，以允许未更改的特权模式代码，特别是管理员级操作系统，支持任意用户模式状态扩展。

[NOTE]
====
迄今为止，V 扩展是唯一定义超出浮点 CSR 和数据寄存器的附加状态的标准扩展。
====

FS[1:0] 和 VS[1:0] *WARL* 字段以及 XS[1:0] 只读字段用于通过设置和跟踪浮点单元和任何其他用户模式扩展的当前状态来减少上下文保存和恢复的成本。FS 字段编码浮点单元状态的状态，包括浮点寄存器 `f0`–`f31` 和 CSR `fcsr`、`frm` 和 `fflags`。VS 字段编码向量扩展状态的状态，包括向量寄存器 `v0`–`v31` 和 CSR `vcsr`、`vxrm`、`vxsat`、`vstart`、`vl`、`vtype` 和 `vlenb`。XS 字段编码附加用户模式扩展和相关状态的状态。这些字段可以由上下文切换例程检查，以快速确定是否需要状态保存或恢复。如果需要保存或恢复，通常需要附加指令和 CSR 来实现和优化过程。

[NOTE]
====
设计预期大多数上下文切换不需要在浮点单元或其他扩展中保存/恢复状态，因此通过 SD 位提供快速检查。
====

FS、VS 和 XS 字段使用如 <<fsxsencoding>> 所示的相同状态编码，四个可能的状态值为 Off、Initial、Clean 和 Dirty。

如果实现 F 扩展，FS 字段不应为只读零。

如果既未实现 F 扩展也未实现 S-mode，则 FS 为只读零。如果实现 S-mode 但未实现 F 扩展，FS 可选为只读零。

[NOTE]
====
具有 S-mode 但没有 F 扩展的实现被允许但不要求使 FS 字段为只读零。一些这样的实现将选择 _不_ 让 FS 字段为只读零，以便通过对 M-mode 的不可见陷阱为 S-mode 和 U-mode 启用 F 扩展的仿真。
====

如果实现 `v` 寄存器，VS 字段不应为只读零。

如果既未实现 `v` 寄存器也未实现 S-mode，则 VS 为只读零。如果实现 S-mode 但未实现 `v` 寄存器，VS 可选为只读零。

在没有需要新状态的附加用户扩展的 hart 中，XS 字段为只读零。每个具有状态的附加扩展提供编码等效于 XS 状态的 CSR 字段。XS 字段表示如 <<fsxsencoding>> 所示的所有扩展状态的摘要。

[NOTE]
====
XS 字段有效地报告所有用户扩展状态字段的最大状态值，尽管各个扩展可以使用与 XS 不同的编码。
====

SD 位是只读位，总结 FS、VS 或 XS 字段是否信号存在一些需要将扩展用户上下文保存到内存的脏状态。如果 FS、XS 和 VS 都为只读零，则 SD 也始终为零。

当扩展的状态设置为 Off 时，任何尝试读取或写入相应状态的指令将引起非法指令异常。当状态为 Initial 时，相应状态应具有初始常数值。当状态为 Clean 时，相应状态可能与初始值不同，但匹配上下文交换时存储的最后值。当状态为 Dirty 时，相应状态可能自上次上下文保存以来已修改。

在上下文保存期间，负责的特权代码只有在其状态为 Dirty 时才需要写出相应状态，然后可以将扩展的状态重置为 Clean。在上下文恢复期间，只有在状态为 Clean 时才需要从内存加载上下文（在恢复时它永远不应该是 Dirty）。如果状态为 Initial，上下文必须在上下文恢复时设置为初始常数值以避免安全漏洞，但这可以在不访问内存的情况下完成。例如，浮点寄存器都可以初始化为立即值 0。

FS 和 XS 字段在保存上下文之前由特权代码读取。在恢复用户上下文时由特权代码直接设置 FS 字段，而通过写入各个扩展的状态寄存器间接设置 XS 字段。状态字段也将在指令执行期间更新，无论特权模式如何。

用户模式 ISA 的扩展通常包括附加用户模式状态，这种状态可能比基础整数寄存器大得多。扩展可能只用于某些应用程序，或者可能只在单个应用程序的短阶段内需要。为了提高性能，用户模式扩展可以定义附加指令，以允许用户模式软件将单元返回到初始状态或甚至关闭单元。

例如，协处理器可能需要在使用前配置，并可以在使用后"取消配置"。取消配置状态将表示为上下文保存的 Initial 状态。如果相同应用程序在取消配置和下次配置之间保持运行（这将状态设置为 Dirty），则在取消配置指令时无需实际重新初始化状态，因为所有状态都是用户进程本地的，即 Initial 状态可能仅在上下文恢复时将协处理器状态初始化为常数值，而不是在每次取消配置时。

执行用户模式指令以禁用单元并将其置于 Off 状态，如果任何后续指令在重新打开单元之前尝试使用该单元，将引起非法指令异常。打开单元的用户模式指令也必须确保单元的状态正确初始化，因为该单元可能同时被另一个上下文使用。

更改 FS 的设置对浮点寄存器状态的内容没有影响。特别是，设置 FS=Off 不会破坏状态，设置 FS=Initial 也不会清除内容。类似地，VS 的设置对向量寄存器状态的内容没有影响。但是，其他扩展在设置为 Off 时可能不保留状态。

实现可以选择通过报告状态为脏来不精确地跟踪浮点寄存器状态的脏性，即使它没有被修改。在某些实现上，一些不改变浮点状态的指令可能导致状态从 Initial 或 Clean 转换到 Dirty。在其他实现上，脏性可能根本不被跟踪，在这种情况下有效的 FS 状态是 Off 和 Dirty，尝试将 FS 设置为 Initial 或 Clean 会导致它被设置为 Dirty。

[NOTE]
====
FS 的这个定义不禁止由于错误推测而将 FS 设置为 Dirty。一些平台可能选择禁止推测性写入 FS 以关闭潜在的侧信道。
====

如果指令显式或隐式写入浮点寄存器或 `fcsr` 但不改变其内容，且 FS=Initial 或 FS=Clean，FS 是否转换到 Dirty 是实现定义的。

实现可以选择以类似的不精确方式跟踪向量寄存器状态的脏性，包括当软件尝试设置 VS=Initial 或 VS=Clean 时可能将 VS 设置为 Dirty。当 VS=Initial 或 VS=Clean 时，写入向量寄存器或向量 CSR 但不改变其内容的指令是否导致 VS 转换到 Dirty 是实现定义的。

[NOTE]
====
许多协处理器扩展仅在有限上下文中使用，允许软件在完成时安全地取消配置甚至禁用单元。这减少了大型有状态协处理器的上下文切换开销。

我们将浮点状态与其他扩展状态分开，因为当存在浮点单元时，浮点寄存器是标准调用约定的一部分，因此用户模式软件无法知道何时安全地禁用浮点单元。
====

XS 字段提供所有添加的扩展状态的摘要，但在扩展中可能维护额外的微架构位以进一步减少上下文保存和恢复开销。

SD 位是只读的，当 FS、VS 或 XS 位编码 Dirty 状态时设置（即 `SD=(FS==0b11 OR XS==0b11 OR VS==0b11)`）。这允许特权代码快速确定何时除了整数寄存器集和 `pc` 之外不需要额外的上下文保存。

浮点单元状态总是使用标准指令（F、D 和/或 Q）初始化、保存和恢复，特权代码必须知道 FLEN 以确定为每个 `f` 寄存器保留的适当空间。

机器和管理员模式共享 FS、VS 和 XS 位的单个副本。管理员级软件通常直接使用 FS、VS 和 XS 位记录相对于管理员级保存上下文的状态。机器级软件在保存和恢复其对应版本的上下文中的扩展状态时必须更加保守。

[NOTE]
====
在任何合理的用例中，用户和管理员级别之间的上下文切换数量应远远超过到其他特权级别的上下文切换数量。注意协处理器不应要求保存和恢复其上下文来服务异步中断，除非中断导致用户级上下文交换。
====

==== 机器陷阱委托 (`medeleg` 和 `mideleg`) 寄存器

默认情况下，任何特权级别的所有陷阱都在机器模式下处理，尽管机器模式处理程序可以使用 MRET 指令（<<otherpriv>>）将陷阱重定向回适当的级别。为了提高性能，实现可以在 `medeleg` 和 `mideleg` 内提供单独的读/写位，以指示某些异常和中断应由较低特权级别直接处理。机器异常委托寄存器（`medeleg`）是 64 位读/写寄存器。机器中断委托（`mideleg`）寄存器是 MXLEN 位读/写寄存器。

在具有 S-mode 的 hart 中，`medeleg` 和 `mideleg` 寄存器必须存在，在 `medeleg` 或 `mideleg` 中设置位将在 S-mode 或 U-mode 中发生时将相应陷阱委托给 S-mode 陷阱处理程序。在没有 S-mode 的 hart 中，`medeleg` 和 `mideleg` 寄存器不应存在。

[NOTE]
====
在版本 1.9.1 和更早版本中，这些寄存器存在但在仅 M-mode 或 M/U 无 N hart 中硬连接为零。没有理由要求它们在这些情况下返回零，因为 `misa` 寄存器指示它们是否存在。
====

当陷阱委托给 S-mode 时，`scause` 寄存器写入陷阱原因；`sepc` 寄存器写入发生陷阱的指令的虚拟地址；`stval` 寄存器写入异常特定数据；`mstatus` 的 SPP 字段写入陷阱时的活动特权模式；`mstatus` 的 SPIE 字段写入陷阱时 SIE 字段的值；`mstatus` 的 SIE 字段被清除。`mcause`、`mepc` 和 `mtval` 寄存器以及 `mstatus` 的 MPP 和 MPIE 字段不写入。

实现可以选择委托陷阱的子集，通过向每个位位置写入 1，然后读回 `medeleg` 或 `mideleg` 中的值以查看哪些位位置保持 1 来找到支持的可委托位。

实现不应有 `medeleg` 的任何位为只读 1，即任何可以委托的同步陷阱都必须支持不被委托。类似地，实现不应固定 `mideleg` 中对应于机器级中断的任何位为只读 1（但可以对较低级别中断这样做）。

[NOTE]
====
版本 1.11 和更早版本禁止 `mideleg` 的任何位为只读 1。平台标准可能总是添加这样的限制。
====

陷阱永远不会从更高特权模式转换到较低特权模式。例如，如果 M-mode 已将非法指令异常委托给 S-mode，M-mode 软件稍后执行非法指令，陷阱在 M-mode 中处理，而不是委托给 S-mode。相比之下，陷阱可能水平处理。使用相同示例，如果 M-mode 已将非法指令异常委托给 S-mode，S-mode 软件稍后执行非法指令，陷阱在 S-mode 中处理。

委托的中断导致中断在委托者特权级别被屏蔽。例如，如果通过设置 `mideleg`[5] 将管理员定时器中断（STI）委托给 S-mode，STI 在 M-mode 中执行时不会被处理。相比之下，如果 `mideleg`[5] 被清除，STI 可以在任何模式中处理，无论当前模式如何都将控制转移到 M-mode。

`medeleg` 为 <<mcauses>> 中显示的每个同步异常分配了位位置，位位置的索引等于 `mcause` 寄存器中返回的值（即设置位 8 允许用户模式环境调用委托给较低特权陷阱处理程序）。

==== 机器中断 (`mip` 和 `mie`) 寄存器

`mip` 寄存器是包含待处理中断信息的 MXLEN 位读/写寄存器，而 `mie` 是包含中断使能位的相应 MXLEN 位读/写寄存器。中断原因号 _i_（如 CSR `mcause` 中报告，<<mcause>>）对应于 `mip` 和 `mie` 中的位 _i_。位 15:0 仅分配给标准中断原因，而位 16 及以上指定用于平台使用。

注意：指定用于平台使用的中断可能由平台自行决定指定用于自定义使用。

.机器中断待处理 (`mip`) 寄存器。
include::images/bytefield/mideleg.edn[]

.机器中断使能 (`mie`) 寄存器
include::images/bytefield/mideleg.edn[]

如果以下所有条件为真，中断 _i_ 将陷阱到 M-mode（导致特权模式更改为 M-mode）：(a) 当前特权模式为 M 且 `mstatus` 寄存器中的 MIE 位被设置，或当前特权模式的特权低于 M-mode；(b) 位 _i_ 在 `mip` 和 `mie` 中都被设置；(c) 如果寄存器 `mideleg` 存在，位 _i_ 在 `mideleg` 中未设置。

必须在从中断在 `mip` 中变为或不再待处理的有界时间内评估这些中断陷阱发生的条件，并且必须在执行 __x__RET 指令或显式写入这些中断陷阱条件明确依赖的 CSR（包括 `mip`、`mie`、`mstatus` 和 `mideleg`）后立即评估。

到 M-mode 的中断优先于到较低特权模式的任何中断。

寄存器 `mip` 中的每个单独位可能是可写的或只读的。当 `mip` 中的位 _i_ 可写时，可以通过向该位写入 0 来清除待处理中断 _i_。如果中断 _i_ 可能变为待处理但 `mip` 中的位 _i_ 为只读，实现必须提供清除待处理中断的其他机制。

如果相应中断可能变为待处理，`mie` 中的位必须可写。不可写的 `mie` 位必须为只读零。

机器级中断寄存器处理一些根中断源，这些中断源被分配固定服务优先级以简化，而单独的外部中断控制器可以在更大的中断集合上实现更复杂的优先级方案，然后复用到机器级中断源中。

不可屏蔽中断不通过 `mip` 寄存器可见，因为它的存在在执行 NMI 陷阱处理程序时隐式已知。

位 `mip`.MEIP 和 `mie`.MEIE 是机器级外部中断的中断待处理和中断使能位。MEIP 在 `mip` 中为只读，由平台特定中断控制器设置和清除。

位 `mip`.MTIP 和 `mie`.MTIE 是机器定时器中断的中断待处理和中断使能位。MTIP 在 `mip` 寄存器中为只读，通过写入内存映射的机器模式定时器比较寄存器来清除。

位 `mip`.MSIP 和 `mie`.MSIE 是机器级软件中断的中断待处理和中断使能位。MSIP 在 `mip` 中为只读，通过访问内存映射控制寄存器写入，这些寄存器被远程 hart 用来提供机器级处理器间中断。hart 可以使用相同的内存映射控制寄存器写入自己的 MSIP 位。如果系统只有一个 hart，或者如果平台标准支持通过外部中断（MEI）而不是机器级处理器间中断的传递，那么 `mip`.MSIP 和 `mie`.MSIE 可能都为只读零。

如果未实现管理员模式，`mip` 的位 SEIP、STIP 和 SSIP 以及 `mie` 的位 SEIE、STIE 和 SSIE 为只读零。

如果实现管理员模式，位 `mip`.SEIP 和 `mie`.SEIE 是管理员级外部中断的中断待处理和中断使能位。SEIP 在 `mip` 中可写，可以由 M-mode 软件写入以向 S-mode 指示外部中断待处理。此外，平台级中断控制器可能生成管理员级外部中断。管理员级外部中断基于软件可写 SEIP 位和来自外部中断控制器的信号的逻辑或变为待处理。当使用 CSR 指令读取 `mip` 时，在 `rd` 目标寄存器中返回的 SEIP 位的值是软件可写位和来自中断控制器的中断信号的逻辑或，但来自中断控制器的信号不用于计算写入 SEIP 的值。只有软件可写 SEIP 位参与 CSRRS 或 CSRRC 指令的读-修改-写序列。

[NOTE]
====
例如，如果我们将软件可写 SEIP 位命名为 `B`，将来自外部中断控制器的信号命名为 `E`，那么如果执行 `csrrs t0, mip, t1`，`t0[9]` 写入 `B || E`，然后 `B` 写入 `B || t1[9]`。如果执行 `csrrw t0, mip, t1`，那么 `t0[9]` 写入 `B || E`，`B` 简单地写入 `t1[9]`。在这两种情况下，`B` 都不依赖于 `E`。

SEIP 字段行为设计为允许较高特权层干净地模拟外部中断，而不丢失任何真实的外部中断。因此 CSR 指令的行为与常规 CSR 访问略有修改。
====

如果实现管理员模式，位 `mip`.STIP 和 `mie`.STIE 是管理员级定时器中断的中断待处理和中断使能位。STIP 在 `mip` 中可写，可以由 M-mode 软件写入以向 S-mode 传递定时器中断。

如果实现管理员模式，位 `mip`.SSIP 和 `mie`.SSIE 是管理员级软件中断的中断待处理和中断使能位。SSIP 在 `mip` 中可写，也可以由平台特定中断控制器设置为 1。

如果实现 Sscofpmf 扩展，位 `mip`.LCOFIP 和 `mie`.LCOFIE 是本地计数器溢出中断的中断待处理和中断使能位。LCOFIP 在 `mip` 中为读写，反映由于任何 `mhpmevent__n__`.OF 位被设置而导致的本地计数器溢出中断请求的发生。如果未实现 Sscofpmf 扩展，`mip`.LCOFIP 和 `mie`.LCOFIE 为只读零。

针对 M-mode 的多个同时中断按以下递减优先级顺序处理：MEI、MSI、MTI、SEI、SSI、STI、LCOFI。

[NOTE]
====
机器级中断固定优先级排序规则是根据以下原理制定的。

较高特权模式的中断必须在较低特权模式的中断之前服务以支持抢占。

位 16 及以上的平台特定机器级中断源具有平台特定优先级，但通常选择具有最高服务优先级以支持非常快的本地向量中断。

外部中断在内部（定时器/软件）中断之前处理，因为外部中断通常由可能需要低中断服务时间的设备生成。

---

软件中断在内部定时器中断之前处理，因为内部定时器中断通常用于时间片，其中时间精度不太重要，而软件中断用于处理器间消息传递。当需要高精度计时时可以避免软件中断，或者高精度定时器中断可以通过不同的中断路径路由。软件中断位于 `mip` 的最低四位，因为这些位经常由软件写入，此位置允许使用带有五位立即数的单个 CSR 指令。
====

`mip` 和 `mie` 寄存器的受限视图作为管理员级别的 `sip` 和 `sie` 寄存器出现。如果通过在 `mideleg` 寄存器中设置位将中断委托给 S-mode，它将在 `sip` 寄存器中变为可见，并可以使用 `sie` 寄存器进行屏蔽。否则，`sip` 和 `sie` 中的相应位为只读零。

==== 硬件性能监控

M-mode 包括基本的硬件性能监控功能。`mcycle` CSR 计算 hart 正在运行的处理器核心执行的时钟周期数。`minstret` CSR 计算 hart 已退役的指令数。`mcycle` 和 `minstret` 寄存器在所有 RV32 和 RV64 hart 上具有 64 位精度。

计数器寄存器在 hart 复位后具有任意值，可以用给定值写入。任何 CSR 写入在写入指令以其他方式完成后生效。`mcycle` CSR 可能在同一核心上的 hart 之间共享，在这种情况下对 `mcycle` 的写入将对这些 hart 可见。平台应提供机制来指示哪些 hart 共享 `mcycle` CSR。

硬件性能监控器包括 29 个额外的 64 位事件计数器，`mhpmcounter3`-`mhpmcounter31`。事件选择器 CSR，`mhpmevent3`-`mhpmevent31`，是控制哪个事件导致相应计数器递增的 64 位 *WARL* 寄存器。这些事件的含义由平台定义，但事件 0 定义为"无事件"。应实现所有计数器，但合法实现是使计数器及其相应事件选择器都为只读 0。

.硬件性能监控计数器。
include::images/bytefield/hpmevents.edn[]

`mhpmcounters` 是支持 RV32 和 RV64 上高达 64 位精度的 *WARL* 寄存器。

当 XLEN=32 时，读取 `mcycle`、`minstret`、`mhpmcounter__n__` 和 `mhpmevent__n__` CSR 返回相应寄存器的位 31-0，写入仅更改位 31-0；读取 `mcycleh`、`minstreth`、`mhpmcounter__n__h` 和 `mhpmevent__n__h` CSR 返回相应寄存器的位 63-32，写入仅更改位 63-32。
仅当实现 Sscofpmf 扩展时才提供 `mhpmevent__n__h` CSR。

[[mcounteren]]
==== 机器计数器使能 (`mcounteren`) 寄存器

计数器使能 `mcounteren` 寄存器是一个 32 位寄存器，控制硬件性能监控计数器对下一个较低特权模式的可用性。

.计数器使能 (`mcounteren`) 寄存器。
include::images/bytefield/counteren.edn[]

该寄存器中的设置仅控制可访问性。读取或写入此寄存器的行为不影响底层计数器，即使在不可访问时计数器也会继续递增。

当 `mcounteren` 寄存器中的 CY、TM、IR 或 HPM__n__ 位被清除时，在 S-mode 或 U-mode 中执行时尝试读取 `cycle`、`time`、`instret` 或 `hpmcountern` 寄存器将引起非法指令异常。当这些位之一被设置时，允许在下一个实现的特权模式（如果实现则为 S-mode，否则为 U-mode）中访问相应寄存器。

[NOTE]
====
计数器使能位以最少的硬件支持两种常见用例。对于不需要高性能定时器和计数器的 hart，机器模式软件可以陷阱访问并在软件中实现所有功能。对于需要高性能定时器和计数器但不关心隐藏底层硬件计数器的 hart，计数器可以直接暴露给较低特权模式。
====

`cycle`、`instret` 和 `hpmcountern` CSR 分别是 `mcycle`、`minstret` 和 `mhpmcounter n` 的只读副本。`time` CSR 是内存映射 `mtime` 寄存器的只读副本。类似地，当 XLEN=32 时，`cycleh`、`instreth` 和 `hpmcounternh` CSR 分别是 `mcycleh`、`minstreth` 和 `mhpmcounternh` 的只读副本。当 XLEN=32 时，`timeh` CSR 是内存映射 `mtime` 寄存器上 32 位的只读副本，而 `time` 仅是 `mtime` 下 32 位的副本。

[NOTE]
====
实现可以将对 `time` 和 `timeh` CSR 的读取转换为对内存映射 `mtime` 寄存器的加载，或在 M-mode 软件中代表较低特权模式模拟此功能。
====

在具有 U-mode 的 hart 中，必须实现 `mcounteren`，但所有字段都是 *WARL* 并且可能为只读零，表示在较低特权模式下执行时读取相应计数器将引起非法指令异常。在没有 U-mode 的 hart 中，`mcounteren` 寄存器不应存在。

==== 机器计数器抑制 (`mcountinhibit`) 寄存器

.计数器抑制 `mcountinhibit` 寄存器
include::images/bytefield/counterinh.edn[]

计数器抑制寄存器 `mcountinhibit` 是一个 32 位 *WARL* 寄存器，控制哪些硬件性能监控计数器递增。该寄存器中的设置仅控制计数器是否递增；它们的可访问性不受该寄存器设置的影响。

当 `mcountinhibit` 寄存器中的 CY、IR 或 HPM__n__ 位被清除时，`mcycle`、`minstret` 或 `mhpmcountern` 寄存器照常递增。当 CY、IR 或 HPM_n_ 位被设置时，相应的计数器不递增。

`mcycle` CSR 可能在同一核心上的 hart 之间共享，在这种情况下 `mcountinhibit.CY` 字段也在这些 hart 之间共享，因此对 `mcountinhibit.CY` 的写入将对这些 hart 可见。

如果未实现 `mcountinhibit` 寄存器，实现表现得就像寄存器被设置为零一样。

[NOTE]
====
当不需要 `mcycle` 和 `minstret` 计数器时，有条件地抑制它们以减少能耗是可取的。提供单个 CSR 来抑制所有计数器还允许对计数器进行原子采样。

因为 `mtime` 计数器可以在多个核心之间共享，所以不能用 `mcountinhibit` 机制抑制它。
====

==== 机器暂存 (`mscratch`) 寄存器

`mscratch` 寄存器是专门供机器模式使用的 MXLEN 位读/写寄存器。通常，它用于保存指向机器模式 hart 本地上下文空间的指针，并在进入 M-mode 陷阱处理程序时与用户寄存器交换。

.机器模式暂存寄存器。
include::images/bytefield/mscratch.edn[]

[NOTE]
====
MIPS ISA 分配了两个用户寄存器（`k0`/`k1`）供操作系统使用。虽然 MIPS 方案提供了快速简单的实现，但它也减少了可用的用户寄存器，并且不能扩展到更多特权级别或嵌套陷阱。它还可能要求在返回用户级别之前清除两个寄存器以避免潜在的安全漏洞并提供确定性调试行为。

RISC-V 用户 ISA 被设计为支持许多可能的特权系统环境，因此我们不想用任何依赖于操作系统的特性感染用户级 ISA。RISC-V CSR 交换指令可以快速保存/恢复 `mscratch` 寄存器的值。与 MIPS 设计不同，操作系统可以依赖在用户上下文运行时在 `mscratch` 寄存器中保持值。
====

==== 机器异常程序计数器 (`mepc`) 寄存器

`mepc` 是一个 MXLEN 位读/写寄存器，格式如 <<mepcreg>> 所示。`mepc` 的低位（`mepc[0]`）始终为零。在仅支持 IALIGN=32 的实现上，两个低位（`mepc[1:0]`）始终为零。

如果实现允许 IALIGN 为 16 或 32（例如通过更改 CSR `misa`），那么，每当 IALIGN=32 时，位 `mepc[1]` 在读取时被屏蔽，使其看起来为 0。这种屏蔽也发生在 MRET 指令的隐式读取中。虽然被屏蔽，但当 IALIGN=32 时 `mepc[1]` 仍然可写。

`mepc` 是一个 *WARL* 寄存器，必须能够保存所有有效的虚拟地址。它不需要能够保存所有可能的无效地址。在写入 `mepc` 之前，实现可能将无效地址转换为 `mepc` 能够保存的其他无效地址。

[NOTE]
====
当地址转换不生效时，虚拟地址和物理地址相等。因此，`mepc` 必须能够表示的地址集合包括可以用作有效 `pc` 或有效地址的物理地址集合。
====

当陷阱进入 M-mode 时，`mepc` 写入被中断或遇到异常的指令的虚拟地址。否则，`mepc` 从不被实现写入，尽管它可以被软件显式写入。

==== 机器原因 (`mcause`) 寄存器

`mcause` 寄存器是一个 MXLEN 位读写寄存器，格式如 <<mcausereg>> 所示。当陷阱进入 M-mode 时，`mcause` 写入指示引起陷阱的事件的代码。否则，`mcause` 从不被实现写入，尽管它可以被软件显式写入。

如果陷阱由中断引起，`mcause` 寄存器中的中断位被设置。异常代码字段包含标识最后一个异常或中断的代码。<<mcauses>> 列出了可能的机器级异常代码。异常代码是 *WLRL* 字段，因此只保证保存支持的异常代码。

.机器原因 (`mcause`) 寄存器。

硬件错误异常是当指令显式或隐式访问损坏或不可纠正的数据时触发的同步异常。在此上下文中，"数据"包括 RISC-V hart 内使用的所有类型的信息。在硬件错误异常时，`__x__epc` 寄存器设置为尝试访问损坏数据的指令地址，而 `__x__tval` 寄存器设置为 0 或尝试访问损坏数据的指令获取、加载或存储的虚拟地址。硬件错误异常的优先级是实现定义的，但任何给定的发生通常期望在发现硬件错误的总体优先级顺序点上被识别。

==== 机器陷阱值 (`mtval`) 寄存器

`mtval` 寄存器是一个 MXLEN 位读写寄存器，格式如 <<mtvalreg>> 所示。当陷阱进入 M-mode 时，`mtval` 要么设置为零，要么写入异常特定信息以协助软件处理陷阱。否则，`mtval` 从不被实现写入，尽管它可以被软件显式写入。硬件平台将指定哪些异常必须信息性地设置 `mtval`，哪些可以无条件地将其设置为零，以及哪些可能表现为任一行为，这取决于引起异常的底层事件。
如果硬件平台指定没有异常将 `mtval` 设置为非零值，那么 `mtval` 为只读零。

如果当断点、地址未对齐、访问故障或页面故障异常在指令获取、加载或存储时发生时 `mtval` 写入非零值，那么 `mtval` 将包含故障虚拟地址。

当启用基于页面的虚拟内存时，`mtval` 写入故障虚拟地址，即使对于物理内存访问故障异常也是如此。这种设计为大多数实现减少了数据路径成本，特别是那些具有硬件页表遍历器的实现。

[[mtvalreg]]
.机器陷阱值 (`mtval`) 寄存器。
include::images/bytefield/mtvalreg.edn[]


如果当未对齐的加载或存储引起访问故障或页面故障异常时 `mtval` 写入非零值，那么 `mtval` 将包含引起故障的访问部分的虚拟地址。

如果当指令访问故障或页面故障异常在具有可变长度指令的 hart 上发生时 `mtval` 写入非零值，那么 `mtval` 将包含引起故障的指令部分的虚拟地址，而 `mepc` 将指向指令的开始。

`mtval` 寄存器也可以可选地用于在非法指令异常时返回故障指令位（`mepc` 指向内存中的故障指令）。如果当非法指令异常发生时 `mtval` 写入非零值，那么 `mtval` 将包含以下中最短的：

* 实际故障指令

* 故障指令的前 ILEN 位

* 故障指令的前 MXLEN 位

在非法指令异常时加载到 `mtval` 中的值是右对齐的，所有未使用的上位都清零。

[NOTE]
====
在 `mtval` 中捕获故障指令减少了指令仿真的开销，如果指令未对齐则可能避免几次部分指令加载，并且当使用加载将指令获取到数据寄存器时可能避免数据缓存未命中或慢的非缓存访问。如果另一个代理正在操纵指令内存，也存在原子性问题，如在动态翻译系统中可能发生的那样。

要求是在进入陷阱之前将整个指令（或至少前 MXLEN 位）获取到 `mtval` 中。这不应约束实现，实现通常在尝试解码指令之前获取整个指令，并避免复杂化软件处理程序。

`mtval` 中的零值表示该功能不受支持，或获取了非法零指令。可以使用从 `mepc` 指向的指令内存的加载来区分这两种情况（或者，可以查询系统配置信息以在运行时之前安装适当的陷阱处理）。
====

在由软件检查异常引起的陷阱中，`mtval` 寄存器保存异常的原因。定义了以下编码：

* 0 - 未提供信息。
* 2 - 着陆垫故障。由 Zicfilp 扩展定义（<<priv-forward>>）。
* 3 - 影子栈故障。由 Zicfiss 扩展定义（<<priv-backward>>）。

对于其他陷阱，`mtval` 设置为零，但未来的标准可能重新定义其他陷阱的 `mtval` 设置。

如果 `mtval` 不是只读零，它是一个 *WARL* 寄存器，必须能够保存所有有效虚拟地址和零值。它不需要能够保存所有可能的无效地址。在写入 `mtval` 之前，实现可能将无效地址转换为 `mtval` 能够保存的其他无效地址。如果实现了返回故障指令位的功能，`mtval` 还必须能够保存所有小于 2^__N__^ 的值，其中 _N_ 是 MXLEN 和 ILEN 中的较小值。

`mconfigptr` 寄存器是一个 MXLEN 位只读 CSR，格式如 <<mconfigptrreg>> 所示，保存配置数据结构的物理地址。软件可以遍历此数据结构以发现有关 hart、平台及其配置的信息。

[[mconfigptrreg]]
.机器配置指针 (`mconfigptr`) 寄存器。

指针对齐（以位为单位）必须不小于 MXLEN：即，如果 MXLEN 是 latexmath:[$8\times n$]，那么 `mconfigptr`[latexmath:[$\log_2n$]-1:0] 必须为零。

虽然 `mconfigptr` 寄存器在某些实现中将简单地硬连线，但其他实现可能提供配置 CSR 读取时返回值的方法。例如，`mconfigptr` 可能呈现由平台或 M-mode 软件在引导过程开始时编程的内存映射寄存器的值。

PBMTE 位控制 Svpbmt 扩展是否可用于 S-mode 和 G 阶段地址转换（即，用于由 `satp` 或 `hgatp` 指向的页表）。当 PBMTE=1 时，Svpbmt 可用于 S-mode 和 G 阶段地址转换。当 PBMTE=0 时，实现表现得就像未实现 Svpbmt 一样。如果未实现 Svpbmt，PBMTE 为只读零。此外，对于具有虚拟化扩展的实现，如果 `menvcfg`.PBMTE 为零，`henvcfg`.PBMTE 为只读零。

更改 `menvcfg`.PBMTE 后，执行 _rs1_=`x0` 和 _rs2_=`x0` 的 SFENCE.VMA 指令足以使地址转换缓存与页表条目的 PBMT 字段的更改解释同步。实现虚拟化扩展时的其他同步要求请参见 <<hyp-mm-fences>>。

如果实现 Svadu 扩展，ADUE 位控制是否为 S-mode 和 G 阶段地址转换启用 PTE A/D 位的硬件更新。
当 ADUE=1 时，在 S-mode 地址转换期间启用 PTE A/D 位的硬件更新，实现表现得就像未为 S-mode 地址转换实现 Svade 扩展一样。
当实现虚拟化扩展时，如果 ADUE=1，在 G 阶段地址转换期间启用 PTE A/D 位的硬件更新，实现表现得就像未为 G 阶段地址转换实现 Svade 扩展一样。
当 ADUE=0 时，实现表现得就像为 S-mode 和 G 阶段地址转换实现了 Svade。
如果未实现 Svadu，ADUE 为只读零。
此外，对于具有虚拟化扩展的实现，如果 `menvcfg`.ADUE 为零，`henvcfg`.ADUE 为只读零。

注意：Svade 扩展要求在需要设置 PTE A/D 位时引发页面故障异常，因此当 ADUE=0 时实现 Svade。

如果实现 Smcdeleg 扩展，CDE（计数器委托使能）位控制 Zicntr 和 Zihpm 计数器是否可以委托给 S-mode。当 CDE=1 时，启用 Smcdeleg 扩展，请参见 <<smcdeleg>>。当 CDE=0 时，Smcdeleg 和 Ssccfg 扩展看起来未实现。如果未实现 Smcdeleg，CDE 为只读零。

STCE 字段的定义由 Sstc 扩展提供。

CBZE 字段的定义由 Zicboz 扩展提供。

CBCFE 和 CBIE 字段的定义由 Zicbom 扩展提供。

PMM 字段的定义由 Smnpm 扩展提供。

Zicfilp 扩展在 `menvcfg` 中添加了 `LPE` 字段。当 `LPE` 字段设置为 1 且实现了 S-mode 时，在 S-mode 中启用 Zicfilp 扩展。如果 `LPE` 字段设置为 1 且未实现 S-mode，在 U-mode 中启用 Zicfilp 扩展。当 `LPE` 字段为 0 时，Zicfilp 扩展未在 S-mode 中启用，以下规则适用于 S-mode。如果 `LPE` 字段为 0 且未实现 S-mode，则相同规则适用于 U-mode。

* hart 不更新 `ELP` 状态；它保持为 `NO_LP_EXPECTED`。
* `LPAD` 指令作为无操作运行。

Zicfiss 扩展向 `menvcfg` 添加 `SSE` 字段。当 `SSE` 字段设置为 1 时，在 S-mode 中激活 Zicfiss 扩展。当 `SSE` 字段为 0 时，以下规则适用于特权级别低于 M 的模式：

* 32 位 Zicfiss 指令将恢复到 Zimop 定义的行为。
* 16 位 Zicfiss 指令将恢复到 Zcmop 定义的行为。
* VS/S 阶段页表中的 `pte.xwr=010b` 编码变为保留。
* `SSAMOSWAP.W/D` 引发非法指令异常。

当 `menvcfg.SSE` 为 0 时，`henvcfg.SSE` 和 `senvcfg.SSE` 字段为只读零。

Ssdbltrp 扩展在 `menvcfg` 中添加双重陷阱使能（`DTE`）字段。当 `menvcfg.DTE` 为零时，实现表现得就像未实现 Ssdbltrp 一样。当未实现 Ssdbltrp 时，`sstatus.SDT`、`vsstatus.SDT` 和 `henvcfg.DTE` 位为只读零。

当 XLEN=32 时，`menvcfgh` 是一个 32 位读/写寄存器，别名 `menvcfg` 的位 63:32。当 XLEN=64 时，`menvcfgh` 寄存器不存在。

如果不支持 U-mode，则寄存器 `menvcfg` 和 `menvcfgh` 不存在。

=== 机器级内存映射寄存器

==== 机器定时器 (`mtime` 和 `mtimecmp`) 寄存器

平台提供实时计数器，作为内存映射的机器模式读写寄存器 `mtime` 暴露。`mtime` 必须以恒定频率递增，平台必须提供确定 `mtime` 时钟周期周期的机制。如果计数溢出，`mtime` 寄存器将回绕。

`mtime` 寄存器在所有 RV32 和 RV64 系统上具有 64 位精度。平台提供 64 位内存映射的机器模式定时器比较寄存器（`mtimecmp`）。每当 `mtime` 包含大于或等于 `mtimecmp` 的值时，机器定时器中断变为待处理，将值视为无符号整数。中断保持发布，直到 `mtimecmp` 变为大于 `mtime`（通常是写入 `mtimecmp` 的结果）。只有在启用中断且在 `mie` 寄存器中设置 MTIE 位时才会处理中断。

.机器时间寄存器（内存映射控制寄存器）。
include::images/bytefield/mtime.edn[]

.机器时间比较寄存器（内存映射控制寄存器）。
include::images/bytefield/mtimecmp.edn[]

[NOTE]
====
定时器设施定义为使用挂钟时间而不是周期计数器，以支持运行在高度可变时钟频率下的现代处理器，通过动态电压和频率缩放来节省能源。

精确的实时时钟（RTC）提供相对昂贵（需要晶体或 MEMS 振荡器），并且必须在系统其余部分断电时运行，因此系统中通常只有一个，位于与处理器不同的频率/电压域中。因此，RTC 必须被系统中的所有 hart 共享，对 RTC 的访问可能会产生电压电平转换器和时钟域交叉的损失。因此，将 `mtime` 暴露为内存映射寄存器比作为 CSR 更自然。

较低特权级别没有自己的 `timecmp` 寄存器。相反，机器模式软件可以通过将下一个定时器中断复用到 `mtimecmp` 寄存器中，在 hart 上实现任意数量的虚拟定时器。

简单的固定频率系统可以使用单个时钟进行周期计数和挂钟时间。
====

如果 `mtime` 和 `mtimecmp` 之间的比较结果发生变化，保证最终会反映在 MTIP 中，但不一定立即反映。

[NOTE]
====
如果中断处理程序递增 `mtimecmp` 然后立即返回，可能会发生虚假定时器中断，因为 MTIP 可能在此期间尚未下降。所有软件都应该编写为假设此事件是可能的，但大多数软件应该假设此事件极不可能。承受偶尔的虚假定时器中断几乎总是比轮询 MTIP 直到它下降更高性能。
====

=== 机器模式特权指令

==== 环境调用和断点

include::images/wavedrom/mm-env-call.edn[]

ECALL 指令用于向支持的执行环境发出请求。当在 U-mode、S-mode 或 M-mode 中执行时，它分别生成来自 U-mode 的环境调用异常、来自 S-mode 的环境调用异常或来自 M-mode 的环境调用异常，并且不执行其他操作。

[NOTE]
====
ECALL 为每个发起特权模式生成不同的异常，以便可以选择性地委托环境调用异常。类 Unix 操作系统的典型用例是将来自 U-mode 的环境调用异常委托给 S-mode，但不委托其他异常。
====

EBREAK 指令由调试器用于使控制转移回调试环境。除非被外部调试环境覆盖，EBREAK 引发断点异常并且不执行其他操作。

[NOTE]
====
如本手册第一卷中的压缩指令"C"标准扩展中所述，C.EBREAK 指令执行与 EBREAK 指令相同的操作。
====

ECALL 和 EBREAK 使接收特权模式的 `epc` 寄存器设置为 ECALL 或 EBREAK 指令本身的地址，_而不是_ 后续指令的地址。由于 ECALL 和 EBREAK 引起同步异常，它们不被认为是退役的，并且不应该递增 `minstret` CSR。

要在处理陷阱后返回，每个特权级别都有单独的陷阱返回指令，MRET 和 SRET。始终提供 MRET。如果支持管理员模式，必须提供 SRET，否则应引发非法指令异常。当 `mstatus` 中 TSR=1 时，SRET 也应引发非法指令异常，如 <<virt-control>> 中所述。__x__RET 指令可以在特权模式 _x_ 或更高级别中执行，其中执行较低特权 __x__RET 指令将弹出相关的较低特权中断使能和特权模式栈。尝试在特权级别低于 _x_ 的模式中执行 __x__RET 指令将引发非法指令异常。除了如 <<privstack>> 中所述操作特权栈外，__x__RET 将 `pc` 设置为存储在 `__x__epc` 寄存器中的值。

[[wfi]]
==== 等待中断

等待中断指令（WFI）通知实现当前 hart 可以停滞，直到可能需要服务中断。执行 WFI 指令也可用于通知硬件平台应优先将适当的中断路由到此 hart。WFI 在所有特权模式中可用，并且可选地可用于 U-mode。如 <<virt-control>> 中所述，当 `mstatus` 中 TW=1 时，此指令可能引发非法指令异常。

include::images/wavedrom/wfi.edn[]

如果已启用的中断存在或在 hart 停滞时稍后变为存在，中断陷阱将在后续指令上进行，即，执行在陷阱处理程序中恢复且 `mepc` = `pc` + 4。

[NOTE]
====
后续指令进行中断陷阱，以便从陷阱处理程序的简单返回将执行 WFI 指令之后的代码。
====

实现被允许因任何原因恢复执行，即使已启用的中断尚未变为待处理。因此，合法实现是简单地将 WFI 指令实现为 NOP。

[NOTE]
====
如果实现在执行指令时不停滞 hart，那么中断将在包含 WFI 的空闲循环中的某个指令上进行，并且在从处理程序的简单返回时，空闲循环将恢复执行。
====

WFI 指令也可以在中断被禁用时执行。WFI 的操作必须不受 `mstatus`（MIE 和 SIE）中的全局中断位和委托寄存器 `mideleg` 的影响（即，如果本地启用的中断变为待处理，hart 必须恢复，即使它已被委托给较低特权模式），但应尊重单独的中断使能（例如，MTIE）（即，如果中断待处理但未单独启用，实现应避免恢复 hart）。WFI 还需要为任何特权级别待处理的本地启用中断恢复执行，无论每个特权级别的全局中断使能如何。

如果导致 hart 恢复执行的事件不导致中断被处理，执行将在 `pc` + 4 处恢复，软件必须确定要采取的行动，包括如果没有可操作事件则循环回去重复 WFI。

[NOTE]
====
通过允许在中断禁用时唤醒，可以调用中断处理程序的替代入口点，该入口点不需要保存当前上下文，因为可以在执行 WFI 之前保存或丢弃当前上下文。

由于实现可以自由地将 WFI 实现为 NOP，软件必须在 WFI 之后的代码中显式检查任何相关的待处理但禁用的中断，如果未检测到合适的中断，应循环回到 WFI。可以查询 `mip` 或 `sip` 寄存器以分别确定机器或管理员模式中任何中断的存在。

WFI 的操作不受委托寄存器设置的影响。

WFI 被定义为实现可以陷阱到更高特权模式，要么在遇到 WFI 时立即陷阱，要么在某个间隔后启动到较低功耗状态的机器模式转换，例如。

***

相同的"等待事件"模板可能用于等待内存位置变化或消息到达的可能未来扩展。

=== 复位

复位时，hart 的特权模式设置为 M。`mstatus` 字段 MIE 和 MPRV 复位为 0。如果支持小端内存访问，`mstatus`/`mstatush` 字段 MBE 复位为 0。`misa` 寄存器复位为启用最大支持扩展集合，如 <<misa>> 中所述。对于具有"A"标准扩展的实现，没有有效的加载保留。`pc` 设置为实现定义的复位向量。`mcause` 寄存器设置为指示复位原因的值。可写 PMP 寄存器的 A 和 L 字段设置为 0，除非平台要求某些 PMP 寄存器的 A 和 L 字段有不同的复位值。如果实现虚拟化扩展，`hgatp`.MODE 和 `vsatp`.MODE 字段复位为 0。如果实现 Smrnmi 扩展，`mnstatus`.NMIE 字段复位为 0。没有 *WARL* 字段包含非法值。如果实现 Zicfilp 扩展，`mseccfg`.MLPE 字段复位为 0。所有其他 hart 状态是未指定的。

复位后的 `mcause` 值具有实现特定的解释，但在不区分不同复位条件的实现上应返回值 0。区分不同复位条件的实现应仅使用 0 来表示最完整的复位。

[NOTE]
====
某些设计可能有多种复位原因（例如，上电复位、外部硬复位、检测到掉电、看门狗定时器到期、睡眠模式唤醒），机器模式软件和调试器可能希望区分这些。

`mcause` 复位值可能与同步异常后的 `mcause` 值重叠。这种重叠应该没有歧义，因为在复位时 `pc` 通常设置为与其他陷阱不同的值。
====

[[nmi]]
=== 不可屏蔽中断

不可屏蔽中断（NMI）仅用于硬件错误条件，并引起立即跳转到在 M-mode 中运行的实现定义的 NMI 向量，无论 hart 的中断使能位状态如何。`mepc` 寄存器写入被中断指令的虚拟地址，`mcause` 设置为指示 NMI 源的值。因此，NMI 可以覆盖活动机器模式中断处理程序中的状态。

在 NMI 上写入 `mcause` 的值是实现定义的。`mcause` 的高中断位应设置为指示这是中断。异常代码 0 保留为表示"未知原因"，不通过 `mcause` 寄存器区分 NMI 源的实现应在异常代码中返回 0。

与复位不同，NMI 不复位处理器状态，从而能够诊断、报告和可能包含硬件错误。

[[pma]]
=== 物理内存属性

完整系统的物理内存映射包括各种地址范围，一些对应于内存区域，一些对应于内存映射控制寄存器，其中部分可能不可访问。某些内存区域可能不支持读取、写入或执行；某些可能不支持子字或子块访问；某些可能不支持原子操作；某些可能不支持缓存一致性或可能具有不同的内存模型。类似地，内存映射控制寄存器在其支持的访问宽度、对原子操作的支持以及读写访问是否具有相关副作用方面有所不同。在 RISC-V 系统中，机器物理地址空间每个区域的这些属性和能力称为 _物理内存属性_（PMA）。本节描述 RISC-V PMA 术语以及 RISC-V 系统如何实现和检查 PMA。

PMA 是底层硬件的固有属性，在系统操作期间很少改变。与 <<pmp>> 中描述的物理内存保护值不同，PMA 不因执行上下文而变化。某些内存区域的 PMA 在芯片设计时固定——例如，对于片上 ROM。其他在板设计时固定，例如取决于哪些其他芯片连接到片外总线。片外总线也可能支持可以在每个电源周期上更改（冷插拔）或在系统运行时动态更改（热插拔）的设备。某些设备可能在运行时可配置以支持暗示不同 PMA 的不同用途——例如，片上暂存 RAM 可能在一个最终应用中由一个核心私有缓存，或在另一个最终应用中作为共享非缓存内存访问。

大多数系统将要求至少一些 PMA 在已知物理地址后在执行管道中稍后在硬件中动态检查，因为某些操作在所有物理内存地址上都不受支持，某些操作需要知道可配置 PMA 属性的当前设置。虽然许多其他架构在虚拟内存页表中指定一些 PMA 并使用 TLB 通知管道这些属性，但这种方法将平台特定信息注入虚拟化层，除非在每个物理内存区域的每个页表条目中正确初始化属性，否则可能导致系统错误。此外，可用页面大小可能不是在物理内存空间中指定属性的最佳选择，导致地址空间碎片化和昂贵 TLB 条目的低效使用。

对于 RISC-V，我们将 PMA 的规范和检查分离到单独的硬件结构，_PMA 检查器_。在许多情况下，每个物理地址区域的属性在系统设计时已知，可以硬连线到 PMA 检查器中。在属性运行时可配置的地方，可以提供平台特定的内存映射控制寄存器，以在适合平台上每个区域的粒度上指定这些属性（例如，对于可以在可缓存和不可缓存用途之间灵活划分的片上 SRAM）。
对物理内存的任何访问都会检查 PMA，包括已经历虚拟到物理内存转换的访问。为了帮助系统调试，我们强烈建议在可能的情况下，RISC-V 处理器精确地陷阱未通过 PMA 检查的物理内存访问。精确陷阱的 PMA 违规表现为指令、加载或存储访问故障异常，与虚拟内存页面故障异常不同。精确 PMA 陷阱可能并不总是可能的，例如，当探测使用访问失败作为发现机制的一部分的传统总线架构时。在这种情况下，来自外围设备的错误响应将报告为不精确的总线错误中断。

软件也必须能够读取 PMA 以正确访问某些设备或正确配置访问内存的其他硬件组件，如 DMA 引擎。由于 PMA 与给定物理平台的组织紧密相关，许多细节本质上是平台特定的，软件可以学习平台 PMA 值的方式也是如此。某些设备，特别是传统总线，不支持 PMA 的发现，因此如果尝试不受支持的访问，将给出错误响应或超时。通常，平台特定的机器模式代码将提取 PMA，并最终使用某种标准表示将此信息呈现给更高级别的较低特权软件。

在平台支持 PMA 动态重新配置的地方，将提供接口以通过将请求传递给可以正确重新配置平台的机器模式驱动程序来设置属性。例如，在某些内存区域上切换可缓存性属性可能涉及平台特定的操作，如缓存刷新，这些操作仅对机器模式可用。

==== 主内存与 I/O 区域

给定内存地址范围最重要的特征是它是否包含常规主内存或 I/O 设备。
常规主内存需要具有下面指定的许多属性，而 I/O 设备可以具有更广泛的属性范围。不适合常规主内存的内存区域，例如设备暂存 RAM，被归类为 I/O 区域。

注意：本规范以前版本称为 _空闲_ 区域的不再是单独的类别；它们现在被描述为不可访问的 I/O 区域（即缺乏读取、写入和执行权限）。
也允许不可访问的主内存区域。

==== 支持的访问类型 PMA

访问类型指定支持哪些访问宽度，从 8 位字节到长多字突发，以及每个访问宽度是否支持未对齐访问。

[NOTE]
====
虽然在 RISC-V hart 上运行的软件无法直接生成到内存的突发，但软件可能需要编程 DMA 引擎来访问 I/O 设备，因此可能需要知道支持哪些访问大小。
====

主内存区域始终支持连接设备所需的所有访问宽度的读取和写入，并可以指定是否支持指令获取。

[NOTE]
====
某些平台可能要求所有主内存都支持指令获取。其他平台可能禁止从某些主内存区域进行指令获取。

***

在某些情况下，访问主内存的处理器或设备的设计可能支持其他宽度，但必须能够使用主内存支持的类型进行功能。
====

I/O 区域可以指定支持哪些读取、写入或执行访问与哪些数据宽度的组合。

对于具有基于页面的虚拟内存的系统，I/O 和内存区域可以指定支持哪些硬件页表读取和硬件页表写入的组合。

[NOTE]
====
类 Unix 操作系统通常要求所有可缓存主内存都支持页表遍历。
====

==== 原子性 PMA

原子性 PMA 描述此地址区域中支持哪些原子指令。对原子指令的支持分为两类：_LR/SC_ 和 _AMO_。

[NOTE]
====
某些平台可能要求所有可缓存主内存都支持连接处理器所需的所有原子操作。
====

===== AMO PMA

在 AMO 内，有四个支持级别：_AMONone_、_AMOSwap_、_AMOLogical_ 和 _AMOArithmetic_。AMONone 表示不支持 AMO 操作。AMOSwap 表示此地址范围仅支持 `amoswap` 指令。AMOLogical 表示支持交换指令加上所有逻辑 AMO（`amoand`、`amoor`、`amoxor`）。AMOArithmetic 表示支持所有 RISC-V AMO。对于每个支持级别，如果底层内存区域支持该宽度的读取和写入，则支持给定宽度的自然对齐 AMO。主内存和 I/O 区域可能仅支持处理器支持的原子操作的子集或不支持。

===== 保留性 PMA

对于 _LR/SC_，有三个支持级别表示保留性和最终性属性的组合：_RsrvNone_、_RsrvNonEventual_ 和 _RsrvEventual_。RsrvNone 表示不支持 LR/SC 操作（位置不可保留）。
RsrvNonEventual 表示支持操作（位置可保留），但没有非特权 ISA 规范中描述的最终成功保证。RsrvEventual 表示支持操作并提供最终成功保证。

[NOTE]
====
我们建议在可能的情况下为主内存区域提供 RsrvEventual 支持。大多数 I/O 区域不支持 LR/SC 访问，因为这些最方便地构建在缓存一致性方案之上，但某些可能支持 RsrvNonEventual 或 RsrvEventual。

***

当 LR/SC 用于标记为 RsrvNonEventual 的内存位置时，软件应提供在检测到缺乏进展时使用的替代回退机制。
====

==== 未对齐原子性粒度 PMA

未对齐原子性粒度 PMA 为未对齐 AMO 提供受约束的支持。
此 PMA（如果存在）指定 _未对齐原子性粒度_ 的大小，自然对齐的 2 的幂字节数。
此 PMA 的特定支持值由 MAG__NN__ 表示，例如，MAG16 表示未对齐原子性粒度至少为 16 字节。

未对齐原子性粒度 PMA 仅适用于 AMO、基础 ISA 中定义的加载和存储，以及 F、D 和 Q 扩展中定义的不超过 XLEN 位的加载和存储。
对于该集合中的指令，如果所有访问的字节都位于同一个未对齐原子性粒度内，指令不会因地址对齐原因引发异常，并且指令对 RVWMO 的目的将仅产生一个内存操作——即，它将原子执行。

如果未对齐 AMO 访问未指定未对齐原子性粒度 PMA 的区域，或如果不是所有访问的字节都位于同一个未对齐原子性粒度内，则引发异常。
对于访问此类区域或不是所有访问的字节都位于同一原子性粒度内的常规加载和存储，要么引发异常，要么访问继续但不保证是原子的。
实现可以为某些未对齐访问引发访问故障异常而不是地址未对齐异常，表示指令不应由陷阱处理程序模拟。

注意：LR/SC 指令不受此 PMA 影响，因此在未对齐时总是引发异常。向量内存访问也不受影响，因此即使包含在未对齐原子性粒度内也可能非原子执行。隐式访问同样不受此 PMA 影响。

==== 内存排序 PMA

为了被 FENCE 指令排序的目的，地址空间的区域被分类为 _主内存_ 或 _I/O_
