== 密码学扩展：向量指令，版本 1.0

本文档描述了 RISC-V 指令集架构的向量密码学扩展。

[[crypto_vector_introduction]]
=== 引言

本文档描述了 RISC-V _向量_ 密码学扩展。
此处提出的所有指令都基于向量寄存器。
这些指令旨在实现高性能，主要目标是大型应用程序和服务器级核心。
配套章节 _第一卷：标量和熵源指令_，描述了
不实现向量扩展的小型核心的密码学指令提案。

[[crypto_vector_audience]]
==== 目标受众

密码学是一个专业领域，需要具有不同背景的人员合作才能安全高效地实现。
在可能的情况下，我们编写本规范时力求让所有人都能理解，尽管我们认识到，对于非领域专家来说，动机以及对算法或其他规范和标准的引用可能不熟悉。

本规范预计将被具有不同背景的各种人士阅读和采纳。
我们试图在此处捕捉这些背景，并简要说明我们期望他们了解什么，以及这与规范的关系。
我们希望这有助于人们理解规范的哪些方面与他们特别相关，以及他们可以（安全地！）忽略或交给同事的方面。

密码学家和密码软件开发人员::
我们期望这些人使用本规范中的指令编写代码。
他们应该相当清楚地理解我们包含的指令的动机，并熟悉我们引用的大多数算法和外部标准。

计算机架构师::
我们不期望架构师具有密码学背景。
尽管如此，我们仍然期望架构师能够检查我们的指令是否存在实现问题，理解指令将如何在上下文中被使用，并就如何最好地将密码学家想要的功能与 ISA 接口匹配提供建议。

数字设计工程师和微架构师::
这些人将在核心内部实现规范。同样，不假定具备密码学专业知识，但我们期望他们解释规范并预测任何硬件实现问题，例如，在高频设计考虑适用或存在延迟/面积权衡等情况下。
特别是，他们应该了解围绕高效实现 AES 和 SM4 SBox 的文献。

验证工程师::
这些人负责确保硬件中扩展的正确实现。
不假定具备密码学背景。
我们期望他们从规范中识别有趣的测试用例。了解其在实际世界中的用法将有助于此。

这些人绝不是唯一关注本规范的人，但他们在我们撰写本规范时是我们考虑最多的人。

[[crypto_vector_sail_specifications]]
==== Sail 规范

RISC-V 维护一个
link:https://github.com/riscv/sail-riscv[形式化模型]
的 ISA 规范，
使用 Sail ISA 规范语言实现
cite:[sail]。
请注意，_Sail_ 指的是规范语言本身，
并且有一个 _RISC-V 模型_，使用 Sail 编写。
将“Sail 模型”称为不正确。
鉴于使用 Sail 实现了许多不同 ISA 的模型，这会产生歧义。
我们将 RISC-V 的 Sail 实现称为
“RISC-V Sail 模型”。

我们打算在本规范中包含实际的 Sail 代码。
然而，向量密码 Sail 模型需要向量 Sail 模型作为构建基础。
此向量密码学扩展规范在批准 RISC-V 向量 Sail 模型之前完成。
因此，我们没有在指令描述中包含任何 Sail 代码。
相反，我们包含了类似 Sail 的伪代码。虽然我们努力遵守 Sail 语法，
但为了简洁起见，我们采取了一些自由，
我们相信我们的意图对读者来说是清楚的。

[NOTE]
====
当变量连接时，所示顺序是它们在向量寄存器中从左到右的出现顺序。
例如，指定为 `{a, b, e, f}` 的元素组将出现在向量寄存器中，其中 `a` 具有该组的最高元素索引，`f` 具有该组的最低索引。
====

为了简洁起见，我们的伪代码不包括对掩码或尾部元素的处理。
我们遵循 *RISC-V “V”向量扩展* 规范中描述的掩码和尾部的 _不受干扰_ 和 _无关_ 策略。
此外，代码不明确处理重叠和 SEW 约束；然而，这些在文本中明确说明。

在许多情况下，伪代码包含
对支持函数的调用，这些函数过于冗长，无法直接包含在规范中。
此支持代码列在
<<crypto_vector_appx_sail>> 中。


建议阅读
link:https://alasdair.github.io/manual.html[Sail 手册]
以更好地理解代码片段。
此外，
link:https://github.com/billmcspadden-riscv/sail/blob/cookbook_br/cookbook/doc/TheSailCookbook_Complete.pdf[Sail 编程语言：Sail 食谱]
是一个很好的参考。

有关最新的 RISC-V Sail 模型，请参阅
形式化模型 GitHub
link:https://github.com/riscv/sail-riscv[仓库]。

[[crypto_vector_policies]]
==== 策略

在创建此提案时，我们努力遵守以下策略：

* 在以下选择之间：
  1) 支持算法的多种实现策略
  或
  2) 支持单一的、性能更高/成本更低的实现风格；
  向量密码扩展将选择更受约束但性能更高的选项。
  这符合 RISC-V 规范其他部分的常见模式，
  其中执行特定任务的推荐（但非必需）指令序列作为示例给出，
  以便硬件和软件实现者可以仅针对单一用例进行优化。

* 扩展将旨在很好地支持 _现有_ 标准化密码结构。
  它不会尝试支持提议的标准，或仅存在于学术界的密码结构。
  与 RISC-V 密码扩展标准化同时或之后确定的密码标准将通过
  未来对 RISC-V 密码标准扩展的添加或版本进行处理。

* 从历史上看，曾有一些讨论
  cite:[LSYRR:04]
  关于通用计算中新支持的操作如何
  为密码算法启用新基础。
  标准不会尝试预测新的有用低级操作，这些操作 _可能_ 有用作
  未来密码结构的构建块。

* 关于侧信道对策：
  在相关情况下，提议的指令必须旨在消除任何时序侧信道的可能性。
  所有指令都应以数据无关的时序实现。也就是说，这些指令的执行延迟不应随不同的输入值而变化。

[[crypto-vector-element-groups]]
==== 元素组

许多向量密码指令操作的运算数比元素宽（目前限制为 64 位宽）。
通常，这些运算数是 128 位和 256 位宽。在许多情况下，这些运算数由较小的运算数组成，这些运算数组合在一起（例如，每个 SHA-2 运算数由 4 个字组成）。然而，在其他情况下，这些运算数是单个值（例如，在 AES 轮指令中，每个运算数是 128 位块或轮密钥）。

我们将这些运算数视为一个或多个 _元素组_ 的向量，如 <<vector-element-groups>> 中定义。

每个操作元素组的向量密码指令都明确指定了它们的三个定义参数：EGW、EGS 和 EEW。

[%autowidth]
[%header,cols="4,4,4,4,4"]
|===
| 指令组
| 扩展
| EGW
| EEW
| EGS

| AES      | <<zvkned>>            | 128 | 32 | 4
| SHA256   | <<zvknh,zvknh[ab]>>  | 128 | 32 | 4
| SHA512   | <<zvknh,zvknhb>>     | 256 | 64 | 4
| GCM      | <<zvkg>>             | 128 | 32 | 4
| SM4      | <<zvksed>>           | 128 | 32 | 4
| SM3      | <<Zvksh>>            | 256 | 32 | 8
|===

[NOTE]
====
- 元素组宽度 (`EGW`) - 元素组中的总位数
- 有效元素宽度 (`EEW`) - 每个元素中的位数
- 元素组大小 (`EGS`) - 元素组中的元素数量
====

对于本规范中的所有向量密码指令，`EEW`=`SEW`。

[NOTE]
====
每个密码指令所需的 `SEW` 是根据实现目标算法时其他指令通常所需的 `SEW` 来选择的。
====

- *向量元素组* 是一个或多个元素组的向量。
- *标量元素组* 是单个元素组。

在 `VLEN` < `EGW` 的实现中，元素组可以通过使用 `LMUL`>1 跨寄存器形成。

[NOTE]
====
由于 *应用程序处理器的向量扩展* 要求 VLEN 最小为 128，因此大多数此类实现将需要 LMUL=2 来形成本规范中最大的元素组。

然而，VLEN 较小的实现（例如嵌入式设计）将需要较大的 `LMUL` 来形成必要的元素组。
重要的是要记住，这会减少可用寄存器组的数量，从而可能难以或不可能为预期的密码算法编写高效代码。

例如，VLEN=32 的实现需要设置 LMUL=8 来为 `SM3` 创建一个 256 位元素组。这意味着将只有 4 个寄存器组，其中 3 个将被单个 `SM3` 消息扩展指令消耗。
====

与所有向量指令一样，处理的元素数量由向量长度 `vl` 指定。操作的元素组数量为 `vl`/`EGS`。
同样，起始元素组为 `vstart`/`EGS`。
有关向量密码指令的 `vl` 和 `vstart` 限制，请参阅 <<crypto-vector-instruction-constraints>>。

// 如果此比率对于向量密码指令不是整数，则会引发非法指令异常。

// 由于 `vstart` 以元素表示，因此起始元素组为 `vstart`/`EGS`。
// 如果此比率对于向量密码指令不是整数，则会引发非法指令异常。

[[crypto-vector-instruction-constraints]]
==== 指令约束

RVV 1.0 指定的所有标准向量指令约束都适用于向量密码指令。
除了这些约束之外，还引入了一些额外的特定约束。

以下是特定向量密码指令的各种约束的快速参考。


vl 和 vstart 约束::
由于 `vl` 和 `vstart` 指的是元素，因此使用元素组的向量密码指令
(参见 <<crypto-vector-element-groups>>) 要求这些值是元素组大小 (`EGS`) 的整数倍。

- 违反 `vl` 或 `vstart` 要求的指令是 _保留的_。

[%autowidth]
[%header,cols="4,4"]
|===
| 指令
| EGS

| vaes*   | 4
| vsha2*  | 4
| vg*     | 4
| vsm3*   | 8
| vsm4*   | 4

|===

LMUL 约束::
对于元素组指令，`LMUL`*`VLEN` 必须始终至少与 `EGW` 一样大，否则会引发 _非法指令异常_，即使 `vl`=0。

[%autowidth]
[%header,cols="4,2,2"]
|===
| 指令
| SEW
| EGW

| vaes*   | 32 | 128
| vsha2*  | 32 | 128
| vsha2*  | 64 | 256
| vg*     | 32 | 128
| vsm3*   | 32 | 256
| vsm4*   | 32 | 128

|===


SEW 约束::
某些向量密码指令仅针对特定 `SEW` 定义。在这种情况下，所有其他 `SEW` 值都是 _保留的_。

[%autowidth]
[%header,cols="4,4"]
|===
| 指令
| 所需 SEW

| vaes*          | 32
| Zvknha: vsha2* | 32
| Zvknhb: vsha2* | 32 或 64
| vclmul[h]      | 64
| vg*            | 32
| vsm3*          | 32
| vsm4*          | 32


|===

向量/标量约束::
本规范定义了使用 *标量元素组* 的新向量/标量 (.vs) 指令。*标量元素组* 操作数的 `EMUL = ceil(EGW / VLEN)`。

[NOTE]
====
对于任何 VLEN ≥ EGW 的实现，标量元素组操作数不需要与 LMUL 对齐。
====

在本规范中定义的 `.vs` 指令中，`vs2` 保存一个 128 位标量元素组。
对于 VLEN ≥ 128 的实现，`vs2` 指的是单个寄存器。因此，`vd` 寄存器组不得与 `vs2` 寄存器重叠。
然而，在 VLEN < 128 的实现中，`vs2` 指的是由保存 128 位标量元素组所需的寄存器数量组成的寄存器组。在这种情况下，`vd` 寄存器组不得与此 `vs2` 寄存器组重叠。

[%autowidth]
[%header,cols="4,4,4"]
|===
| 指令
| 寄存器
| 不能重叠

| vaes*.vs      | vs2      | vd
| vsm4r.vs      | vs2      | vd
| vsha2c[hl]    | vs1, vs2 | vd
| vsha2ms       | vs1, vs2 | vd
| vsm3me        | vs2      | vd
| vsm3c         | vs2      | vd


|===

[[crypto-vector-scalar-instructions]]
==== 向量-标量指令

RISC-V 向量扩展定义了三种向量-标量操作编码，它们从 GPR 或 FP 寄存器获取标量操作数：

- OPIVX：标量 GPR _x_ 寄存器
- OPFVF：标量 FP _f_ 寄存器
- OPMVX：标量 GPR _x_ 寄存器

然而，向量扩展包括向量归约操作，这些操作也可以被视为向量-标量操作，因为标量操作数是从向量寄存器 `vs1` 的元素 0 提供的。向量操作数在向量寄存器组 `vs2` 中提供。
这些归约操作都在其助记符中使用 `.vs` 后缀。此外，归约操作都在目标寄存器 `vd` 的元素 0 中产生标量结果。

向量密码扩展定义了向量-标量指令，这些指令与这些向量归约操作类似，因为它们从向量寄存器获取标量操作数。然而，它们的不同之处在于它们从 `vs2` 获取标量元素组（参见 <<crypto-vector-element-groups>>），并且它们将 _向量_ 结果返回到 `vd`，`vd` 也是源向量操作数。
这些向量-标量密码指令也在其助记符中使用 `.vs` 后缀。

[NOTE]
====
我们选择使用 `vs2` 作为标量操作数，使用 `vd` 作为向量操作数，这样我们就可以使用 `vs1` 说明符作为这些指令的附加编码位。这使得这些指令具有更小的编码占用空间，为将来的其他指令留出更多空间。
====

这些指令使得单个密钥（在 `vs2` 中指定为标量元素组）能够应用于寄存器组 `vd` 的每个元素组。

[NOTE]
====
标量元素组在应用程序处理器中最多占用单个寄存器。然而，在 VLEN<128 的实现中，它们将占用 2 个（VLEN=64）或 4 个（VLEN=32）寄存器。
====

[NOTE]
====
通常使用相同的轮密钥并行执行多个 AES 加密轮次（例如在计数器模式中）。
这些向量-标量密码指令允许将轮密钥指定为标量元素组，而不必首先将公共密钥分散到整个向量组中。
====

[[crypto-vector-software-portability]]
==== 软件可移植性

以下包含一些指导原则，可使基于向量密码的代码能够移植到具有不同 `VLEN` 值的实现上。

应用程序处理器::
应用程序处理器预期遵循 V 扩展，因此将具有 `VLEN` ≥ 128。

由于大多数 _密码学特定_ 指令的 `EGW`=128，对于支持 `VLEN`=128 的实现，这些指令不需要做任何特殊处理。

然而，SHA-512 和 SM3 指令的 `EGW`=256。对于 `VLEN` = 128 的实现，需要将这些指令的 `LMUL` 加倍，以便在一对寄存器上创建 256 位元素。
使用这种 `LMUL` 加倍编写的代码不会影响 `VLEN` ≥ 256 实现返回的结果，因为 `vl` 控制处理多少个元素组。因此，我们建议实现 SHA-512 和 SM3 的库采用这种 `LMUL` 加倍，以确保软件可以在所有 `VLEN` ≥ 128 的实现上运行。

虽然对于 `VLEN` ≥ 256 的实现，这些指令的 `LMUL` 加倍是 _安全的_，但它可能不太优化，因为它会导致不必要的寄存器压力，并可能在某些微架构中产生性能损失。因此，我们建议除了为 SHA-512 和 SM3 提供可移植代码外，库还应该在 `VLEN` ≥ 256 时为这些指令包含更优化的代码。

[%autowidth]
[%header,cols="4,4,4,4"]
|===
| 算法
| 指令
| VLEN
| LMUL

| SHA-512 |  vsha2* | 64 | vl/2
| SM3     | vsm3*   | 32 | vl/4
|===

嵌入式处理器::

嵌入式处理器通常具有 `VLEN` < 128 的实现。这将需要用更大的 `LMUL` 值编写代码以形成元素组。

`.vs` 指令需要 `EGW`=128 的标量元素组。在 `VLEN` < 128 的实现中，这些标量元素组必须跨寄存器形成。这与向量指令中通常消耗单个寄存器一部分的大多数标量不同。

我们建议为 `VLEN`=32 和 `VLEN`=64 提供不同的代码，因为为 `VLEN`=32 编写的代码对于 `VLEN`=64 实现来说可能过于繁重。

[[crypto_vector_extensions]]
=== 扩展概述

本节介绍向量密码学指令集扩展规范中的所有扩展。

<<zvknh,Zvknhb>> 和 <<zvbc>> 向量密码扩展
--以及相应的复合扩展 <<Zvkn>>、<<Zvknc>>、<<Zvkng>> 和 <<Zvksc>>--
依赖于 Zve64x。

所有其他向量密码扩展都依赖于 `Zve32x`。

注意：如果支持 `Zve32x`，那么 `Zvkb` 或 `Zvbb` 提供对 8、16 和 32 位 EEW 的支持。如果支持 `Zve64x`，那么 `Zvkb` 或 `Zvbb` 还添加对 64 位 EEW 的支持。

本向量密码规范中定义的所有 _密码学特定_ 指令（即 <<zvkned>>、<<zvknh,Zvknh[ab]>>、<<Zvkg>>、<<Zvksed>> 和 <<zvksh>> 中的指令，但 _不包括_ <<zvbb>>、<<zvkb>> 或 <<zvbc>>）应按照
<<#crypto_scalar_instructions,RISC-V 标量密码学扩展规范>> 中定义的数据无关执行延迟执行。
重要的是要注意，向量密码指令独立于 `Zkt` 扩展的实现，不要求实现 `Zkt`。

本规范包括一个 <<Zvkt>> 扩展，当实现时，要求某些向量指令（包括 <<zvbb>>、<<zvkb>> 和 <<zvbc>>）以数据无关的执行延迟执行。

各个密码学扩展的检测使用统一的基于软件的 RISC-V 发现方法。

====
在撰写本文时，这些发现机制仍在开发中。

[[crypto-vector-software-portability]]
==== 软件可移植性
以下包含一些指导方针，可实现基于向量密码的代码
到具有不同 `VLEN` 值的实现的移植性

应用程序处理器::
应用程序处理器预计将遵循 V 扩展，因此 VLEN ≥ 128。



// [NOTE]
// ====
由于大多数 _密码学特定_ 指令的 `EGW`=128，因此这些指令无需特殊处理即可支持 VLEN=128 的实现。

然而，SHA-512 和 SM3 指令的 `EGW`=256。VLEN=128 的实现要求这些指令的 `LMUL` 加倍，以便在寄存器对中创建 256 位元素。
使用此 `LMUL` 加倍编写的代码不会影响 VLEN ≥ 256 的实现返回的结果，因为 `vl` 控制处理的元素组数量。因此，我们建议实现 SHA-512 和 SM3 的库采用此 `LMUL` 加倍，以确保软件可以在所有 VLEN ≥ 128 的实现上运行。

虽然这些指令的 `LMUL` 加倍对于 VLEN ≥ 256 的实现是 _安全_ 的，但它可能不是最优的，因为它会导致不必要的寄存器压力，并可能在某些微架构中产生性能损失。因此，我们建议除了为 SHA-512 和 SM3 提供可移植代码外，库还应在 VLEN ≥ 256 时包含这些指令的更优代码。
// ====

[%autowidth]
[%header,cols="4,4,4,4"]
|===
| 算法
| 指令
| VLEN
| LMUL

| SHA-512 |  vsha2* | 64 | vl/2
| SM3     | vsm3*   | 32 | vl/4
|===

// [NOTE]
// ====
// 我们建议所有应用程序处理器的库代码都应编写为可在任何 VLEN ≥ 128 的实现上运行。还鼓励此类库具有针对 VLEN ≥ 256 的实现优化的 SHA-512 和 SM3 代码版本。
// ====

嵌入式处理器::

嵌入式处理器通常具有 VLEN < 128 的实现。这将需要编写具有较大 `LMUL` 值的代码，以使元素组能够形成。

`.vs` 指令需要 `EGW`=128 的标量元素组。在 VLEN < 128 的实现中，这些标量元素组必然会在寄存器之间形成。这与向量指令中通常占用单个寄存器一部分的大多数标量不同。


// [NOTE]
// ====
我们建议为 VLEN=32 和 VLEN=64 提供不同的代码，因为为 VLEN=32 编写的代码对于 VLEN=64 的实现来说可能过于繁重。
// ====

[[zvkt,Zvkt]]
==== `Zvkt` - 向量数据无关执行延迟

Zvkt 扩展要求以下列表中的所有已实现指令都以数据无关的执行延迟执行，如 <<#crypto_scalar_instructions,RISC-V 标量密码学扩展规范>> 中定义。

数据无关执行延迟 (DIEL) 适用于指令的所有 _数据操作数_，即使那些不属于主体或不活动的也适用。然而，DIEL 不适用于其他值，例如 vl、vtype 和掩码（当用于控制掩码向量指令的执行时）。
此外，DIEL 不适用于指令编码中指定的常量值，例如零寄存器 (`x0`) 的使用，以及在指令的立即数形式中，立即数字段中的值（即 imm 和 uimm）。

在某些情况下——如下面列表中明确指定的——用作控制而不是数据的操作数免于 DIEL。

[NOTE]
====
DIEL 有助于防止侧信道时序攻击，这些攻击用于确定旨在保密的数值。此类值包括密码密钥、明文和部分加密文本。DIEL 无意于保守软件（以及其中包含的密码算法）的秘密，因为假定攻击者已经知道这些。这就是 DIEL 不适用于嵌入在指令编码中的常量的原因。

重要的是，不在主体中或被屏蔽的元素的值不影响指令的执行延迟。有时此类元素包含也需要保密的数据。
====

描述::

//  if( ((vl%EGS)<>0) | ((vstart%EGS)<>0) | (LMUL*VLEN < EGW))  then {

操作::
[source,sail]
--
function clause execute (VAESDF(vs2, vd, suffix)) = {
  if(LMUL*VLEN < EGW)  then {
    handle_illegal();  // 非法指令异常
    RETIRE_FAIL
  } else {

  eg_len = (vl/EGS)
  eg_start = (vstart/EGS)

  foreach (i from eg_start to eg_len-1) {
    let keyelem = if suffix == "vv" then i else 0;
    let state : bits(128) = get_velem(vd,  EGW=128, i);
    let rkey  : bits(128) = get_velem(vs2, EGW=128, keyelem);
    let sr    : bits(128) = aes_shift_rows_inv(state);
    let sb    : bits(128) = aes_subbytes_inv(sr);
    let ark   : bits(128) = sb ^ rkey;
    set_velem(vd, EGW=128, i, ark);
  }
  RETIRE_SUCCESS
  }
}

=== 向量密码学指令总结

向量密码学扩展为现代密码学算法提供了高效的硬件加速支持：

1. **AES支持**: 包括加密、解密、密钥扩展的完整指令集
2. **SHA-2支持**: SHA-256和SHA-512的消息调度和压缩指令
3. **中国密码学标准**: SM3和SM4算法的专用指令
4. **高性能**: 所有指令都设计为恒定时间执行，防止侧信道攻击
5. **灵活配置**: 支持不同的元素宽度和向量长度配置

这些指令极大地提高了密码学操作的性能，同时保持了安全性。

=== 使用指南和最佳实践

==== 性能优化建议

**向量长度配置**：
- 对于 AES、SHA-256、GCM、SM4：推荐 VLEN ≥ 128
- 对于 SHA-512、SM3：推荐 VLEN ≥ 256
- 在较小的 VLEN 上使用适当的 LMUL 值

**指令选择**：
- 优先使用专用的密码学指令而非通用指令序列
- 合理利用向量-标量指令减少密钥复制开销
- 考虑使用复合扩展(Zvkn、Zvks等)简化软件支持

==== 安全实现要求

**侧信道防护**：
- 所有密码学专用指令保证恒定时间执行
- 避免在关键路径中使用数据相关的分支
- 正确处理掩码和尾部元素

**密钥管理**：
- 密钥材料应存储在向量寄存器中最小化内存访问
- 使用适当的清零序列清理寄存器
- 注意向量-标量指令的密钥布局要求

=== 实现注意事项

1. **恒定时间执行**: 所有密码学指令必须实现为数据无关的执行时间
2. **元素组大小**: 大多数密码学指令使用固定的元素组大小（如AES为128位）
3. **寄存器重叠限制**: 某些指令禁止源和目标寄存器重叠
4. **SEW限制**: 大多数指令要求特定的SEW值（通常为32位）

=== 实现注意事项总结

1. **数据无关执行时间**：所有密码学指令必须以恒定时间执行，不依赖于操作数的值。

2. **元素组操作**：大多数密码学指令操作固定大小的元素组（如AES的128位）。

3. **寄存器对齐**：某些指令要求向量寄存器组正确对齐。

4. **SEW限制**：大多数密码学指令要求特定的SEW值（通常为32位）。

5. **掩码处理**：密码学指令的掩码行为需要特别注意，以避免信息泄露。
