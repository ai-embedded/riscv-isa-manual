== 介绍

RISC-V（发音为"risk-five"）是一种新的指令集架构（ISA），最初设计用于支持计算机架构研究和教育，但我们现在也希望它能成为工业实现的标准自由开放架构。我们在定义 RISC-V 时的目标包括：

* 一个完全 _开放_ 的 ISA，可供学术界和工业界自由使用。
* 一个适合直接本地硬件实现的 _真实_ ISA，而不仅仅是仿真或二进制转换。
* 一个避免为特定微架构风格（例如，微编码、顺序、解耦、乱序）或实现技术（例如，全定制、ASIC、FPGA）"过度架构"的 ISA，但允许在其中任何一种中高效实现。
* 一个分离为 _小型_ 基本整数 ISA 的 ISA，可单独用作定制加速器的基础或用于教育目的，以及可选的标准扩展，以支持通用软件开发。
* 支持修订的 2008 IEEE-754 浮点标准。cite:[ieee754-2008]
* 支持广泛的 ISA 扩展和专门变体的 ISA。
* 应用程序、操作系统内核和硬件实现的 32 位和 64 位地址空间变体。
* 支持高度并行多核或众核实现的 ISA，包括异构多处理器。
* 可选的 _变长指令_ 既可以扩展可用的指令编码空间，也可以支持可选的 _密集指令编码_，以提高性能、静态代码大小和能效。
* 完全可虚拟化的 ISA，以简化管理程序开发。
* 简化新特权架构设计实验的 ISA。

[NOTE]
====
选择 RISC-V 这个名称是为了代表来自 UC Berkeley 的第五个主要 RISC ISA 设计（RISC-I cite:[riscI-isca1981]、RISC-II cite:[Katevenis:1983]、SOAR cite:[Ungar:1984] 和 SPUR cite:[spur-jsscc1989] 是前四个）。我们还巧妙地使用罗马数字"V"来表示"变化"和"向量"，因为对一系列架构研究的支持，包括各种数据并行加速器，是 ISA 设计的明确目标。
====
(((ISA，定义)))
RISC-V ISA 的定义尽可能避免实现细节（尽管包含了对实现驱动决策的评论），应该被理解为各种实现的软件可见接口，而不是特定硬件工件的设计。RISC-V 手册分为两卷。本卷涵盖基本 _非特权_ 指令的设计，包括可选的非特权 ISA 扩展。非特权指令是那些在所有特权架构的所有特权模式中通常可用的指令，尽管行为可能因特权模式和特权架构而异。第二卷提供第一个（"经典"）特权架构的设计。手册使用 IEC 80000-13:2008 约定，字节为 8 位。

[NOTE]
====
在非特权 ISA 设计中，我们试图消除对特定微架构特性（例如缓存行大小）或特权架构细节（例如页面转换）的任何依赖。这既是为了简单起见，也是为了最大限度地提高替代微架构或替代特权架构的灵活性。
====

=== RISC-V 硬件平台术语

RISC-V 硬件平台可以包含一个或多个 RISC-V 兼容的处理核心以及其他非 RISC-V 兼容的核心、固定功能加速器、各种物理内存结构、I/O 设备和互连结构，以允许组件进行通信。
(((核心，组件)))

如果一个组件包含一个独立的指令获取单元，则称其为 _核心_。一个 RISC-V 兼容的核心可能通过多线程支持多个 RISC-V 兼容的硬件线程，或 _hart_。
(((核心，扩展，协处理器)))

一个 RISC-V 核心可能具有额外的专用指令集扩展或附加的 _协处理器_。我们使用术语 _协处理器_ 来指代连接到 RISC-V 核心的单元，主要由 RISC-V 指令流进行排序，但包含额外的架构状态和指令集扩展，并且可能相对于主 RISC-V 指令流具有一定的有限自主性。

我们使用术语 _加速器_ 来指代不可编程的固定功能单元或可以自主操作但专门用于某些任务的核心。在 RISC-V 系统中，我们预计许多可编程加速器将是基于 RISC-V 的核心，具有专用指令集扩展和/或定制协处理器。RISC-V 加速器的一个重要类别是 I/O 加速器，它们将 I/O 处理任务从主应用程序核心卸载。
(((核心，加速器)))

RISC-V 硬件平台的系统级组织可以从单核微控制器到数千个共享内存众核服务器节点的集群。即使是小型片上系统也可能被构建为多计算机和/或多处理器的层次结构，以模块化开发工作或在子系统之间提供安全隔离。
(((核心，集群，多处理器)))

=== RISC-V 软件执行环境和 Hart

RISC-V 程序的行为取决于其运行的执行环境。RISC-V 执行环境接口 (EEI) 定义了程序的初始状态、环境中 hart 的数量和类型（包括 hart 支持的特权模式）、内存和 I/O 区域的可访问性和属性、每个 hart 上执行的所有合法指令的行为（即 ISA 是 EEI 的一个组成部分），以及执行期间引发的任何中断或异常（包括环境调用）的处理。EEI 的示例包括 Linux 应用程序二进制接口 (ABI) 或 RISC-V supervisor 二进制接口 (SBI)。RISC-V 执行环境的实现可以是纯硬件、纯软件或硬件和软件的组合。例如，操作码陷阱和软件仿真可用于实现硬件中未提供的功能。执行环境实现的示例包括：

* "裸机"硬件平台，其中 hart 由物理处理器线程直接实现，指令可以完全访问物理地址空间。硬件平台定义了一个在上电复位时开始的执行环境。
* RISC-V 操作系统，通过将用户级 hart 多路复用到可用的物理处理器线程并控制通过虚拟内存访问内存来提供多个用户级执行环境。
* RISC-V 管理程序，为客户操作系统提供多个 supervisor 级执行环境。
* RISC-V 模拟器，例如 Spike、QEMU 或 rv8，它们在底层 x86 系统上模拟 RISC-V hart，并且可以提供用户级或 supervisor 级执行环境。

[NOTE]
====
裸硬件平台可以被视为定义了一个 EEI，其中可访问的 hart、内存和其他设备填充了环境，初始状态是上电复位时的状态。通常，大多数软件都设计为使用更抽象的硬件接口，因为更抽象的 EEI 提供了跨不同硬件平台的更大可移植性。EEI 通常是分层的，其中一个更高级别的 EEI 使用另一个更低级别的 EEI。
====
(((hart，执行环境)))
从在给定执行环境中运行的软件的角度来看，hart 是一种资源，它在该执行环境中自主获取和执行 RISC-V 指令。在这方面，hart 的行为类似于硬件线程资源，即使它由执行环境在真实硬件上进行时间多路复用。一些 EEI 支持创建和销毁额外的 hart，例如，通过环境调用来 fork 新的 hart。

执行环境负责确保其每个 hart 的最终前进。对于给定的 hart，当 hart 正在执行明确等待事件的机制时（例如本规范第二卷中定义的等待中断指令），该责任暂停；如果 hart 终止，则该责任终止。以下事件构成前进：

* 指令的退役。
* 陷阱，如 <<trap-defn>> 中定义。
* 扩展定义的任何其他构成前进的事件。

[NOTE]
====
hart 这个术语是在 Lithe cite:[lithe-pan-hotpar09] 和 cite:[lithe-pan-pldi10] 的工作中引入的，旨在提供一个术语来表示抽象执行资源，而不是软件线程编程抽象。

硬件线程 (hart) 和软件线程上下文之间的重要区别在于，在执行环境内部运行的软件不负责使其每个 hart 前进；这是外部执行环境的责任。因此，环境的 hart 从执行环境内部软件的角度来看，就像硬件线程一样运行。

执行环境实现可以将一组客户 hart 时间多路复用到较少的主机 hart 上，这些主机 hart 由其自身的执行环境提供，但必须以客户 hart 像独立的硬件线程一样运行的方式进行。特别是，如果客户 hart 数量多于主机 hart 数量，则执行环境必须能够抢占客户 hart，并且不得无限期地等待客户 hart 上的客户软件"让出"客户 hart 的控制权。
====

=== RISC-V ISA 概述

RISC-V ISA 被定义为基本整数 ISA，任何实现中都必须存在，以及基本 ISA 的可选扩展。基本整数 ISA 与早期 RISC 处理器非常相似，只是没有分支延迟槽，并支持可选的可变长度指令编码。基本 ISA 被仔细限制为最小指令集，足以提供编译器、汇编器、链接器和操作系统（具有附加特权操作）的合理目标，因此提供了一个方便的 ISA 和软件工具链"骨架"，在此基础上可以构建更定制的处理器 ISA。

虽然基本 ISA 本身对许多用途都很有用，但其主要设计目的是成为附加标准和自定义扩展的基础。例如，我们希望对科学计算有用的 ISA 还将包括用于单精度和双精度浮点的标准扩展，可能还有一些针对科学计算中常见的快速三角函数计算的自定义扩展。

将架构描述为强制性基本 ISA 加上可选扩展的方法，将整体架构空间分解为一个可重用的基础（基本 ISA）加上可重用的功能块（标准扩展）和定制功能块（非标准扩展）。这种方法旨在最大限度地提高每个块的重用性，也可以提供单个 ISA 规范很难实现的丰富多样性，同时仍然提供兼容性，其中子集的兼容性明确定义。

[NOTE]
====
显式分离基本 ISA 的主要优势在于，每个基本 ISA 都可以针对其需求进行优化，而不需要支持其他基本 ISA 所需的所有操作。例如，RV64I 可以省略仅为应对 RV32I 中较窄寄存器而需要的指令和 CSR。RV32I 变体可以使用原本为仅宽地址空间变体所需的指令保留的编码空间。

不将设计视为单个 ISA 的主要缺点是，它使在另一个基本 ISA 上模拟一个基本 ISA 所需的硬件复杂化（例如，在 RV64I 上模拟 RV32I）。然而，寻址差异和非法指令陷阱通常意味着即使具有完整的超集指令编码，在任何情况下都需要某种模式切换，而且不同的 RISC-V 基本 ISA 足够相似，支持多个版本的成本相对较低。尽管有些人建议严格的超集设计将允许传统的 32 位库与 64 位代码链接，但由于软件调用约定和系统调用接口的差异，即使具有兼容的编码，这在实践中也是不切实际的。

RISC-V 特权架构在 `misa` 中提供字段，以控制每个级别的非特权 ISA，以支持在相同硬件上模拟不同的基本 ISA。我们注意到，较新的 SPARC 和 MIPS ISA 修订版本已经弃用了在 64 位系统上不变地运行 32 位代码的支持。

一个相关的问题是为什么在 RV32I (ADD) 和 RV64I (ADDW) 中 32 位加法有不同的编码？ADDW 操作码可以用于 RV32I 中的 32 位加法，ADDD 用于 RV64I 中的 64 位加法，而不是现有的设计，它在 RV32I 中为 32 位加法使用相同的操作码 ADD，在 RV64I 中为 64 位加法使用相同的操作码 ADD，并为 RV64I 中的 32 位加法使用不同的操作码 ADDW。这也将与 RV32I 和 RV64I 中 32 位加载使用相同的 LW 操作码更一致。RISC-V ISA 的最初版本确实有这种替代设计的变体，但 RISC-V 设计在 2011 年 1 月更改为当前选择。我们的重点是在 64 位 ISA 中支持 32 位整数，而不是提供与 32 位 ISA 的兼容性，动机是消除由于 RV32I 中不是所有操作码都有 *W 后缀（例如，ADDW，但 AND 不是 ANDW）而产生的不对称性。事后看来，这可能不是很有道理，这是同时设计两个 ISA 而不是稍后添加一个坐在另一个之上的结果，也是由于我们认为必须将平台要求折叠到 ISA 规范中，这意味着所有 RV32I 指令都需要在 RV64I 中。现在更改编码已经太晚了，但由于上述原因，这也没有什么实际后果。

已经注意到我们可以启用 *W 变体作为 RV32I 系统的扩展，以在 RV64I 和未来的 RV32 变体之间提供通用编码。
====

为每个架构关注点提供单独的基本 ISA 并允许在扩展中混合和匹配，应该提供比尝试在单个 ISA 中提供大量内置选项更好的性能和能效。关注点的分离还有助于现代超标量实现，其中不同的指令类型可以在不同的执行单元中执行，而无需在指令集中为每种组合提供单独的接口。

我们打算保持基本 ISA 和每个标准扩展常数随时间变化，而是将新指令分层为进一步的可选扩展。例如，基本整数 ISA 将继续作为完全支持的独立 ISA，无论任何后续扩展如何。

=== 内存

RISC-V hart 具有单个字节可寻址的地址空间，包含 latexmath:[$2^{\text{XLEN}}$] 字节，用于所有内存访问。内存的 _字_ 定义为 32 位（4 字节）。相应地，_半字_ 是 16 位（2 字节），_双字_ 是 64 位（8 字节），_四字_ 是 128 位（16 字节）。内存地址空间是循环的，因此地址 latexmath:[$2^{\text{XLEN}}-1$] 处的字节与地址零处的字节相邻。因此，硬件执行的内存地址计算忽略溢出，而是围绕 latexmath:[$2^{\text{XLEN}}$] 取模回绕。

执行环境确定硬件资源到 hart 地址空间的映射。hart 地址空间的不同地址范围可能（1）包含 _主内存_，或（2）包含一个或多个 _I/O 设备_。I/O 设备的读写可能具有可见的副作用，但对主内存的访问不能。空闲地址范围不是单独的类别，但可以表示为不可访问的主内存或 I/O 区域。尽管执行环境可能将 hart 地址空间中的所有内容都称为 I/O 设备，但通常期望将某些部分指定为主内存。

当 RISC-V 平台具有多个 hart 时，任何两个 hart 的地址空间可能完全相同，或完全不同，或可能部分不同但共享某些资源子集，映射到相同或不同的地址范围。

[NOTE]
====
对于纯"裸机"环境，所有 hart 可能看到相同的地址空间，完全通过物理地址访问。然而，当执行环境包括使用地址转换的操作系统时，通常为每个 hart 提供很大程度上或完全属于自己的虚拟地址空间。
====
(((内存访问，隐式和显式)))

执行每个 RISC-V 机器指令都需要一次或多次内存访问，细分为 _隐式_ 和 _显式_ 访问。对于执行的每条指令，执行 _隐式_ 内存读取（指令获取）以获得要执行的编码指令。许多 RISC-V 指令除了指令获取之外不执行进一步的内存访问。特定的加载和存储指令在由指令确定的地址处执行内存的 _显式_ 读取或写入。执行环境可能规定指令执行除了为非特权 ISA 记录的那些之外还执行其他 _隐式_ 内存访问（例如实现地址转换）。

执行环境确定地址空间的哪些部分可访问用于每种内存访问。例如，可以为指令获取隐式读取的位置集合可能与可以由加载指令显式读取的位置集合有重叠或没有重叠；可以由存储指令显式写入的位置集合可能只是可以读取的位置的子集。通常，如果指令尝试在不可访问的地址访问内存，则为该指令引发异常。

除非另有规定，否则不引发异常且没有副作用的隐式读取可能任意早地和推测性地发生，甚至在机器可能证明需要读取之前。例如，有效的实现可能尝试在最早的机会读取所有主内存，缓存尽可能多的可获取（可执行）字节以供以后的指令获取，并避免再次为指令获取读取主内存。为了确保某些隐式读取仅在对相同内存位置的写入之后排序，软件必须执行为此目的定义的特定栅栏或缓存控制指令（例如 <<zifencei>> 中定义的 FENCE.I 指令）。

hart 执行的内存访问（隐式或显式）可能看起来以不同的顺序发生，正如另一个 hart 或可以访问相同内存的任何其他代理所感知的那样。然而，这种内存访问的感知重新排序总是受到适用的内存一致性模型的约束。RISC-V 的默认内存一致性模型是 RISC-V 弱内存排序（RVWMO），在 <<memorymodel>> 和附录中定义。可选地，实现可以采用更强的全存储排序模型，如 <<ztso>> 中定义的。执行环境还可以添加约束，进一步限制内存访问的感知重新排序。由于 RVWMO 模型是任何 RISC-V 实现允许的最弱模型，为此模型编写的软件与所有 RISC-V 实现的实际内存一致性规则兼容。与隐式读取一样，软件必须执行栅栏或缓存控制指令，以确保超出假定的内存一致性模型和执行环境要求的内存访问的特定排序。

=== 基本指令长度编码

基本 RISC-V ISA 具有固定长度的 32 位指令，必须在 32 位边界上自然对齐。然而，标准 RISC-V 编码方案设计为支持具有变长指令的 ISA 扩展。变长指令扩展的标准编码使用可变数量的 16 位指令 _包_。指令编码的最低有效位用于识别包含指令的包数。

[NOTE]
====
基本 32 位指令格式最初由 UC Berkeley 的 Guy Lemieux 提出。
====

包含指令的 16 位包数由其前 N 位确定，其中 N ≤ 4。图 <<inst-length-encoding>> 显示了标准的 RISC-V 指令长度编码约定。

include::images/bytefield/inst-length-encoding.edn[]

给定指令的基址是指令第一个 16 位包的地址。指令的地址对齐约束是基址必须是包数的两倍的倍数。例如，4 字节指令必须在 4 字节边界上对齐。

潜在的指令编码分为三类：正常、保留和非标准。正常编码保证永远不会与当前或未来的标准扩展冲突，并且由于编码空间限制，被控制。保留编码由标准为未来使用保留，目前会导致非法指令陷阱，但可能在未来标准扩展中重新定义。在本规范中，我们对保留编码使用术语 RESERVED。非标准编码永远不会被分配给标准扩展，并且可供各种非标准扩展使用。在本规范中，我们对非标准编码使用术语 CUSTOM。

我们相信 RISC-V 的标准编码提供了足够的编码空间给可预见的标准扩展使用，同时也为定制扩展留下了大量编码空间。然而，编码空间分配和冲突的问题可能很复杂，特别是对于部分使用 RESERVED 或 CUSTOM 编码空间的实现。

=== 异常、陷阱和中断

我们将 _异常_ 定义为在执行指令时检测到的异常条件，可能导致在当前执行流中发生意外的控制转移。我们使用术语 _陷阱_ 来指代任何类型向（较高特权级别的）陷阱处理程序的控制转移，并将陷阱分为两类。包含异常的陷阱是 _同步的_，因为它们是从特定指令引起的，而从外部事件引起的其他陷阱是 _异步的_。我们对异步陷阱使用术语 _中断_。

[[trap-defn]]
我们注意到，对于 hart 来说，_陷阱_ 可以定义为控制转移到执行环境的陷阱处理程序。

由于本文档描述的是非特权指令，因此很少提及陷阱。处理包含陷阱的架构方法在特权架构手册中定义，以及支持更丰富 EEI 的其他功能。此处记录了仅用于引起请求陷阱的非特权指令。不可见陷阱，就其性质而言，不在本文档的范围之内。此处未定义且未通过其他方式定义的指令编码可能会导致致命陷阱。

=== 未指定行为和值

架构充分描述了实现必须做什么以及它们可能做什么的任何约束。在架构有意不约束实现的情况下，明确使用术语 UNSPECIFIED。
(((未指定，行为)))
(((未指定，值)))

术语 UNSPECIFIED 指的是有意不受约束的行为或值。这些行为或值的定义开放给扩展、平台标准或实现。扩展、平台标准或实现文档可以提供规范性内容，以进一步约束基本架构定义为 UNSPECIFIED 的情况。

与基本架构一样，扩展应充分描述允许的行为和值，并对有意不受约束的情况使用术语 UNSPECIFIED。这些情况可以由其他扩展、平台标准或实现约束或定义。

[NOTE]
====
在非特权 ISA 设计中，我们试图消除对特定微架构特性（例如缓存行大小）或特权架构细节（例如页面转换）的任何依赖。这既是为了简单起见，也是为了最大限度地提高替代微架构或替代特权架构的灵活性。
