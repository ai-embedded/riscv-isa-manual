[[supervisor]]
== Supervisor 级 ISA，版本 1.13

本章描述了 RISC-V supervisor 级架构，它包含一个与各种 supervisor 级地址转换和保护方案一起使用的通用核心。

[NOTE]
====
Supervisor 模式在与底层物理硬件（例如物理内存和设备中断）的交互方面受到严格限制，以支持干净的虚拟化。本着这种精神，某些 supervisor 级设施（包括定时器和处理器间中断请求）由实现特定机制提供。其他系统则通过其他实现定义的机制直接提供这些设施。
====

=== Supervisor CSR

为 supervisor 提供了许多 CSR。

[NOTE]
====
Supervisor 应该只查看对 supervisor 级操作系统可见的 CSR 状态。特别是，在 supervisor 可访问的 CSR 中，没有关于更高特权级别（机器级别或其他）存在（或不存在）的信息。

许多 supervisor CSR 是等效机器模式 CSR 的子集，应首先阅读机器模式章节以帮助理解 supervisor 级 CSR 描述。
====

SPP 位指示 hart 在进入 supervisor 模式之前执行的特权级别。当发生陷阱时，如果陷阱源自用户模式，则 SPP 设置为 0，否则设置为 1。当执行 SRET 指令（参见 <<otherpriv>>）从陷阱处理程序返回时，如果 SPP 位为 0，则特权级别设置为用户模式，如果 SPP 位为 1，则设置为 supervisor 模式；然后 SPP 设置为 0。

SIE 位启用或禁用 supervisor 模式下的所有中断。当 SIE 清除时，在 supervisor 模式下不接受中断。当 hart 在用户模式下运行时，SIE 中的值被忽略，并且 supervisor 级中断被启用。supervisor 可以使用 `sie` CSR 禁用单个中断源。

SPIE 位指示在陷入 supervisor 模式之前 supervisor 中断是否已启用。当陷阱进入 supervisor 模式时，SPIE 设置为 SIE，SIE 设置为 0。当执行 SRET 指令时，SIE 设置为 SPIE，然后 SPIE 设置为 1。

`sstatus` 寄存器是 `mstatus` 寄存器的子集。

[NOTE]
====
在直接实现中，读取或写入 `sstatus` 中的任何字段等效于读取或写入 `mstatus` 中同名字段。
====

===== `sstatus` 寄存器中的基本 ISA 控制

UXL 字段控制 U 模式的 XLEN 值，称为 _UXLEN_，它可能与 S 模式的 XLEN 值（称为 _SXLEN_）不同。UXL 的编码与 `misa` 的 MXL 字段相同，如 <<misabase>> 所示。

当 SXLEN=32 时，UXL 字段不存在，UXLEN=32。当 SXLEN=64 时，它是一个 *WARL* 字段，编码 UXLEN 的当前值。特别是，实现可以使 UXL 成为一个只读字段，其值始终确保 UXLEN=SXLEN。

如果 UXLEN≠SXLEN，则在较窄模式下执行的指令必须忽略高于配置 XLEN 的源寄存器操作数位，并且必须符号扩展结果以填充目标寄存器中支持的最宽 XLEN。

如果 UXLEN latexmath:[$<$] SXLEN，用户模式指令获取地址以及加载和存储有效地址将取模 latexmath:[$2^{\text{UXLEN}}$]。例如，当 UXLEN=32 且 SXLEN=64 时，用户模式内存访问引用地址空间的最低 4 GiB。

一些 HINT 指令编码为整数计算指令，它们用其当前值覆盖其目标寄存器，例如 `c.addi x8, 0`。
当此类 HINT 在 XLEN < SXLEN 且目标寄存器的 SXLEN..XLEN 位不全等于位 XLEN-1 时执行时，目标寄存器的 SXLEN..XLEN 位是保持不变还是被 XLEN-1 位的副本覆盖是实现定义的。

NOTE: 此定义允许实现省略某些 HINT 的寄存器回写，同时允许它们以与其他整数计算指令相同的方式执行其他 HINT。
实现选择仅对 SXLEN > UXLEN 的 S 模式可见；对 U 模式不可见。

[[sum]]
===== `sstatus` 寄存器中的内存特权

MXR（使可执行可读）位修改加载访问虚拟内存的特权。当 MXR=0 时，只有标记为可读（<<sv32pte>> 中 R=1）的页面加载才会成功。当 MXR=1 时，标记为可读或可执行（R=1 或 X=1）的页面加载都会成功。当未启用基于页的虚拟内存时，MXR 无效。

SUM（允许 Supervisor 用户内存访问）位修改 S 模式加载和存储访问虚拟内存的特权。当 SUM=0 时，S 模式内存访问 U 模式可访问的页面（<<sv32pte>> 中 U=1）将导致故障。当 SUM=1 时，允许这些访问。当未启用基于页的虚拟内存时，SUM 无效，在 U 模式下执行时也无效。请注意，无论 SUM 如何，supervisor 都不能在 U=1 的页面上执行代码。

SUM 在 `satp`.MODE 为只读 0 时为只读 0。

[NOTE]
====
SUM 机制可防止 supervisor 软件无意中访问用户内存。操作系统可以在 SUM 清除的情况下执行大部分代码；少数应访问用户内存的代码段可以暂时设置 SUM。

SUM 机制不赋予 S 模式软件在用户代码页面中执行指令的权限。在 supervisor 上下文中从用户内存执行的合法用例通常很少见，在 POSIX 环境中则不存在。然而，如果 supervisor 漏洞利用代码可以存储在攻击者选择的虚拟地址处的用户缓冲区中，则导致任意代码执行的 supervisor 错误更容易被利用。

一些非 POSIX 单地址空间操作系统确实允许某些特权软件在 supervisor 模式下部分执行，而大多数程序在用户模式下运行，所有这些都在共享地址空间中。此用例可以通过将物理代码页面映射到具有不同权限的多个虚拟地址来实现，可能借助指令页故障处理程序来指导 supervisor 软件使用替代映射。
====

===== `sstatus` 寄存器中的字节序控制

UBE 位是一个 *WARL* 字段，控制从 U 模式进行的显式内存访问的字节序，这可能与 S 模式下的内存访问字节序不同。实现可以使 UBE 成为一个只读字段，该字段始终指定与 S 模式相同的字节序。

UBE 控制从 U 模式进行的显式加载和存储内存访问是小端序 (UBE=0) 还是大端序 (UBE=1)。

UBE 对指令获取没有影响，指令获取是始终为小端序的 _隐式_ 内存访问。

对于对 supervisor 级内存管理数据结构（例如页表）的 _隐式_ 访问，S 模式字节序始终适用，并且 UBE 被忽略。

[NOTE]
====
标准 RISC-V ABI 预计将是纯小端或纯大端，不兼容混合字节序。
尽管如此，字节序控制的定义允许一个字节序的操作系统执行相反字节序的用户模式程序。
====

===== `sstatus` 寄存器中先前的预期着陆垫 (ELP) 状态

对 Zicfilp 添加的 `SPELP` 字段的访问，当 `V=0` 时访问 `mstatus` 的同名字段，当 `V=1` 时访问 `vsstatus` 的同名字段。

[[supv-double-trap]]
===== `sstatus` 寄存器中的双重陷阱控制

S-mode-disable-trap (`SDT`) 位是 Ssdbltrp 扩展引入的 WARL 字段，用于解决低于 M 模式的特权模式下的双重陷阱（参见 <<machine-double-trap>>）。

当 `SDT` 位通过显式 CSR 写入设置为 1 时，`SIE`（Supervisor 中断使能）位清除为 0。无论同一写入是否写入 `SIE` 位，此清除都会发生。`SIE` 位只能通过显式 CSR 写入设置为 1，如果 `SDT` 位正在通过同一写入设置为 0 或已为 0。

当陷阱将进入 S 模式时，如果 `SDT` 位当前为 0，则将其设置为 1，并且陷阱按预期传递。但是，如果 `SDT` 已设置为 1，则这是一个 _意外陷阱_。发生 _意外陷阱_ 时，双重陷阱异常陷阱将传递到 M 模式。为了传递此陷阱，hart 写入寄存器（除了 `mcause` 和 `mtval2`），其信息与 _意外陷阱_ 如果进入 M 模式将写入的信息相同。然后 `mtval2` 寄存器设置为 _意外陷阱_ 将写入 `mcause` 寄存器的值。`mcause` 寄存器设置为 16，即双重陷阱异常代码。

SRET 指令将 `SDT` 位设置为 0。

[NOTE]
====
陷阱处理程序在保存了恢复陷阱所需的 `scause`、`sepc` 和 `stval` 等状态并可重入后，应清除 `SDT` 位。

通过 SRET 复位 `SDT` 使陷阱处理程序能够检测在尾部阶段可能发生的双重陷阱，在该阶段它恢复关键状态以从陷阱返回。

此规范的结果是，如果关键错误条件是由客户机页故障引起的，则当双重陷阱传递到 M 模式时，`mtval2` 中将无法获得 GPA。如果 HS 模式在 `SDT` 为 1 且指令引发客户机页故障时调用 hypervisor 虚拟机加载或存储指令，则会出现此情况。在此陷阱处理阶段使用此类指令并不常见。然而，不记录 GPA 被认为是良性的，因为如果需要，仍然可以通过遍历页表的过程获得它——尽管需要额外的努力。

对于源自 VS 模式的双重陷阱，M 模式应通过将陷阱更新的 M 模式 CSR 值复制到 HS 模式 CSR，并使用 `MRET` 在 `stvec` 中的地址处恢复执行，从而将异常重定向到 HS 模式。

Supervisor 软件事件 (SSE) 是 SBI 的扩展，它提供了一种机制，用于 supervisor 软件注册和处理来自 SBI 实现（例如固件或 hypervisor）的系统事件。在发生双重陷阱时，HS 模式和 M 模式可以利用 SSE 机制分别调用 VS 模式或 S/HS 模式中的关键错误处理程序。此外，SSE 协议的实现可以被视为一种可选措施，以帮助从此类关键错误中恢复。
====

==== Supervisor 陷阱向量基地址 (`stvec`) 寄存器

`stvec` 寄存器是一个 SXLEN 位读/写寄存器，它保存陷阱向量配置，由向量基地址 (BASE) 和向量模式 (MODE) 组成。

.Supervisor 陷阱向量基地址 (`stvec`) 寄存器。
include::images/bytefield/stvec.edn[]

`stvec` 中的 BASE 字段是一个字段，它可以保存任何有效的虚拟或物理地址，但受以下对齐约束：地址必须是 4 字节对齐的，并且除 Direct 之外的 MODE 设置可能对 BASE 字段中的值施加额外的对齐约束。
请注意，CSR 仅包含地址 BASE 的 XLEN-1 到 2 位。
当用作地址时，低两位填充零以获得一个始终对齐到 4 字节边界的 XLEN 位地址。

==== Supervisor 中断 (`sip` 和 `sie`) 寄存器

`sip` 寄存器是一个 SXLEN 位读/写寄存器，包含待处理中断的信息，而 `sie` 是相应的 SXLEN 位读/写寄存器，包含中断使能位。
中断原因号 _i_（如 CSR `scause`，<<scause>> 中报告）对应于 `sip` 和 `sie` 中的位 _i_。位 15:0 仅分配给标准中断原因，而位 16 及以上指定用于平台使用。

.Supervisor 中断待处理 (`sip`) 寄存器。
include::images/bytefield/sip.edn[]

.Supervisor 中断使能 (`sie`) 寄存器。
include::images/bytefield/sie.edn[]

当中断 _i_ 满足以下两个条件时，它将陷阱到 S 模式：(a) 当前特权模式是 S 且 `sstatus` 寄存器中的 SIE 位已设置，或者当前特权模式的特权低于 S 模式；(b) `sip` 和 `sie` 中位 _i_ 都已设置。

这些中断陷阱发生的条件必须在中断变为或停止待处理在 `sip` 中时，以及在执行 SRET 指令或显式写入这些中断陷阱条件明确依赖的 CSR（包括 `sip`、`sie` 和 `sstatus`）之后立即评估。

中断到 S 模式优先于任何较低特权模式的中断。

`sip` 寄存器中的每个单独位可以是可写或只读。当 `sip` 中位 _i_ 可写时，可以通过将此位写入 0 来清除待处理中断 _i_。如果中断 _i_ 可以变为待处理，但 `sip` 中位 _i_ 是只读的，则实现必须提供其他机制来清除待处理中断（可能涉及调用执行环境）。

如果相应的中断可以变为待处理，则 `sie` 中的位必须是可写的。`sie` 中不可写的位是只读零。

`sip` 和 `sie` 寄存器的标准部分（位 15:0）的格式分别如 <<sipreg-standard>> 和 <<siereg-standard>> 所示。

`sip`.SEIP 和 `sie`.SEIE 位是 supervisor 级外部中断的中断待处理和中断使能位。如果实现，SEIP 在 `sip` 中是只读的，并由执行环境设置和清除，通常通过平台特定的中断控制器。

`sip`.STIP 和 `sie`.STIE 位是 supervisor 级定时器中断的中断待处理和中断使能位。如果实现，STIP 在 `sip` 中是只读的，并由执行环境设置和清除。

`sip`.SSIP 和 `sie`.SSIE 位是 supervisor 级软件中断的中断待处理和中断使能位。如果实现，SSIP 在 `sip` 中是可写的，也可以由平台特定的中断控制器设置为 1。

如果实现了 Sscofpmf 扩展，则 `sip`.LCOFIP 和 `sie`.LCOFIE 位是本地计数器溢出中断的中断待处理和中断使能位。
LCOFIP 在 `sip` 中是读写的，并反映由于任何 `mhpmevent__n__`.OF 位设置而导致的本地计数器溢出中断请求的发生。
如果未实现 Sscofpmf 扩展，则 `sip`.LCOFIP 和 `sie`.LCOFIE 为只读零。

[NOTE]
====
处理器间中断通过实现特定的方式发送到其他 hart，最终将导致 SSIP 位在接收 hart 的 `sip` 寄存器中设置。
====

每个标准中断类型（SEI、STI、SSI 或 LCOFI）可能未实现，在这种情况下，相应的中断待处理和中断使能位是只读零。`sip` 和 `sie` 中的所有位都是 *WARL* 字段。已实现的中断可以通过将 1 写入 `sie` 中的每个位位置，然后读回以查看哪些位位置为 1 来找到。

[NOTE]
====
`sip` 和 `sie` 寄存器是 `mip` 和 `mie` 寄存器的子集。读取 `sip`/`sie` 的任何已实现字段，或写入任何可写字段，都会影响 `mip`/`mie` 中同名字段的读取或写入。

`sip` 和 `sie` 的位 3、7 和 11 分别对应于机器模式软件、定时器和外部中断。由于大多数平台将选择不将这些中断从 M 模式委托给 S 模式，因此它们在 <<sipreg-standard>> 和 <<siereg-standard>> 中显示为 0。
====

同时针对 supervisor 模式的多个中断按以下递减优先级顺序处理：SEI、SSI、STI、LCOFI。

==== Supervisor 定时器和性能计数器

Supervisor 软件使用与用户模式软件相同的硬件性能监控设施，包括 `time`、`cycle` 和 `instret` CSR。实现应提供一种机制来修改计数器值。

实现必须提供一种设施，用于根据实时计数器 `time` 调度定时器中断。

==== 计数器使能 (`scounteren`) 寄存器

.计数器使能 (`scounteren`) 寄存器
include::images/bytefield/scounteren.edn[]

计数器使能 (`scounteren`) CSR 是一个 32 位寄存器，控制硬件性能监控计数器对 U 模式的可用性。

当 `scounteren` 寄存器中的 CY、TM、IR 或 HPM__n__ 位清除时，在 U 模式下执行时尝试读取 `cycle`、`time`、`instret` 或 `hpmcountern` 寄存器将导致非法指令异常。当这些位中的一个设置时，允许访问相应的寄存器。

`scounteren` 必须实现。然而，任何位都可以是只读零，表示在 U 模式下执行时，读取相应的计数器将导致异常。因此，它们实际上是 *WARL* 字段。

[NOTE]
====
`mcounteren` 中位的设置不影响 `scounteren` 中相应位是否可写。然而，U 模式只有在 `scounteren` 和 `mcounteren` 中相应位都设置时才能访问计数器。
====

==== Supervisor 暂存 (`sscratch`) 寄存器

`sscratch` CSR 是一个 SXLEN 位读/写寄存器，专用于 supervisor。通常，`sscratch` 用于在 hart 执行用户代码时保存指向 hart 局部 supervisor 上下文的指针。
在陷阱处理程序开始时，软件通常使用 CSRRW 指令将 `sscratch` 与整数寄存器交换，以获得初始工作寄存器。

==== Supervisor 异常程序计数器 (`sepc`) 寄存器

`sepc` 是一个 SXLEN 位读/写 CSR，格式如 <<epcreg>> 所示。`sepc` 的低位 (`sepc[0]`) 始终为零。在仅支持 IALIGN=32 的实现上，低两位 (`sepc[1:0]`) 始终为零。

如果实现允许 IALIGN 为 16 或 32（例如通过更改 CSR `misa`），则无论何时 IALIGN=32，`sepc[1]` 位在读取时都会被屏蔽，使其显示为 0。这种屏蔽也发生在 SRET 指令的隐式读取中。尽管被屏蔽，但当 IALIGN=32 时，`sepc[1]` 仍然可写。

`sepc` 是一个 *WARL* 寄存器，必须能够保存所有有效的虚拟地址。它不需要能够保存所有可能的无效地址。在写入 `sepc` 之前，实现可以将无效地址转换为 `sepc` 能够保存的其他无效地址。

当陷阱进入 S 模式时，`sepc` 写入被中断或遇到异常的指令的虚拟地址。否则，`sepc` 从不被实现写入，尽管它可以由软件显式写入。

==== Supervisor 原因 (`scause`) 寄存器

==== Supervisor 陷阱值 (`stval`) 寄存器

`stval` CSR 是一个 SXLEN 位读写寄存器，格式如 <<stvalreg>> 所示。当陷阱进入 S 模式时，`stval` 写入异常特定信息，以帮助软件处理陷阱。否则，`stval` 从不被实现写入，尽管它可以由软件显式写入。硬件平台将指定哪些异常必须有意义地设置 `stval`，哪些可以无条件地将其设置为零，以及哪些可以根据导致异常的底层事件表现出任一行为。

当指令获取、加载或存储发生断点、地址未对齐、访问故障或页故障异常时，如果 `stval` 写入非零值，则 `stval` 将包含故障虚拟地址。

[[stvalreg]]
.Supervisor 陷阱值寄存器。
include::images/bytefield/stvalreg.edn[]

当未对齐加载或存储导致访问故障或页故障异常时，如果 `stval` 写入非零值，则 `stval` 将包含导致故障的访问部分的虚拟地址。

如果 `stval` 写入非零值，并且在具有可变长度指令的系统上发生指令访问故障或页故障异常，则 `stval` 将包含导致故障的指令部分的虚拟地址，而 `sepc` 将指向指令的开头。

`stval` 寄存器还可以选择用于在非法指令异常时返回故障指令位（`sepc` 指向内存中的故障指令）。如果 `stval` 在非法指令异常时写入非零值，则 `stval` 将包含以下最短值：

* 实际故障指令
* 故障指令的前 ILEN 位
* 故障指令的前 SXLEN 位

在非法指令异常时加载到 `stval` 中的值是右对齐的，所有未使用的上位都清零。

在由软件检查异常引起的陷阱上，`stval` 寄存器保存异常的原因。定义了以下编码：

* 0 - 未提供信息。
* 2 - 着陆垫故障。由 Zicfilp 扩展定义（<<priv-forward>>）。
* 3 - 影子栈故障。由 Zicfiss 扩展定义（<<priv-backward>>）。

对于其他陷阱，`stval` 设置为零，但未来的标准可能会重新定义 `stval` 对其他陷阱的设置。

`stval` 是一个 *WARL* 寄存器，必须能够保存所有有效的虚拟地址和值 0。它不需要能够保存所有可能的无效地址。在写入 `stval` 之前，实现可以将无效地址转换为 `stval` 能够保存的其他无效地址。如果实现了返回故障指令位的功能，`stval` 还必须能够保存所有小于 latexmath:[$2^N$] 的值，其中 latexmath:[$N$] 是 SXLEN 和 ILEN 中较小的一个。

[NOTE]
====
FIOM 位存在于特定情况下，当为 U 模式模拟 I/O 设备时，并且以下两个条件都为真：(a) 模拟设备具有应为 I/O 空间但实际上通过地址转换映射到主内存的内存缓冲区，并且 (b) 多个物理 hart 同时从 U 模式访问此模拟设备。

在没有 hypervisor 扩展（<<hypervisor>>）的情况下，在 S 模式下运行的 hypervisor 可能需要为 U 模式模拟设备，如果无法使用半虚拟化。如果同一个 hypervisor 为虚拟机 (VM) 提供多个虚拟 hart，一对一映射到真实 hart，则多个 hart 可以同时访问模拟设备，这可能是因为：(a) VM 中的客户操作系统将设备中断处理分配给一个 hart，而设备也由中断处理程序之外的不同 hart 访问，或者 (b) 设备的控制权（或部分控制权）正在从一个 hart 迁移到另一个 hart，例如为了在 VM 中进行中断负载均衡。对于此类情况，VM 中的客户软件应使用互斥锁和/或处理器间中断来正确协调对（模拟）设备的访问，这部分涉及执行 I/O 栅栏。但是，如果某些设备“I/O”实际上是主内存，而客户机不知道，则这些 I/O 栅栏可能不足。设置 FIOM=1 会修改这些栅栏（以及 U 模式下执行的所有其他 I/O 栅栏），使其也包含主内存。

软件总是可以通过不使用主内存来模拟应为 I/O 空间的设备内存缓冲区来避免设置 FIOM 的需要。
然而，这种选择通常需要捕获所有 U 模式对模拟缓冲区的访问，这可能会对性能产生显著影响。FIOM 提供的替代方案实现成本足够低，我们认为即使很少启用也值得支持。
====

CBZE 字段的定义由 Zicboz 扩展提供。

CBCFE 和 CBIE 字段的定义由 Zicbom 扩展提供。

PMM 字段的定义由 Ssnpm 扩展提供。

Zicfilp 扩展在 `senvcfg` 中添加了 `LPE` 字段。当 `LPE` 字段设置为 1 时，Zicfilp 扩展在 VU/U 模式下启用。当 `LPE` 字段为 0 时，Zicfilp 扩展在 VU/U 模式下未启用，并且以下规则适用于 VU/U 模式：

* hart 不更新 `ELP` 状态；它保持为 `NO_LP_EXPECTED`。
* `LPAD` 指令作为空操作执行。

Zicfiss 扩展在 `senvcfg` 中添加了 `SSE` 字段。当 `SSE` 字段设置为 1 时，Zicfiss 扩展在 VU/U 模式下激活。当 `SSE` 字段为 0 时，Zicfiss 扩展在 VU/U 模式下保持非活动状态，并且以下规则适用：

* 32 位 Zicfiss 指令将恢复其由 Zimop 定义的行为。
* 16 位 Zicfiss 指令将恢复其由 Zcmop 定义的行为。
* 当 `menvcfg.SSE` 为 1 时，`SSAMOSWAP.W/D` 在 U 模式下引发非法指令异常，在 VU 模式下引发虚拟指令异常。

[[satp]]
==== Supervisor 地址转换和保护 (`satp`) 寄存器

`satp` CSR 是一个 SXLEN 位读/写寄存器，格式如 SXLEN=32 时的 <<rv32satp>> 和 SXLEN=64 时的 <<rv64satp>> 所示，它控制 supervisor 模式地址转换和保护。该寄存器保存根页表的物理页号 (PPN)，即其 supervisor 物理地址除以 4 KiB；一个地址空间标识符 (ASID)，用于促进基于每个地址空间的地址转换栅栏；以及 MODE 字段，该字段选择当前地址转换方案。有关此寄存器访问的更多详细信息，请参见 <<virt-control>>。

[[rv32satp]]
.SXLEN=32 时的 Supervisor 地址转换和保护 (`satp`) 寄存器。
include::images/bytefield/rv32satp.edn[]

[NOTE]
====
将 PPN 存储在 `satp` 中，而不是物理地址，支持 RV32 的物理地址空间大于 4 GiB。

`satp`.PPN 字段可能无法保存所有物理页号。某些平台标准可能会对 `satp`.PPN 可能采用的值施加约束，例如，要求所有对应于主内存的物理页号都可表示。
====

[NOTE]
====
我们将 ASID 和页表基地址存储在同一个 CSR 中，以允许在上下文切换时原子地更改这对。非原子地交换它们可能会用新的转换污染旧的虚拟地址空间，反之亦然。这种方法还略微降低了上下文切换的成本。
====

<<satp-mode>> 显示了 SXLEN=32 和 SXLEN=64 时 MODE 字段的编码。
当 MODE=Bare 时，supervisor 虚拟地址等于 supervisor 物理地址，并且除了 <<pmp>> 中描述的物理内存保护方案之外，没有额外的内存保护。要选择 MODE=Bare，软件必须将 `satp` 的其余字段（SXLEN=32 时为位 30-0，SXLEN=64 时为位 59-0）清零。尝试使用非零模式选择 MODE=Bare 会对其余字段的值产生未指定的影响，并对地址转换和保护行为产生未指定的影响。

当 SXLEN=32 时，对应于 MODE=Bare 和 ASID[8:7]=3 的 `satp` 编码指定用于自定义用途，而对应于 MODE=Bare 和 ASID[8:7]≠3 的编码保留用于未来的标准用途。当 SXLEN=64 时，所有对应于 MODE=Bare 的 `satp` 编码保留用于未来的标准用途。

[NOTE]
====
此标准的 1.11 版本声明，当 MODE=Bare 时，`satp` 中的其余字段无效。将这些字段保留有助于未来定义额外的转换和保护模式，特别是在 RV32 中，其中现有 MODE 字段的所有模式都已分配。
====

当 SXLEN=32 时，MODE 的唯一其他有效设置是 Sv32，一种在 <<sv32>> 中描述的页式虚拟内存方案。

当 SXLEN=64 时，定义了三种页式虚拟内存方案：Sv39、Sv48 和 Sv57，分别在 <<sv39>>、<<sv48>> 和 <<sv57>> 中描述。一种额外的方案 Sv64 将在未来版本的本规范中定义。其余 MODE 设置保留供将来使用，并且可能定义 `satp` 中其他字段的不同解释。

不要求实现支持所有 MODE 设置，如果 `satp` 写入不支持的 MODE，则整个写入无效；`satp` 中的任何字段都不会被修改。

对于许多应用程序，页面大小的选择对性能有实质性影响。大页面大小增加了 TLB 覆盖范围，并放宽了虚拟索引、物理标记缓存的关联性约束。同时，大页面加剧了内部碎片，浪费了物理内存和可能的缓存容量。

经过深思熟虑，我们为 RV32 和 RV64 都确定了 4 KiB 的常规页面大小。我们预计这一决定将简化低级运行时软件和设备驱动程序的移植。现代操作系统中透明的超大页面支持缓解了 TLB 覆盖范围问题。 cite:[transparent-superpages] 此外，多级 TLB 层次结构相对于其映射的地址空间的复杂多级缓存层次结构来说，成本相当低。
====

`satp` CSR 在有效特权模式为 S 模式或 U 模式时被视为 _活动_。地址转换算法的执行只能在 `satp` 活动时开始使用给定的 `satp` 值。

[NOTE]
====
当 `satp` 不再活动时，不要求在 `satp` 活动时开始的转换完成或终止，除非执行了匹配地址和 ASID 的 SFENCE.VMA 指令。SFENCE.VMA 指令必须用于确保 hart 对这些结构的后续隐式读取观察到地址转换数据结构的更新。
====

请注意，写入 `satp` 不意味着页表更新和后续地址转换之间有任何排序约束，也不意味着地址转换缓存的任何失效。如果已修改新地址空间的页表，或者 ASID 被重用，则可能需要在写入 `satp` 之后（或在某些情况下之前）执行 SFENCE.VMA 指令（参见 <<sfence.vma>>）。

[NOTE]
====
在 `satp` 写入时不对实现施加刷新地址转换缓存的要求，可以降低上下文切换的成本，前提是 ASID 空间足够大。
====

对于使 `satp`.MODE 只读零（始终为 Bare）的实现，尝试执行 SFENCE.VMA 指令可能会引发非法指令异常。

[[sv32]]
=== Sv32：基于页的 32 位虚拟内存系统

当 `satp` 寄存器（参见 <<satp>>）中的 MODE 字段写入 Sv32 时，supervisor 在 32 位页式虚拟内存系统中运行。在此模式下，supervisor 和用户虚拟地址通过遍历基数树页表转换为 supervisor 物理地址。Sv32 在 SXLEN=32 时受支持，旨在包含足以支持现代基于 Unix 的操作系统的机制。

[NOTE]
====
最初的 RISC-V 页式虚拟内存架构被设计为直接实现，以支持现有操作系统。我们设计了页表布局以支持硬件页表遍历器。软件 TLB 填充是高性能系统上的性能瓶颈，并且对于解耦的专用协处理器尤其麻烦。实现可以选择使用机器模式陷阱处理程序作为 M 模式的扩展来实现软件 TLB 填充。

***

一些 ISA 在架构上暴露了 _虚拟索引、物理标记_ 缓存，因为通过不同虚拟地址访问相同物理地址可能不一致，除非虚拟地址位于同一缓存集中。隐式地，本规范不允许这种行为在架构上暴露。
====

[[translation]]
==== 寻址和内存保护

Sv32 实现支持 32 位虚拟地址空间，分为页面。Sv32 虚拟地址分为虚拟页号 (VPN) 和页偏移量，如 <<sv32va>> 所示。
当 `satp` 寄存器 MODE 字段中选择 Sv32 虚拟内存模式时，supervisor 虚拟地址通过两级页表转换为 supervisor 物理地址。20 位 VPN 转换为 22 位物理页号 (PPN)，而 12 位页偏移量未转换。生成的 supervisor 级物理地址然后使用任何物理内存保护结构（<<pmp>>）进行检查，然后直接转换为机器级物理地址。如果需要，supervisor 级物理地址零扩展到实现中物理地址位的数量。

[NOTE]
====
例如，考虑一个支持 34 位物理地址的 RV32 系统。当 `satp`.MODE 的值为 Sv32 时，直接生成 34 位物理地址，因此不需要零扩展。当 `satp`.MODE 的值为 Bare 时，32 位虚拟地址（未修改）转换为 32 位物理地址，然后该物理地址零扩展为 34 位机器级物理地址。
====

尝试从没有执行权限的页面获取指令会引发获取页故障异常。尝试执行有效地址位于没有读取权限的页面内的加载或加载-预留指令会引发加载页故障异常。尝试执行有效地址位于没有写入权限的页面内的存储、条件存储或 AMO 指令会引发存储页故障异常。

[NOTE]
====
AMO 永远不会引发加载页故障异常。由于任何不可读页面也是不可写的，因此尝试对不可读页面执行 AMO 总是会引发存储页故障异常。
====

U 位指示页面是否可由用户模式访问。U 模式软件仅当 U=1 时才能访问页面。如果 `sstatus` 寄存器中的 SUM 位设置，则 supervisor 模式软件也可以访问 U=1 的页面。然而，supervisor 代码通常在 SUM 位清除的情况下运行，在这种情况下，supervisor 代码将对用户模式页面的访问产生故障。无论 SUM 如何，supervisor 都不能在 U=1 的页面上执行代码。

[NOTE]
====
另一种 PTE 格式将支持 supervisor 和用户的不同权限。我们省略了此功能，因为它与 SUM 机制（参见 <<sum>>）基本冗余，并且需要 PTE 中更多的编码空间。
====

G 位指定 _全局_ 映射。全局映射是指存在于所有地址空间中的映射。对于非叶 PTE，全局设置意味着页表后续级别中的所有映射都是全局的。请注意，未能将全局映射标记为全局只会降低性能，而将非全局映射标记为全局是软件错误，在切换到具有不同非全局映射的地址空间后，可能会不可预测地导致使用其中一个映射。

[NOTE]
====
全局映射无需在地址转换缓存中为多个 ASID 冗余存储。此外，当执行 SFENCE.VMA 指令且 __rs2__≠`x0` 时，它们无需从本地地址转换缓存中刷新。
====

RSW 字段保留供 supervisor 软件使用；实现应忽略此字段。

每个叶 PTE 包含一个访问 (A) 和脏 (D) 位。A 位指示自上次清除 A 位以来，虚拟页面已被读取、写入或获取。D 位指示自上次清除 D 位以来，虚拟页面已被写入。

定义了两种管理 A 和 D 位的方案：

* _Svade_ 扩展：当虚拟页面被访问且 A 位清除，或被写入且 D 位清除时，会引发页故障异常。

* 当未实现 Svade 扩展时，适用以下方案。 +
                                                                             +
  当虚拟页面被访问且 A 位清除时，PTE 会更新以设置 A 位。当虚拟页面被写入且 D 位清除时，PTE 会更新以设置 D 位。当 G 阶段地址转换在使用且不是 Bare 时，G 阶段虚拟页面可能会被隐式访问 VS 级内存管理数据结构（例如页表）访问或写入。 +
                                                                        +
  当两阶段地址转换在使用时，显式访问可能会导致 VS 阶段和 G 阶段 PTE 都被更新。以下规则适用于由显式或隐式内存访问引起的所有 PTE 更新。 +
                                                                        +
  PTE 更新必须相对于对 PTE 的其他访问是原子的，并且必须原子地执行该叶 PTE 的所有页表遍历检查，作为条件更新 PTE 值的一部分，并在条件更新 PTE 值之前。A 位的更新可能是推测性执行的结果，即使关联的内存访问最终未在架构上执行。然而，D 位的更新（由显式存储引起）必须是精确的（即非推测性的），并且由本地 hart 按程序顺序观察到。当两阶段地址转换处于活动状态时，G 阶段 PTE 中 D 位的更新可以通过隐式访问 VS 阶段 PTE 来执行，如果 G 阶段 PTE 提供写入权限，则在任何推测性访问 VS 阶段 PTE 之前。 +
                                                                        +
  PTE 更新必须在全局内存顺序中出现在导致 PTE 更新的内存访问之前，以及在本地 hart 对该虚拟页面的任何后续显式内存访问之前。FENCE 指令提供的加载和存储排序以及原子指令上的获取/释放位也排序了与这些加载和存储关联的 PTE 更新，如远程 hart 所观察到的。 +
                                                                        +
  PTE 更新不需要相对于导致更新的内存访问是原子的，并且在 PTE 更新和导致 PTE 更新的内存访问之间可能会发生陷阱。如果发生陷阱，则 A 和/或 D 位可能会更新，但导致 PTE 更新的内存访问可能不会发生。hart 不得在 PTE 更新全局可见之前执行导致 PTE 更新的内存访问。 +
                                                                        +
  页表必须位于具有硬件页表写入访问和 _RsrvEventual_ PMA 的内存中。

系统中的所有 hart 必须采用相同的 PTE 更新方案。

[NOTE]
====
由于内存访问而导致的 PTE 更新（在 FENCE 之后排序）本身不受 FENCE 的排序。

更简单的实现可以命令页表条目 (PTE) 更新先于所有后续显式内存访问，而不是确保 PTE 更新在后续显式内存访问关联虚拟页面之前精确排序。

本规范的先前版本要求 PTE A 位更新是精确的，但允许 A 位作为推测的结果进行更新简化了地址转换预取器的实现。系统软件通常使用 A 位作为页面替换策略提示，但不需要精确性以实现功能正确性。另一方面，D 位更新仍然要求精确并按程序顺序执行，因为 D 位影响页面逐出的功能正确性。

当然，实现仍然允许以精确的方式执行 A 和 D 位更新。

在这两种情况下，要求原子性可确保 PTE 更新不会被对页表的其他介入写入中断，因为此类中断可能导致 A/D 位在已用于其他目的的 PTE 上设置，在已回收用于其他目的的内存上设置，等等。简单的实现可以改为生成页故障异常。

A 和 D 位永远不会由实现清除。如果 supervisor 软件不依赖访问和/或脏位，例如，如果它不将内存页面交换到辅助存储或页面用于映射 I/O 空间，则它应始终在 PTE 中将它们设置为 1 以提高性能。
====

任何级别的 PTE 都可以是叶 PTE，因此除了 4 KiB 页面之外，Sv32 还支持 4 MiB _巨页_。巨页必须在虚拟和物理上对齐到 4 MiB 边界；如果物理地址未充分对齐，则会引发页故障异常。

对于非叶 PTE，D、A 和 U 位保留供将来标准使用。在它们的用途由标准扩展定义之前，软件必须将它们清零以实现向前兼容性。

对于同时具有基于页的虚拟内存和“A”标准扩展的实现，LR/SC 预留集必须完全位于单个基本物理页面内（即，自然对齐的 4 KiB 物理内存区域）。

在某些实现中，未对齐的加载、存储和指令获取也可能分解为多个访问，其中一些可能在发生页故障异常之前成功。特别是，未对齐存储的一部分（通过异常检查）可能变得可见，即使另一部分未能通过异常检查。相同的行为可能出现在宽于 XLEN 位的存储中（例如，RV32D 中的 FSD 指令），即使存储地址自然对齐。


[[sv32algorithm]]
==== 虚拟地址转换过程

虚拟地址 _va_ 转换为物理地址 _pa_ 如下：

. 令 _a_ 为 `satp`.__ppn__×PAGESIZE，令 __i__=LEVELS-1。（对于 Sv32，PAGESIZE=2^12^ 且 LEVELS=2。）`satp` 寄存器必须处于 _活动_ 状态，即有效特权模式必须是 S 模式或 U 模式。

. 令 _pte_ 为地址 __a__+__va__.__vpn__[__i__]×PTESIZE 处的 PTE 值。（对于 Sv32，PTESIZE=4。）如果访问 _pte_ 违反 PMA 或 PMP 检查，则引发与原始访问类型对应的访问故障异常。

. 如果 _pte_._v_=0，或者如果 _pte_._r_=0 且 _pte_._w_=1，或者如果 _pte_ 中设置了任何保留供将来标准使用的位或编码，则停止并引发与原始访问类型对应的页故障异常。

. 否则，PTE 有效。如果 __pte__.__r__=1 或 __pte__.__x__=1，则转到步骤 5。否则，此 PTE 是指向页表下一级的指针。令 __i=i__-1。如果 __i__<0，则停止并引发与原始访问类型对应的页故障异常。否则，令 __a__=__pte__.__ppn__×PAGESIZE 并转到步骤 2。

. 已到达叶 PTE。如果 _i>0_ 且 _pte_._ppn_[__i__-1:0] ≠ 0，则这是一个未对齐的超大页面；停止并引发与原始访问类型对应的页故障异常。

. 根据当前特权模式以及 *mstatus* 寄存器中 SUM 和 MXR 字段的值，确定请求的内存访问是否允许由 _pte_._u_ 位。如果否，则停止并引发与原始访问类型对应的页故障异常。

. 根据影子栈内存保护规则，确定请求的内存访问是否允许由 _pte_._r_、_pte_._w_ 和 _pte_._x_ 位。如果否，则停止并引发访问故障异常。

. 确定请求的内存访问是否允许由 _pte_._r_、_pte_._w_ 和 _pte_._x_ 位。如果否，则停止并引发与原始访问类型对应的页故障异常。

. 如果 _pte_._a_=0，或者如果原始内存访问是存储且 _pte_._d_=0：

* 如果实现了 Svade 扩展，则停止并引发与原始访问类型对应的页故障异常。
* 如果对 _pte_ 的存储违反 PMA 或 PMP 检查，则引发与原始访问类型对应的访问故障异常。
* 原子地执行以下步骤：
** 将 _pte_ 与地址 __a__+__va.vpn__[__i__]×PTESIZE 处的 PTE 值进行比较。
** 如果值匹配，则将 _pte_._a_ 设置为 1，如果原始内存访问是存储，则也将 _pte_._d_ 设置为 1。
** 如果比较失败，则返回步骤 2。

. 转换成功。转换后的物理地址如下：
* _pa.pgoff_ = _va.pgoff_。
* 如果 _i_>0，则这是一个超大页面转换，并且 __pa.ppn__[__i__-1:0] = __va.vpn__[__i__-1:0]。
* _pa.ppn_[LEVELS-1:__i__] = _pte_._ppn_[LEVELS-1:__i__]。

此算法中对地址转换数据结构的所有隐式访问都使用宽度 PTESIZE 执行。

[NOTE]
====
这意味着，例如，Sv48 实现不能使用两个单独的 4B 读取来非原子地访问单个 8B PTE，并且实现执行的 A/D 位更新被视为原子地更新整个 PTE，而不仅仅是 A 和/或 D 位（即使 PTE 值没有其他变化）。
====

步骤 2 中隐式地址转换读取的结果可以保存在只读、非一致的 _地址转换缓存_ 中，但不能与其他 hart 共享。地址转换缓存可以保存任意数量的条目，包括相同地址和 ASID 的任意数量的条目。地址转换缓存中的条目可以满足后续步骤 2 读取，如果与条目关联的 ASID 与步骤 0 中加载的 ASID 匹配，或者如果条目与 _全局_ 映射关联。为了确保隐式读取观察到对相同内存位置的写入，必须在写入后执行 SFENCE.VMA 指令以刷新相关的缓存转换。

地址转换缓存不能在步骤 9 中使用；访问和脏位只能直接在内存中更新。
[NOTE]
====
允许存在多个地址转换缓存条目用于同一地址。这表示在传统的 TLB 层次结构中，如果例如页面升级为超大页面而未首先清除原始非叶 PTE 的有效位并执行 SFENCE.VMA 且 _rs1_=`x0`，或者如果在给定层次级别存在多个 TLB，则可能存在多个条目匹配单个地址。在这种情况下，就像在写入内存管理表和随后隐式读取相同地址之间未执行 SFENCE.VMA 一样：旧的非叶 PTE 或新的叶 PTE 是否使用是不可预测的，但行为在其他方面是明确定义的。
====

实现还可以随时推测性地执行地址转换算法，对于任何虚拟地址，只要 `satp` 处于活动状态（如 <<satp>> 中定义）。此类推测性执行具有预填充地址转换缓存的效果。

地址转换算法的推测性执行行为与非推测性执行行为相同，只是它们不得设置 PTE 的脏位，不得触发异常，并且不得创建地址转换缓存条目，如果这些条目将被 hart 执行的任何 SFENCE.VMA 指令自算法推测性执行开始以来失效。

[NOTE]
====
例如，对于翻译算法的非推测性和推测性执行，都不能开始，读取 2 级页表，在 hart 执行 SFENCE.VMA 且 _rs1_=_rs2_=`x0` 时暂停，然后使用现在过时的 2 级 PTE 恢复，因为后续的隐式读取可能会用过时的 PTE 填充地址转换缓存。

在许多实现中，带有 _rs1_=`x0` 的 SFENCE.VMA 指令因此要么终止所有先前启动的地址转换算法的推测性执行（如果适用，对于指定的 ASID），要么简单地等待它们完成（在这种情况下，创建的任何地址转换缓存条目将由 SFENCE.VMA 适当失效）。同样，带有 __rs1__≠``x0`` 的 SFENCE.VMA 指令通常必须要么确保先前启动的地址转换算法的推测性执行（如果适用，对于指定的 ASID）被阻止创建新的地址转换缓存条目映射叶 PTE，要么等待它们完成。

实现被允许任意早地推测性读取转换数据结构的一个结果是，在任何时候，所有通过执行算法可到达的页表条目都可以加载到地址转换缓存中。

尽管将页表放置在非幂等内存中是不常见的，但没有明确禁止这样做。由于算法只能触及 `satp` 中指示的根页表可到达的页表，因此实现页表遍历器将触及的地址范围完全在 supervisor 控制之下。

***

该算法不承认对于具有较窄物理地址的实现忽略高阶 PPN 位的可能性。
====

[[sv39]]
=== Sv39：基于页的 39 位虚拟内存系统

本节描述了 SXLEN=64 的简单页式虚拟内存系统，它支持 39 位虚拟地址空间。Sv39 的设计遵循 Sv32 的总体方案，本节仅详细说明两种方案之间的差异。

[NOTE]
====
我们为 RV64 指定了多个虚拟内存系统，以缓解在提供大地址空间和最小化地址转换成本之间的矛盾。对于许多系统，39 位虚拟地址空间足够大，因此 Sv39 就足够了。Sv48 将虚拟地址空间增加到 48 位，但增加了用于页表的物理内存容量、页表遍历的延迟以及存储虚拟地址的硬件结构的大小。Sv57 进一步增加了虚拟地址空间、页表容量要求和转换延迟。
====

[[addressing-and-memory-protection]]
==== 寻址和内存保护

Sv39 实现支持 39 位虚拟地址空间，分为页面。Sv39 地址的划分如 <<sv39va>> 所示。指令获取地址以及加载和存储有效地址（64 位）必须使位 63-39 都等于位 38，否则将发生页故障异常。27 位 VPN 通过三级页表转换为 44 位 PPN，而 12 位页偏移量未转换。

[NOTE]
====
在较窄和较宽地址之间映射时，RISC-V 将较窄的物理地址零扩展到较宽的大小。64 位虚拟地址和 Sv39 的 39 位可用地址空间之间的映射不是基于零扩展，而是遵循一种根深蒂固的约定，该约定允许操作系统使用全尺寸（64 位）虚拟地址的一个或几个最高有效位来快速区分用户和 supervisor 地址区域。
====

Sv39 页表包含 2^9^ 个页表条目 (PTE)，每个条目八字节。页表的大小恰好是一个页面，并且必须始终对齐到页面边界。根页表的物理页号存储在 `satp` 寄存器的 PPN 字段中。

Sv39 的 PTE 格式如 <<sv39pte>> 所示。
位 9-0 的含义与 Sv32 相同。位 63 保留供 <<svnapot>> 中的 Svnapot 扩展使用。如果未实现 Svnapot，则位 63 保持保留，并且软件必须将其清零以实现向前兼容性，否则将引发页故障异常。位 62-61 保留供 <<svpbmt>> 中的 Svpbmt 扩展使用。如果未实现 Svpbmt，则位 62-61 保持保留，并且软件必须将其清零以实现向前兼容性，否则将引发页故障异常。位 60-54 保留供将来标准使用，并且在它们的用途由标准扩展定义之前，软件必须将其清零以实现向前兼容性。如果这些位中的任何一个被设置，则会引发页故障异常。

[NOTE]
====
我们保留了几个 PTE 位，用于可能通过跳过页表级别来改进对稀疏地址空间支持的扩展，从而减少内存使用和 TLB 填充延迟。这些保留位也可以用于促进研究实验。代价是减少物理地址空间，但目前足够。当它不再足够时，未分配的保留位可以用于扩展物理地址空间。
====

任何级别的 PTE 都可以是叶 PTE，因此除了 4 KiB 页面之外，Sv39 还支持 2 MiB _巨页_ 和 1 GiB _千兆页_，每个都必须在虚拟和物理上对齐到与其大小相等的边界。如果物理地址未充分对齐，则会引发页故障异常。

虚拟到物理地址转换的算法与 <<sv32algorithm>> 中的算法相同，只是 LEVELS 等于 3 且 PTESIZE 等于 8。

* 隐式读取 NAPOT 页表条目可能会创建地址转换缓存条目，将 _a_ + _j_×PTESIZE 映射到 _pte_ 的副本，其中 _pte_._ppn_[_i_][_pte_.__napot_bits__-1:0] 被 _vpn[i][pte.napot_bits_-1:0] 替换，适用于任何或所有 _j_，使得 __j__ >> __napot_bits__ = __vpn__[__i__] >> __napot_bits__，所有这些都适用于步骤 1 中加载的 _satp_ 中标识的地址空间。

[NOTE]
====
NAPOT PTE 的动机是它可以作为 TLB 中的一个或多个条目缓存，表示连续区域，就像它是由单个转换覆盖的单个（大）页面一样。这种压缩有助于在某些情况下缓解 TLB 压力。该编码旨在适应预先存在的 Sv39、Sv48 和 Sv57 PTE 格式，以免干扰选择不实现该方案的现有实现或设计。它还旨在不使地址转换算法的定义复杂化。

地址转换缓存抽象捕获了创建覆盖整个 NAPOT 区域的单个 TLB 条目所产生的行为。它还旨在与通过将 NAPOT 区域拆分为覆盖任何较小 2 的幂区域大小的 TLB 条目来支持 NAPOT PTE 的实现保持一致。例如，一个 64 KiB NAPOT PTE 可能会触发创建 16 个标准 4 KiB TLB 条目，所有这些条目都包含从 NAPOT PTE 生成的内容（即使其他 4 KiB 区域的 PTE 具有不同的内容）。

在典型使用场景中，同一区域中的 NAPOT PTE 将具有相同的属性、相同的 PPN 和相同的位 5-0 值。RSW 仍保留用于 supervisor 软件控制。操作系统和/或 hypervisor 有责任以确保 NAPOT PTE 与重叠相同地址范围的其他 NAPOT 或非 NAPOT PTE 之间没有不一致的方式配置页表。如果需要进行更新，操作系统通常应首先将所有 PTE 标记为无效，然后发出覆盖该范围内所有 4 KiB 区域的 SFENCE.VMA 指令（通过单个 SFENCE.VMA 且 _rs1_=`x0`，或通过多个 SFENCE.VMA 指令且 _rs1_≠`x0`），然后更新 PTE，如 <<sfence.vma>> 中所述，除非已知任何不一致之处是良性的。如果确实存在任何不一致之处，则效果与 SFENCE.VMA 使用不正确时相同：将选择其中一个转换，但选择是不可预测的。

当 PBMT 字段编码为 PMA 时，页面的内存属性由平台中的物理内存属性确定。

====

====

每个 PTE 还具有 N 位（位 63），当物理地址低端对齐至少为 4 KB 时适用（例如，当中间页表项指向物理地址或数据页时）。当 N=1 时，它指示（跨该页的）指令获取可能会导致不可获取的指令异常，并且页面不应被硬件指令预取器缓存在指令缓存中。

[NOTE]
====
所有平台都必须支持所有定义的内存类型，但某些类型的效果可能相同。例如，可以实现 NC 和 IO 以具有相同的行为。

术语"弱"和"强"推测指的是相对投机性的内存访问，其中"弱"允许较少的推测性访问（例如，仅向前推测），"强"允许更多的推测性访问（例如，多个方向的推测）。

[[sec:ssqosid]]
== "Ssqosid" 扩展：服务质量 (QoS) 标识符，版本 1.0

服务质量 (QoS) 定义为服务级别协议 (SLA) 向工作负载提前保证的最小端到端性能。性能指标可能包括每周期指令数 (IPC)、服务延迟等度量。

当多个工作负载在现代处理器（配备大型核心计数、多个缓存层次结构和多个内存控制器）上并发执行时，由于共享资源争用，任何给定工作负载的性能变得不那么确定，甚至是非确定性的。

为了管理性能变化，系统软件需要资源分配和监视功能。这些功能允许保留缓存和带宽等资源，从而满足个别性能目标，同时最小化干扰。对于资源管理，硬件应提供监视功能，允许系统软件分析工作负载资源消耗并相应地分配资源。

为了促进这一点，QoS 标识符扩展 (Ssqosid) 引入了 `srmcfg` 寄存器，该寄存器为 hart 配置两个标识符：资源控制 ID (`RCID`) 和监视计数器 ID (`MCID`)。这些标识符伴随 hart 向共享资源控制器发出的每个请求。

附加元数据，如内存访问的性质和发起监督域的 ID，可以伴随 `RCID` 和 `MCID`。资源控制器可以使用此元数据进行差异化服务，如对代码存储与数据存储进行不同的容量分配。资源控制器可以将此数据用于安全策略，如不向另一个安全域暴露一个安全域的统计信息。

=== Supervisor 资源管理配置 (`srmcfg`) 寄存器

`srmcfg` 寄存器是一个 SXLEN 位读/写寄存器，用于配置 hart 的 QoS 标识符。该寄存器的格式在 RV64 的情况下如下所示：

[wavedrom, ,svg]
....
{reg: [
  {bits: 16, name: 'RCID'},
  {bits: 16, name: 'MCID'},
  {bits: 32, name: 'WPRI'},
], config:{lanes: 1, hspace:1024}}
....

对于 RV32，该寄存器的格式类似，但寄存器宽度为 32 位。

RCID 字段指定资源控制 ID，MCID 字段指定监视计数器 ID。

`srmcfg` 中的 `RCID` 和 `MCID` 适用于 hart 上的所有特权级别。通常，更高特权模式不修改 `srmcfg`，因为它们通常为较低特权的任务提供服务。如果需要区分，更高特权代码可以更新 `srmcfg` 并在返回到较低特权级别之前恢复它。

在 VM 环境中，管理程序通常管理资源分配，使客户操作系统不参与 QoS 流。如果需要，管理程序可以使用在客户访问时触发的虚拟指令异常为 VM 虚拟化 `srmcfg` CSR。如果 VM 直接选择 `RCID` 和 `MCID` 变得常见且仿真开销成为问题，未来的扩展可能允许 VS 模式使用选择器来访问管理程序配置的一组 CSR，这些 CSR 保存指定给该客户操作系统使用的 `RCID` 和 `MCID` 值。

在上下文切换期间，监督程序可以选择使用传出上下文的 `srmcfg` 执行，以将执行归因于它。在恢复新上下文之前，它切换到新 VM 的 `srmcfg`。监督程序还可以使用单独的配置执行，以便不归因于任一上下文。
