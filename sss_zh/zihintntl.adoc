== “Zihintntl”非临时局部性提示扩展，版本 1.0

NTL 指令是 HINT，表示紧随其后的指令（以下称为“目标指令”）的显式内存访问表现出较差的时间局部性。NTL 指令不会改变体系结构状态，也不会改变目标指令的体系结构可见效果。提供了四种变体：

NTL.P1 指令表示目标指令在内存层次结构中最内层私有缓存的容量内不表现出时间局部性。NTL.P1 编码为 ADD _x0, x0, x2_。

NTL.PALL 指令表示目标指令在内存层次结构中任何级别的私有缓存的容量内都不表现出时间局部性。NTL.PALL 编码为 ADD _x0, x0, x3_。

NTL.S1 指令表示目标指令在内存层次结构中最内层共享缓存的容量内不表现出时间局部性。NTL.S1 编码为 ADD _x0, x0, x4_。

NTL.ALL 指令表示目标指令在内存层次结构中任何级别的缓存的容量内都不表现出时间局部性。NTL.ALL 编码为 ADD _x0, x0, x5_。

[NOTE]
====
NTL 指令可用于在流式传输数据或遍历大型数据结构时避免缓存污染，或减少生产者-消费者交互中的延迟。

微体系结构可以使用 NTL 指令来通知缓存替换策略，或决定分配到哪个缓存，或完全避免缓存分配。例如，NTL.P1 可能表示实现不应在私有 L1 缓存中分配行，而应在 L2（无论是私有还是共享）中分配。在另一个实现中，NTL.P1 可能会在 L1 中分配行，但处于最近最少使用的状态。

NTL.ALL 通常会通知实现不要在缓存层次结构中的任何位置进行分配。程序员应将 NTL.ALL 用于没有可利用的时间局部性的访问。

与任何 HINT 一样，这些指令可以被自由忽略。因此，尽管它们是根据基于缓存的内存层次结构来描述的，但它们并不强制要求提供缓存。

某些实现可能会对某些内存访问遵守这些 HINT，而对其他内存访问则不遵守：例如，通过在 L1 中以独占状态获取缓存行来实现 LR/SC 的实现可能会忽略 LR 和 SC 上的 NTL 指令，但可能会遵守 AMO 和常规加载和存储的 NTL 指令。
====

如果提供了 C 扩展，则还提供了这些 HINT 的压缩变体：C.NTL.P1 编码为 C.ADD _x0, x2_；C.NTL.PALL 编码为 C.ADD _x0, x3_；C.NTL.S1 编码为 C.ADD _x0, x4_；C.NTL.ALL 编码为 C.ADD _x0, x5_。

NTL 指令影响除 Zicbom 扩展中的缓存管理指令之外的所有内存访问指令。

[NOTE]
====
在撰写本文时，此规则没有其他例外，因此 NTL 指令影响基本 ISA 和 A、F、D、Q、C 和 V 标准扩展中定义的所有内存访问指令，以及第二卷中虚拟机管理程序扩展中定义的那些指令。

NTL 指令可以影响除 Zicbom 扩展中的缓存管理操作之外的缓存管理操作。例如，NTL.PALL 后跟 CBO.ZERO 可能表示该行应在 L3 中分配并清零，但不在 L1 或 L2 中分配。

当 NTL 指令应用于 Zicbop 扩展中的预取提示时，它表示应将缓存行预取到比 NTL 指定的级别更_外层_的缓存中。

[NOTE]
====
例如，在具有私有 L1 和共享 L2 的系统中，NTL.P1 后跟 PREFETCH.R 可能会以读取意图预取到 L2 中。

要预取到最内层的缓存中，请不要在预取指令前加上 NTL 指令。

在某些系统中，NTL.ALL 后跟预取指令可能会预取到内存控制器内部的缓存或预取缓冲区中。
====

不鼓励软件在 NTL 指令后跟不显式访问内存的指令。不遵守此建议可能会降低性能，但不会产生其他体系结构可见的影响。

如果在目标指令上发生陷阱，则不鼓励实现将 NTL 应用于陷阱处理程序中的第一条指令。相反，建议实现在这种情况下忽略 HINT。

[NOTE]
====
如果在 NTL 指令及其目标指令的执行之间发生中断，则执行通常将在目标指令处恢复。NTL 指令未重新执行不会改变程序的语义。

某些实现可能更愿意在看到目标指令之前不处理 NTL 指令（例如，以便 NTL 可以与其修改的内存访问融合）。此类实现可能更愿意在 NTL 之前而不是在 NTL 和内存访问之间接受中断。
====
'''''
[NOTE]
====
由于 NTL 指令被编码为 ADD，因此它们可以在 LR/SC 循环中使用而不会使前向进度保证无效。但是，由于在 LR/SC 循环中使用其他加载和存储_确实_会使前向进度保证无效，因此在此类循环中使用 NTL 的唯一原因是修改 LR 或 SC。

=== 性能影响和最佳实践

软件开发者在使用 NTL 指令时应考虑以下性能影响和最佳实践：

==== 工作集分析

在决定使用哪个 NTL 变体之前，开发者应分析其应用程序的内存访问模式：

1. **小工作集** (< L1 缓存大小)：通常不需要 NTL 指令。
2. **中等工作集** (L1 < 大小 < L2)：使用 NTL.P1 避免污染 L1。
3. **大工作集** (> L2 缓存大小)：使用 NTL.PALL 或 NTL.S1。
4. **流式访问**：使用 NTL.ALL 避免所有缓存分配。

==== 代码示例

以下示例演示了 NTL 指令的典型使用场景：

```assembly
# 流式复制大量数据
stream_copy:
    ntl.all
    ld      t0, 0(a0)       # 从源地址加载
    ntl.all  
    sd      t0, 0(a1)       # 存储到目标地址
    addi    a0, a0, 8
    addi    a1, a1, 8
    bne     a0, a2, stream_copy

# 遍历大型数据结构
large_array_scan:
    ntl.pall
    ld      t0, 0(a0)       # 访问数组元素
    # 处理数据
    addi    a0, a0, 8
    bne     a0, a1, large_array_scan

# 访问争用的同步变量
acquire_lock:
    ntl.pall
    lr.w    t0, (a0)        # 加载-保留锁变量
    bnez    t0, acquire_lock
    li      t1, 1
    sc.w    t2, t1, (a0)    # 尝试获取锁
    bnez    t2, acquire_lock
```

==== 缓存层次结构优化

不同的缓存配置需要不同的 NTL 策略：

**单级私有缓存系统**：
- 所有 NTL 变体（P1、PALL、S1、ALL）都映射到同一缓存级别
- 只有 NTL.ALL 有意义，用于避免缓存分配

**多级私有缓存系统**：
- NTL.P1：避免最内层私有缓存分配
- NTL.PALL：避免所有私有缓存分配
- 适用于 CPU 密集型应用的数据局部性优化

**混合缓存层次结构**：
- 需要根据具体的私有/共享缓存配置选择合适的 NTL 变体
- 软件应该针对目标平台的缓存层次结构进行调优

==== 与预取指令的交互

NTL 指令与 Zicbop 扩展中的预取指令结合使用时：

```assembly
# 预取到外层缓存
ntl.p1
prefetch.r  0(a0)       # 预取到 L2（而不是 L1）

# 预取到内存控制器缓存
ntl.all
prefetch.w  64(a0)      # 预取到内存控制器缓冲区
```

这种组合允许精确控制预取行为，优化内存带宽利用。

==== 多线程环境考虑

在多线程应用中使用 NTL 指令的考虑因素：

1. **共享数据访问**：使用 NTL.S1 或 NTL.ALL 避免在私有缓存中分配共享数据。

2. **生产者-消费者模式**：生产者使用 NTL.PALL 写入数据，减少消费者的缓存未命中延迟。

3. **锁争用缓解**：在获取高争用锁时使用 NTL.PALL，减少缓存一致性开销。

==== 实现特定的优化

不同的实现可能对 NTL 指令有不同的响应：

**积极实现**：
- 严格遵守 NTL 提示
- 可能提供细粒度的缓存控制
- 适合高性能计算应用

**保守实现**：
- 可能忽略某些 NTL 指令
- 提供基本的缓存管理功能
- 适合一般用途应用

**自适应实现**：
- 根据运行时行为动态调整 NTL 响应
- 可能结合硬件性能计数器进行优化

==== 调试和性能分析

使用 NTL 指令时的调试技巧：

1. **性能计数器**：监控缓存未命中率和内存带宽利用率。

2. **微基准测试**：创建简单的测试用例验证 NTL 指令的效果。

3. **系统性能分析**：使用工具如 `perf` 分析整体系统性能影响。

4. **A/B 测试**：比较有和没有 NTL 指令的代码性能。

通过遵循这些最佳实践，软件开发者可以有效利用 NTL 指令提高应用程序的内存性能，特别是在处理大量数据或高争用同步的情况下。
====
